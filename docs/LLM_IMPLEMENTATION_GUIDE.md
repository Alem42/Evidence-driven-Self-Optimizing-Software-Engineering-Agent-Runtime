# MASA：面向后续 LLM 的实施入口与会话协议

版本 v0.3 / 2026-09-26。本文是后续实现整个项目的操作入口，不要求一次会话完成所有内容。必须结合当前用户消息判断本轮是设计、审查还是代码实现。

## 1. 首要目标

构建一个小而完整、可重构的 Evidence-driven Agent Runtime：先有可运行图与真实工具链，再增加 Go 仓库代码证据、上下文、多角色闭环；最后在有效数据上尝试经验驱动的策略优化。

短名称 MASA。Self-Optimizing 是 P2 目标，未验证前不要写已具有自学习提升。用户已认可前序规划；本轮文档整理不等于已要求立即编码。下一轮如果用户说“开始实现/继续开发”，按路线自主推进，不重复请求同一范围的确认。

## 2. 每次启动必读与事实检查

依次读：[项目长期约定](MEMORY_PROJECT.md) → 本文件 → [STATUS_PROJECT](STATUS_PROJECT.md) → [PLAN_PRIORITY_ROADMAP](PLAN_PRIORITY_ROADMAP.md) → 最近一份 progress 报告 → 本轮相关 DESIGN。

- 查实际文件和 Git 状态（如果已初始化），识别用户已有改动；文档写完成但文件不存在时先核对，不虚构恢复。
- 使用 [ENV_LOCAL_SETUP](ENV_LOCAL_SETUP.md) 了解环境；只在需要时检查版本，不每轮重新安装工具链或运行所有测试。
- 读取适用的上层/目录指令；不因为本项目设计涉及 multi-agent 就自动启动协作子代理。
- 选择最早未完成且依赖已满足的任务；如果用户明确指定另一个已可执行任务，以用户为准。
- 在状态中将当前任务标为 in_progress，记录基线、准备修改的模块和本轮验收。

源码不存在时从 P0-01 开始。不要因为某个高级模块看起来更有趣而跳到 P2。

## 3. 每轮执行范围

一轮围绕一个可验收增量，可完成一个任务或其子任务。先明确结果，落地最小纵向链路，验证后再重构。允许任务合理连续推进，但不能把全部路线视为一次会话的完成义务。

每轮都应让当前能力可解释、可运行或有清晰的暂不可运行原因。禁止只生成成堆空类/空接口再标框架完成。代码之外，报告、状态更新和必要文档同步属于本轮完成条件。

长任务中途若收到补充约束，保留原目标并调整当前切片；只在用户明确取消或替换目标时停止原任务。接近上下文边界时先写进度与下一步，不能依赖下一轮仍保有聊天上下文。

## 4. 技术决策基线

Python 3.12 系列负责控制面，Go 负责 runner 和 AST。单进程 Python、SQLite、本地 artifact、CLI、stdio JSON。按阶段创建 pyproject/uv.lock、go.mod/go.sum，只声明真实使用依赖。

P0 的 WorkflowPolicy 和 ModelRouter 是普通函数与数据配置：前者返回一个 GraphSpec，后者返回默认 ModelProfile。后续增加实现不会改变 Runtime 调用边界。不要先引入插件容器、工作流 DSL 解释器或独立策略服务。

全局配置显式列出 budget、deadline、并发、工具权限与模型 alias；密钥通过环境或本地控制台会话内存注入且不入库。模型不可用时 scripted provider 保持机制测试可运行，但不能静默替代真实模型运行。当前真实验证接线与仍未完成的修复能力以 STATUS_PROJECT 为准。

## 5. 强制不变量

用户新增编码约定（2026-09-26）：新增或修改的函数添加中英文对照功能说明；核心状态、权限、预算与恢复逻辑同步添加解释性注释。开始新的实现前保存已有修改为 Git 基线；每个可验证增量独立 commit，保留原有用户改动，不把密钥或运行副本提交进仓库。此为后续轮次持续适用的偏好。

1. 模型只提出计划、结构化结果和允许的 tool calls；runtime 校验并执行。
2. GraphSpec 是可校验数据；不执行模型返回的任意工作流代码。
3. 原代码仓库与 run 工作副本分离；一份工作区同时最多一个写者。
4. 每次修改生成可追溯 snapshot；旧 evidence 不支持新版本成功判定。
5. Runtime Gate、用户验收、隐藏评估测试不可被优化器削弱。
6. 工具 intent/result、前后哈希、图版本和消息 receipt 支持核对恢复；不承诺 exactly-once。
7. 并行 GoCheck/Review 使用相同快照；修复和模型升级成本累计。
8. 代码 AST 候选关系不当作精确调用图；经验反思不当作已验证策略。
9. 有界预算不足或信息缺失要明确处理，不能无限补证、重试或增殖节点。
10. 文档声明与实际实现状态一致，未测的效果必须标为未验证。

## 6. 实施与验收方法

P0-01 完成最小项目与可运行入口；P0-02～06 接起数据图、状态、Go 和 scripted loop。P1 按路线补写工具、CIE、memory/context、角色和适应图；P2 根据明确优化任务再启用经验/路由/策略实验。

测试关注真实行为：依赖不满足不调度、超时清理、部分补丁恢复、过期证据拒绝、图变更原子性、预算边界和独立验收。不要为了数量写与实现逐行对应的测试。

每个完成项附验证命令、退出结果和测试范围；只做文档更新时检查链接、任务依赖和术语，不伪称业务测试通过。需要 API key/真实模型预算才能完成的验证，明确列为未执行；其余独立工作继续。

P0 的边界恢复不能写成“完整多文件补丁恢复”；P1 的经验记录不能写成“自优化完成”；P2 的一次提升不能写成“所有任务都会提升”。

## 7. 任务状态与中断恢复协议

状态枚举：todo / in_progress / blocked / done / deferred。blocked 表示确有缺失输入或外部条件，说明具体阻塞；不是工作量大。deferred 表示路线后置，不计入当前阶段完成分母。

任务只有实现和验收都满足才 done。部分完成的任务保留 in_progress，列明已完成子项、当前失败、修改文件、下一可执行动作和必要命令。

下一轮不能直接根据报告重放上次 shell 命令：先确认文件、进程、锁和工具账本状态。上次处于写操作中断时先 reconciliation，不能重新应用 patch 猜测结果。

状态文件记录的是开发进展；SQLite/Event 是未来 runtime 的产品运行记录，二者不要混用。

## 8. 每轮必须生成用户可读 Markdown

不论实现、设计、审查、故障修复或只完成一部分，只要本轮执行了项目任务，在结束前都要：

1. 新建 `docs/progress/PROGRESS_YYYY-MM-DD_NNN_short-topic.md`，使用 [报告模板](templates/TEMPLATE_PROGRESS.md)。日期按用户时区，NNN 取当日已有最大序号加一，不能覆盖旧报告。
2. 用中文直说本轮解决了什么、为什么重要、文件改动、如何验证、未完成/风险和下一步。先给用户能理解的结果，再给必要技术证据。
3. 更新 STATUS_PROJECT：本轮任务状态、最新报告链接、下一任务与接续指令。报告中的相对链接从 progress 目录解析。
4. 若更改架构或范围，同步相关 DESIGN/PLAN 并记录决定；普通内部重构无需反复修改全部文档。
5. 最终回复链接本轮报告，并指出完成与未完成的界限。

日常报告建议 300～800 中文字，按复杂度调整。命令只列有用的验证，不粘贴几百行日志，不记录密钥。不因未完整完成某个任务而省略报告。

普通闲聊或纯问答不强制创建报告；用户要求不写文件时遵从最新指令。若工具故障导致无法落盘，在最终回复给出报告正文并说明状态未保存，不能声称文件已生成。

## 9. 范围变更与有限自主性

已授权的正常实现、读操作、可逆修复和测试继续执行，无需逐步询问。遇到原设计的具体缺陷，可以在本轮范围内修正并报告理由；影响用户目标、明显扩大 P2/P3 或需要新外部账户时再询问关键缺失信息。

原详细设计第 13 节保留历史拆分。现在唯一执行顺序来自 PLAN_PRIORITY_ROADMAP；不要把历史依赖 H03/C02 当成 P1 的硬性阻塞，因为 delta 与模型摘要已后置。

## 10. 下一轮最小启动方式

用户说“开始”后：检查当前状态 → 领取 P0-01 → 建立最小 Python/Go 工程与测试入口 → 验证入口可启动 → 写进展报告并更新状态。不要同轮擅自实现所有 agent、下载多个模型 SDK 或部署服务。

如果用户继续评审架构，继续只修改对应文档并写报告；不会由于本文存在就自动启动编码。
