## 预期演示

输入 Go Todo 的修复需求 → Planner 定位契约与相关文件 → Developer 提交受控补丁 → Tester 整理验证需求、运行 GoCheck → Reviewer 独立审查 diff 与同一快照 → Gate 汇聚证据。失败时先清楚解释原因，再增加最多一次修复回合。

先串行运行，保留可并行的图依赖；不同时引入多模型、向量库、消息中间件或服务拆分。

## Python 边界与应修改的位置

| 模块 | 保留职责 | 下一步改动 |
|---|---|---|
| domain / workflow | 数据契约、图模板与校验 | 给节点增加向后兼容的角色身份；角色不等于 Go operation；Web 不自行拼角色图 |
| agent | 共用执行循环、预算、事件 | 根据角色校验输出和交接；验证角色 final 仍要求工具证据，不能机械套用到 Planner |
| adapters/chat | HTTP 与提供商响应解码 | 将当前固定验证提示和 schema 变为显式角色协议；调整 policy_version，不能静默恢复成不同协议 |
| context / memory | 角色材料、来源、失效 | 每次交接按接收角色重建上下文；不传整段聊天；补丁后旧快照失效 |
| patching / tools | 唯一写入及工具边界 | Developer 只提案；运行时校验哈希、提交新快照；复用已有恢复逻辑 |
| runtime / SQLite | 调度与持久化事实 | 图内写入阶段和交接 receipt 事务；Reviewer 与 GoCheck 的证据必须绑定同一快照 |
| web / React | 用例入口与事实展示 | 展示角色、交接、补丁及图版本；不在 UI 推断任务成功 |

不提前拆出空的 manager/service/repository 层。只有当“输出协议”“交接事务”等职责真正落地时，才增加小模块。现有 Store 保持一个 SQLite 适配器，暂不做全仓库数据库接口重构。
