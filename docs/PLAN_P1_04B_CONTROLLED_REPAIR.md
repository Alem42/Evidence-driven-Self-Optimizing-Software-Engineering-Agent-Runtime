## 交付目标与顺序

| 增量 | 预计更新 | 必须验收 |
|---|---|---|
| 04b-1 语义契约 | Planner 的 plan、Developer 的 patch proposal、Reviewer 的 review verdict 分开校验；保留 run/role/snapshot envelope | 缺验收项、未知文件、缺证据与错角色输出被拒绝；旧验证图仍可运行 |

| 04b-3 新快照验证 | 补丁后更新权威 run data、索引与上下文，再执行 Tester/Reviewer，Gate 汇聚两者 | 新快照不能接受旧工具证据；Reviewer 拒绝时即使测试通过也不能成功 |

先用确定性提案验证机制，真实 DeepSeek 角色提示/schema 接线单独验收。不给模型任意文件编辑或 shell 权限，不在同一增量引入多轮自修复、多模型路由或并行写入。

## 本次发现的关键设计问题

1. **Patches 当前只允许验证前写入。** 四角色图已有 Planner/Developer attempt，不能直接删掉原守卫。应将写权限绑定显式阶段、节点、当前快照与单写者，而不是放宽成“任何 agent 可写”。
2. **Runtime 当前在执行开始缓存 data。** 补丁发布后必须重新读取 snapshot/manifest/index；否则后续角色会使用旧版本。上下文、memory 失效检查也必须随之执行。
3. **旧规划与新验收属于不同版本。** 当前 Gate 要求所有只读结果匹配当前快照。修复后 Planner 的旧结果应保留为历史规划来源，不能重新标成新快照事实；需要区分规划输入版本、补丁前后版本和验收版本，明确各类证据的 Gate 规则。
4. **当前 reviewer ready 不是审查通过。** 新 review verdict 必须有显式 accept/reject、风险和来源；不得把通用 ready 直接等同于可发布。
5. **恢复绑定协议版本。** 新角色语义与 provider 提示必须有版本标识；旧图不能在重启时静默升级成新行为。
