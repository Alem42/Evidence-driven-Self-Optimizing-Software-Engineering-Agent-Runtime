# M2：流式传输、动态角色与真实评测——做了什么、测出什么

2026-10-07。本文是**写给你自己改简历/面试稿用的素材**（简历文档本身没有改动）。所有数字都标明来源；“没有收益”也是结论。

## 1. 简短版（约 150 字）

给多模型 Go 项目生成运行时做了“角色即数据”的 RoleSpec 注册表（角色用 JSON+Markdown 定义，新增角色不改 Python，加载时校验，黄金样本证明迁移前后提示词与 schema 逐字节一致），并在其上实现了混合式指挥者（规则优先、模型只在补丁停滞时从已注册候选里选一个、非法提议回退并留痕）和 AFlow-lite 工作流调优器（搜索空间只是数据）。用真实 API（Pro 决策 + Flash 生成，总花费 ¥8）做了 25 次 A/B 运行：**指挥者未见通过率收益（关 10/11，开 10/14）且每任务多花 24%–96%，因此保持默认关闭**；评测顺带发现并修复了流式响应上限按 SSE 原始字节计算导致长回答被拒的真实缺陷。

## 2. 详细版（面试讲述用）

**背景。** 运行时已经有事件溯源账本、独立 Gate、路由梯子与预算、声明式修复工作流。想让“角色与流程”动态，同时不破坏可验证/可恢复/成本可控。我给自己立了四条原则：动态的是选择和数据而不是代码；每个动态决策都是账本事件；规则优先、LLM 只处理歧义；**用评测决定是否启用**。

**做了什么**
1. **RoleSpec 注册表（P1）**：以前加一个角色要改提示词 if 链、schema、校验器、路由角色表、配置白名单、前端标签共 7–8 处；现在一个 JSON（+可选 Markdown 提示词），其余都从注册表读。迁移前抓取黄金样本，迁移后逐字节比对提示词与 schema（含属性顺序，约束解码依赖顺序）；旧测试一条断言不改即全绿。
2. **混合式指挥者（P2）**：`llm_choice` 图节点；简报由代码从账本截取（不含源码和日志）；提议经校验（必须是当前候选），不合法/崩溃/超时/超预算都拒绝并写 `conductor_rejected`，回到确定性规则；另有只读的测试怀疑者和代码审阅者两个数据角色。默认关闭。
3. **工作流调优器（P3）**：搜索空间是路由策略和可选的图边（数据）；补丁至多 3 条操作，应用后须同时通过策略校验与图校验；逐代淘汰、`min_gain` 防噪声、token/分钟/候选数三重预算。**只有离线测试，没有跑过真实调优。**
4. **部署与护栏**：Docker 镜像（同源、演示只读、Host/Origin 白名单、Linux runner 隔离）；启动时检测显卡/内存，不足则禁用本地模型。
5. **评测基础设施**：评测运行器支持费用上限、覆盖配置、保留账本；`scripts/p2_eval.py` 做 A/B；`scripts/loop_equivalence.py` 做“默认流程没变”的差分检查。

**真实评测（P2 的 A/B）**
- 方法：模型分工 Pro（规划/测试/诊断/指挥者…）+ Flash（生成/修复）；题库 L2–L5 随机抽题；同一任务关/开各一次、交替先后；独立判官复核；费用硬上限。
- 数据（25 次有效运行，总花费 ¥8.02）：

| 组 | 运行 | 通过 | 每次费用 | 每次云端 token |
|---|---|---|---|---|
| 关（规则） | 11 | 10 | ¥0.235 | 25.3k |
| 开 v1（首轮就问，含 halt） | 7 | 5 | ¥0.292 | 29.7k |
| 开 v2（去掉 halt） | 4 | 3 | ¥0.460 | 52.0k |
| 开 v3（仅停滞时问） | 3 | 2 | ¥0.432 | 42.1k |

  指挥者真正被调用的 7 次运行里 3 次通过，同样任务“关”组 6/7 通过。**结论：没有证据表明收益，且更贵；样本很小，不能断言有害。**
- 评测中修掉的真实问题：(a) 流式响应上限按原始 SSE 字节计（每 token 约 250 字节外壳），约 4000 token 的正常回答就被拒，首轮 7 次里 2 次中招；(b) 指挥者 reason 超 200 字整条提议被拒；(c) 指挥者能选 `halt` 把任务自己终止（已移除）；(d) 首轮“归属不明”几乎每个任务都触发，选的和规则一样白花钱（改为仅停滞触发）。
- 成本结构（来自“关”组 8 次运行的账本，价格为保守估算）：Pro 占 ¥1.74、Flash 占 ¥0.21——**成本主要在 Pro**，其中 `project_tester`、`project_developer`（升级到 Pro 的生成）、`project_test_revision` 最高。这是后续优化的数据线索（见 §4），**未验证**。

**可以怎么讲“为什么没做成”**：这不是失败而是方法论：先设评测门槛，再做对照；对照发现机制不赚钱就保持关闭，而且评测本身挖出了与该功能无关的真实缺陷。这比“加了个 agent 就说有提升”更可信。

## 3. 默认流程没有变（可验证）

- 指挥者策略关闭时，修复子图里指向 `conduct` 的边永远不触发，默认策略里的“直接用最高等级”名单与动态角色改动之前逐项相同（可选角色只在 `conductor` 打开时才加入）。
- 差分检查 `scripts/loop_equivalence.py`：同一批 6 个脚本化场景（双缺陷、只剩断言、无改动升级、规格判停、本地修不好升级、全员无改动停止）分别在改动前的提交 `ceda2ae` 和当前代码上运行，**完整事件序列（约 520 条）与模型调用序列逐项相同**；唯一差异是策略里多了三个默认关闭的键。

## 4. RoleSpec 之后还能保留/做什么（诚实版）

- **肯定保留、且确实有正面效果的（工程性的，不是通过率）**：RoleSpec 注册表（改一个角色的成本从 7–8 处降到 1 个文件，加载时校验，有黄金样本证明无行为变化）；流式上限缺陷修复（直接提高云端长回答的成功率）；评测的费用上限与按次费用记录；差分等价检查；本地模型护栏与 Docker 部署。
- **没有证据、不要宣称提升通过率的**：指挥者、测试怀疑者、代码审阅者（保留为实验选项）；调优器（只有离线测试）。
- **最可能带来真实正面效果的下一步（假设，需实测）**：用调优器/RoleSpec 的 `level` 做**降本**而不是提通过率——例如让 Planner 或部分生成在 Flash 上跑，只让测试作者和诊断者用 Pro（现在 Pro 占费用约 89%）。验证方式：同一批任务、同样的 A/B 方法，看通过率不降而费用下降。

## 6. 收尾验证（2026-10-07，新的 ¥10 预算里花了 ¥1.83）

- **默认流程**（指挥者关闭）：从题库 L1–L5 随机抽 5 题（seed 11）各跑一次：roman、knap、fizz 通过；lcs 在**生成阶段**被确定性的“main.go 只能做薄包装”检查连续拒绝（9 次调用，¥0.42）；wc 修复 4 轮后仍未通过（Diagnoser 在“测试错 / 实现错”之间摇摆，这是 wc 一贯的不稳定，之前 3/4）。**3/5 通过，¥1.15。** 与之前“关”组 10/11 相比偏低，但这两个失败都是默认流程里**早就存在**的模型波动（本次没有任何指挥者相关代码在这条路径上运行），差分检查已证明代码路径没变——所以我不把它当作回归，也不夸大“恢复正常”：这就是默认流程的真实水平，每个任务只跑 1 次，噪声很大。
- **设置页开关 → 实际流程**这条路：把指挥者写进（副本的）路由设置而不用覆盖项，跑 wc 一次：指挥者决策 1 次、审阅 1 次，通过，¥0.68（同一任务关闭时 ¥0.16–0.46）。说明开关能真正生效，也再次看到开启更贵。
- 单元测试：后端 475 通过、前端 40 通过（4 个 ERROR 是改动之前就存在的，被导入的 `test_*` 函数被 pytest 当成用例收集）。
