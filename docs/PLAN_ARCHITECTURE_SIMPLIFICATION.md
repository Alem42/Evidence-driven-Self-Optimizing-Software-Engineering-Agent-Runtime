# 架构减法建议（供审核，非全面重构已完成）

2026-10-02。

## 结论

当前问题不是目录数量本身，而是同时保留了多套“流程状态”和早期演示路线。继续添加Reviewer、图、报告入口，会增加理解成本。建议先收敛为一套项目流程，保留简单角色服务和真实验证内核；高级功能作为可选评测入口。

## 你看到的检查依赖图

ProjectDetails.jsx 原来把 detail.run.data.graph 画在版本日志里。来源是 engine.py 的 compile_project_checks：Tester 在 go_test、go_vet、go_fmt_check 中选检查，Runtime 生成这些工具节点，再加唯一 Gate。所有检查直接指向 Gate。

所以你的观察正确：它没有复杂动态结构。默认三项检查时一直是三个节点加Gate，只更新执行状态。选择只测试或测试+vet时节点数会变；没有角色自发增加节点、依赖重排或失败分支画进此图。它的后端意义是验证账本和依赖调度，前端意义只是开发者诊断，不能当项目能力卖点。

本轮已把它折叠为技术详情，并只在验证记录展示。后端Graph仍保留，因为Runtime调度、Gate覆盖与历史证据依赖它。未来集成检查有真实前后依赖时再考虑展示，不为图好看增加依赖。

## 主要冗余和问题

| 现状 | 为什么不清晰 | 建议 |
|---|---|---|
| 项目角色图与检查图并列 | 两个不同粒度都叫workflow | 主界面只角色阶段，工具结果用列表，检查图仅技术详情 |
| Coordinator、RoleRuntime、工具Runtime各有状态 | 一个阶段已结束，另一状态可能还在运行 | 定义阶段状态映射表，项目阶段作为UI主状态；调用/工具保留底层事实 |
| 规划、草稿、验证、评审都用Run | 评审Run不是验证Run，容易误用恢复入口 | 显式run_kind与入口校验，先小改，不迁移全部数据库 |
| role_calls旧表与role_invocations新表 | 旧表仅兼容，重复迁移逻辑长期保留 | 明确schema版本，一次迁移；稳定后停止每次初始化迁移，历史仍可读 |
| readonly collaboration demo与真实项目角色 | 相似名字但演示不生成真实项目 | CLI标记legacy/demo；未来取消默认入口，确认无使用后删演示服务与专属测试 |
| 单文件路线和多文件路线 | 相同职责重复 | 多文件优先；单文件后续作为单文件ProjectSpec，而不是另一套服务 |
| rules / AST / semantic三种审查 | 容易误解为三个完整Reviewer | 一个审查面板按来源展示；语义可选收费，AST可选只读，结果不能互相代替 |
| 多个评测脚本和原始日志 | 不利于普通使用 | 放开发者评测入口，避免把mutation等加进主流程默认步骤 |
| docs进展不断追加到状态页 | 旧限制和新实现混杂 | STATUS当前事实、PLAN下一步、CURRENT接续；progress保留历史，不重复当权威 |
| 未跟踪domain.py/runtime.py/workflow.py与同名包 | 早期代码副本，与现目录重复且容易误读 | 当前Python使用同名包；先确认来源再删除，不纳入新版本，不把它们当实现入口 |

源码定位：application/coordinator.py串联自动循环；application/planning.py/generation.py提供业务服务；runtime/roles.py模型调用持久化；runtime/engine.py工具图和Gate；application/projects.py从事件生成角色展示。后者只是投影，不能证明已有任意动态图调度。

## 建议保留的最小骨架

```text
UI：一个项目流程 + 当前动作 + 结果/代码 + 日志
Console：接口与worker入口
Coordinator：阶段推进、等待、恢复、修复策略
Project services：规划 / 生成 / 审查
Execution：持久模型调用 + 受控工具检查 + Gate
Store：运行 / 调用 / artifact / 事件
Go：源码事实 + 工具进程
```

现有domain/application/runtime/infrastructure/interfaces分层可以保留，不再进行大规模搬目录。领域校验模块数量不代表过度设计，但明显重复的职责要合并。memory/context/index保留实际修复检索使用部分；跨任务经验、自动模型路由、自优化图等未形成闭环的目标降为后续实验，不继续增加抽象层。

## 稳定版的推进顺序

1. 收敛UI角色状态与恢复入口，测试真实用户从描述到代码再到运行的一条完整路径。把评测入口从主流程隔离。
2. run_kind和状态转换校验，确保失败、等待、取消、过期有确定结果；评审不会进入工具执行。
3. 时间seed条款与固定seed实现冲突修复，用新版本和实际CLI验证。这比增加新图更重要。
4. 语义评审接前端前，先把来源和建议误报讲清；保留可选，不自动放宽测试。
5. 再处理旧CLI演示、重复单文件服务、旧表迁移；逐个删除，有使用证据和回归保障。
6. 稳定后才扩上下文收益、中型仓库；任意动态图和多角色并发延后。

## 本轮实施范围
