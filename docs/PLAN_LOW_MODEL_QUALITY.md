## 1. 现在的工作流是什么

```
需求 ─► Triage(本地,只告警) ─► Planner(规格/澄清, 最高等级) ─► Tester(测试方案, 最高等级) ─► 自动批准
      ─► 测试文件先由 Tester 等级写(定义公共 API) ─► 实现由本地模型对着冻结的测试逐文件生成
      ─► 每个文件: 确定性 import 修复 → gofmt → gofmt -e 语法门(失败就地带行列号重写)
      ─► 冻结测试 + Go 验证(build/vet/test/gofmt)
      ─► 失败 ─► fix-v1 子图: 归属分析 ─► (需要时 Diagnoser, 最高等级) ─► 修实现 / 改测试 / 仲裁 ─► 新版本 ─► 再验证
         · 证据带出错行源码片段 · 带“前几轮试过什么”的账本摘要 · 修复轮数随进展延长 · 最强模型不改实现 ⇒ 转去修订测试
      每个“模型调用”经 Router：规格/测试/测试修订/诊断 最高等级；实现/修复 从本地起步逐级上推；任务级预算；切换即释放本地模型
```

“高等级出 plan 和 test、低等级写代码、再一步步推到高等级”：默认 `prefer_highest_roles = [planner, tester, test_revision, diagnoser]` 即是这个意思。规格与测试决定下游一切、token 又少，所以放最高等级；实现和修复从最低等级起步，失败逐级上推。可在“路由与预算”里改。

## 2. 为什么“文本统计 CLI”没有自我修复（证据在账本里）

分三层，逐层查出来：

1. **第一层（你那次失败）**：冻结的**测试文件**自始至终有语法错误 `stats_test.go:51:238: string literal not terminated`。那一行是 `t.Fatalf("… % previous_attempt_error: The file … could not be processed …`——弱模型把提示词里的反馈文本抄进了字符串。每轮“修复实现”都在真实推进实现（错误 7→3→1→1），但**修复实现被禁止改冻结的测试**，4 轮额度被占满，测试始终没轮到。
2. **第二层（继续查）**：`*_test.go` 其实一直是**本地 Developer 在实现之后写的**（Tester 只出检查方案），规格里又没有函数签名，所以测试和实现各自发明 API（`Count` 既当类型又当函数，强模型修 3 轮也没消掉）。
3. **第三层（最后一次真实运行）**：测试先行后强模型写的测试质量不错，但**期望值手算错了**（`"hello world\nfoo bar\n"` 实为 20 字节，测试写 19），强模型三次“不改实现”后工作流停下；Diagnoser 还被测试带偏判成“实现问题”。

结论：不是 runner，也不是 plan；是**测试/实现的契约没有人钉死**，加上 agent loop 缺少“生成后立刻确定性自检”“期望值复核”“该改测试时改测试”。

## 3. 运行报错是否返回给了模型（现状）

是。修复调用收到：
- `failure_evidence[*].diagnostics`：每个检查最多 24 条关键行；**新增 `snippets`**：每条 `文件:行` 诊断附出错行前后各 4 行带行号的源码，出错行标 `>>`（最多 8 段）。
- 截断后的 stdout/stderr（stdout 超过 8000 字符保留头 3000/尾 5000）。
- 归属分析给的“只关注你这一侧”的提示；Diagnoser 的诊断与指示；用户反馈。
- **新增“前几轮摘要”**：每一轮改了哪些文件、由谁改、未解决条目 N→M、还剩什么。事实取自账本而不是模型自述。

仍然没有的：被禁止改的一侧的错误对它没用（已用归属提示缓解）；跨任务的经验（见 §5 #7）。

## 4. 上下文与窗口现在如何管理

- **准入**：每次调用前估算输入 token（`domain/tokens.py`，用真实调用校准的下界估计）+ `min(max_output, 4096)` 与候选窗口比较；放不下的候选被路由跳过。
- **硬拦截**：本地模型（Ollama 会静默截断）在估算下界已超窗口时发送前直接拒绝。
- **裁剪**：修复调用按诊断里的文件 + AST 候选选源码，保留 `go.mod` 与全部测试，记录被省略的文件；没有定位证据则回退完整输入。
- **没有**：对话压缩、跨任务记忆、技能库。每个角色调用是无状态的“结构化输入 → 结构化输出”，利于恢复；弱模型每轮重犯同类错的问题由 §3 的“账本摘要”缓解。

## 5. 主流做法逐项展开（谁怎么做 · 为什么 · 我们取什么 · 状态）

### #1 确定性自检前移（机器能判的事，不问模型）

| 谁 | 他们怎么做 | 为什么这样做 |
|---|---|---|
| **SWE-agent**（Yang 等，2024，Princeton） | 编辑命令内置 linter：**引入语法错误的编辑被直接拒绝**，并把错误回给模型重写 | 语法错误是确定性的；让坏编辑进入后续步骤会污染整条轨迹，越晚发现越贵 |
| **Aider** | 每次编辑后自动跑 lint/测试，把输出回给模型（`--auto-lint`、`--auto-test`）；可对 lint 输出用工具自动修 | 同上；并把“格式、import”这类问题交给工具 |
| **goimports / gopls**（Go 官方工具链） | 自动补缺失 import、删没用 import | 这两类占了弱模型编译错误的大头，工具比模型可靠 |

**我们取**：① 每个 Go 文件写完立刻 `gofmt -e` 语法门，失败就地带 `文件:行:列` 让模型重写（≤2 次，本地免费），整包再兜底；② **确定性 import 修复**（`goimports.py`）：补缺失的标准库 import、删没用的，保守（同名局部变量不加、别名/点/非标准库不动、`rand` 有歧义不加），之后编译仍独立验证；真实任务里 `undefined: io/bytes`、`"bufio" imported and not used` 约占一半。
**我们不取**：把整个 lint 套件塞进生成阶段——Go 没有现成的“只类型检查不构建”入口，包级编译前移会再启动一次 runner，收益有限，**暂缓**（见 §7 #1b）。
**状态**：语法门 ✅、import 修复 ✅（均有测试；真实运行验证见进展013）。

### #2 失败反馈的格式：给“出错位置附近的源码”，不是长日志

| 谁 | 他们怎么做 | 为什么 |
|---|---|---|
| **SWE-agent** | “Agent-Computer Interface”：文件查看器每次只显示一个窗口（约 100 行）、命令输出简短、错误信息精简 | 论文的核心论点之一：**给语言模型设计的接口**比给人设计的接口效果好；长输出会淹没信号 |
| **Aider** | 用 tree-sitter 生成 repo map，只给相关符号与签名，按 token 预算裁剪 | 上下文有限；定位比全量更重要 |
| **Liu 等，2023（Lost in the Middle）** | 长上下文里处于中间的信息利用率明显更低 | 说明“把长日志整段扔进去”对弱模型尤其不划算 |

**我们取**：`failure_evidence.snippets`（`snippets.py`）：每条诊断带 ±4 行带行号源码，出错行 `>>`；路径只在能唯一匹配到一个文件时才用（两个文件同名就不猜）；Windows 反斜杠路径、`go test` 只给文件名的情况都处理；提示词要求“就在那里改”。
**状态**：✅。

### #3 尝试历史：别让弱模型在两个错误之间来回翻转

| 谁 | 他们怎么做 | 为什么 |
|---|---|---|
| **Reflexion**（Shinn 等，2023） | 每次失败后让模型写一段语言反思，放进“情景记忆”，下一次尝试带上 | 不更新权重也能“从失败中学习”；同一任务内的重复犯错明显减少 |
| **Self-Debug**（Chen 等，2023） | 把执行反馈（以及对代码的逐行解释）喂回模型，多轮调试 | 执行反馈比模型自评可靠 |
| **SWE-agent** | “history processors”：压缩旧观察，只保留近期完整、旧的折叠 | 轨迹会变长，必须有取舍 |

**我们取**：`attempts.py`：每轮记录 `改了哪些文件 / 谁改的 / 未解决 N→M / 还剩什么`，下一轮提示里列最近 4 轮，并写明“不要重复没用的做法”。**与 Reflexion 的区别**：反思的内容是**账本事实**而不是模型自述，所以弱模型不会“反思错”。
**状态**：✅。

### #4 测试先行 + 测试锁定 + 测试自检

| 谁 | 他们怎么做 | 为什么 |
|---|---|---|
| **AlphaCodium**（Ridnik 等，2024） | “flow engineering”：先理解题目与生成测试，再迭代“生成代码→跑测试→修”，用结构化（YAML）输出，并把已通过的测试当“锚点”不允许回退 | 测试既是规格也是反馈；论文报告在 CodeContests 上对 GPT-4 有大幅提升 |
| **TiCoder**（Fakhoury 等，2023） | 把测试当作用户意图的形式化，用测试来澄清需求再生成代码 | 测试是消除歧义最便宜的办法 |
| **Aider architect 模式** | 强模型出方案，弱模型（editor）落地编辑 | 把贵的推理放在“少而关键”的一步，正是我们“强模型写规格与测试、弱模型写实现”的结构 |

**我们取**：本地起步时 **Tester 等级（最高）先写测试并定义公共 API**，本地模型对着冻结的测试写实现（提示词：测试冻结、按其用到的标识符与签名实现、不要同名类型和函数）。
**我们不取（暂）**：AlphaCodium 的“AI 生成额外测试 + 锚点”——需要多轮与并行验证，放 M2。
**状态**：测试先行 ✅。**冻结前检查**做了能干净做的一半：`testlint.py` 静态检查测试文件——必须有 Test 函数、必须有失败断言（`t.Errorf/Fatal…` 或 assert 库）、不能 `t.Skip`，不满足就带原因就地重写（和语法门同一条路）；注释和字符串里的假断言不算。**真正的“红灯”**（测试在空实现上必须失败）需要存根实现或变异（把实现改坏看测试是否变红），放到 M3 的变异门，这里不假装做到。

### #5 小步 + 可编译骨架

| 谁 | 他们怎么做 | 为什么 |
|---|---|---|
| **Agentless**（Xia 等，2024） | 分层定位：文件 → 类/函数 → 行，再针对性地生成补丁，不做自由的 agent 循环 | 把大问题拆成小而确定的步骤，**比复杂 agent 更省钱且不差** |
| 仓库级生成的一般做法 | 先骨架（类型/签名），再逐函数填充，每步编译 | 弱模型一次写 200 行的出错率远高于写 30 行 |

**我们**：现在是逐文件；逐函数需要 runner 的并发与编译循环，**放 M2**。

### #6 多样本 + 选择（用算力换质量）

| 谁 | 他们怎么做 | 为什么 |
|---|---|---|
| **AlphaCode**（Li 等，2022） | 大量采样，用样例测试过滤，再聚类选代表 | 弱的单次生成 + 强的验证 = 可靠结果 |
| **CodeT**（Chen 等，2022） | 让模型同时生成代码与测试，用“代码-测试双向一致”给候选排序 | 没有真值时，用一致性当信号 |
| **Agentless** | 生成多个补丁，用复现测试与回归测试筛选，多数投票 | 同上 |

**我们**：本地模型免费，这是最适合我们的“换算力”办法；需要 runner 并发与隔离副本，**M2 核心任务之一**。

### #7 经验库 / 技能（跨任务学习，不训练模型）

| 谁 | 他们怎么做 | 为什么 |
|---|---|---|
| **Voyager**（Wang 等，2023） | 把验证过的可执行代码存进技能库，按描述检索复用，失败时带环境反馈迭代 | 能力积累在库里，而不是模型里；**只存验证通过的**，避免污染 |
| **Claude Code / Cursor 等** | 项目规则文件（CLAUDE.md、rules）与按需加载的技能 | 把“这个项目的坑”变成短规则，按相关性注入 |

**我们取**：“经验卡”= 失败签名 + 根因 + 一句规则，**只在修复后 Gate 通过时由 Diagnoser 产出**，人审后入库，按角色/语言检索 ≤5 条注入。例：“字符串里不要出现提示词字段名”“只用标准库时不要留未使用的 import”。**先只记录不注入**，攒一批后用评测集验证有没有帮助再注入。
**状态**：未做（设计在上）。

### #8 上下文压缩
本项目调用是无状态的；需要的是 #3 的“尝试摘要”，不是通用对话压缩。**不做**。

### #9 约束解码 / 结构化输出

| 谁 | 他们怎么做 | 为什么 |
|---|---|---|
| **Ollama structured outputs / llama.cpp GBNF / Outlines** | 用 JSON schema 或文法在解码时限制输出 | 弱模型最常见的失败是 JSON 不合法 |
| **Tam 等，2024（Let Me Speak Freely?）** | 研究发现**过严的格式约束可能降低推理类任务的表现** | 提醒：约束要“够用就好”，让模型先自由推理再输出 |

**更正（我之前写错了）**：**这一项早已实现**——本地 Ollama 请求对每个角色都带 JSON schema（`agents/schemas.py` 的 `response_schema` → 请求体 `format`）：规划、测试方案、逐文件生成（路径被约束为唯一键）、修复（路径限制为允许修改的文件类别）、诊断、预检均有。云端 DeepSeek 只支持 `json_object`，无 schema。
**这次真正做的**：把“云端返回截断 JSON”按“已收到”处理，使其重试/升级而不是中止（进展011）。
**待评估**：Diagnoser 的 schema 目前把 `rationale` 限制为 2000 字符且是一次输出；按 Tam 等的提醒，可考虑“先自由文本分析、再结构化输出”的两段式，对比准确率（需要 §6 的评测集）。

### #11（新）规格里钉死边界语义 + 实现提示

| 谁 | 他们怎么做 | 为什么 |
|---|---|---|
| **规格驱动开发**（如 GitHub spec-kit、AWS Kiro 的 requirements → design → tasks） | 先产出可审阅的需求与设计，再生成任务与代码 | 把歧义消灭在最便宜的阶段 |
| **Aider architect** | 强模型先写“怎么做”，弱模型照做 | 强模型用很少 token 给出方向，比让弱模型反复试错省 |

**我们的动机来自真实失败**：“文本统计”最后卡在“无结尾换行时字节数怎么算”——规格没说，实现和测试各执一词。
**方案**：Planner 的 `acceptance` 必须覆盖边界（空输入、无结尾换行、超长行、非法输入），并附 2–3 句**实现提示**（如“字节数用 io.Copy 到计数器直接统计，不要逐行”）；Developer 提示词引用它。**状态**：✅ 已实现（Planner 提示词：验收项必须钉死边界语义并给 2–3 条实现提示）。

### #12（新）期望值复核（对付“测试里手算错”）

| 谁 | 做法 |
|---|---|
| **CodeT** | 用“两个独立来源的一致性”当信号 |
| **AlphaCodium** | 额外生成测试并交叉验证 |

**动机**：本次真实失败里，强模型写的测试有两处期望值算错（20 写成 19、9 写成 8）。
**第二个证据（CSV 任务）**：测试期望把“按金额降序”写成了升序（`clothing: -0.50` 在 `food: 1.00` 前），实现是对的；Diagnoser 看了测试后编出“同额按类别升序”的理由，判成“实现有问题”，流程把轮数全花在修正确的实现上。**所以仅靠“强模型重算期望”不够，诊断本身也要防被测试带偏**：
- **盲测诊断**：Diagnoser 先**不看测试**，只根据需求与验收项为每个失败用例独立写出期望输出，再与测试里的期望比对；不一致 ⇒ 判 `test`，并把自己的推导作为 `test_instructions`。这与 CodeT 的“用独立来源的一致性当信号”同理，成本只是一次诊断调用。
**实现时的修正（重要）**：最初设想“盲测”——诊断时完全不让 Diagnoser 看测试。做不到：失败用例的**输入只存在于测试源码里**，不看测试就无法判断输出对不对。改为 **chain-of-verification 式**（Dhuliawala 等，2023：先独立回答验证问题，再与草稿比对）：
1. Diagnoser 的输出新增 `expectation_checks`：每个失败用例先写 `requirement_says`（只根据目标与验收项自己算出的正确输出），再写 `test_expects`，最后 `matches`；schema 的属性顺序即生成顺序，所以“先写需求怎么说”。
2. **确定性改判**（`reconcile_diagnosis`）：核对过的用例全部“不一致” ⇒ 判测试有问题；部分不一致且原判只是实现 ⇒ 两侧都有问题。结论必须服从它自己的核对，不能再编一个叙述把测试圆过去。
3. 只剩断言失败时**第一轮就诊断**（以前要等 2 轮失败后），错误的期望越早发现越省轮数。
4. 顺手修了一个 bug：断言条目里只有文件名（`cli_test.go`），而 bundle 里是完整路径，**测试源码一直没有送进 Diagnoser**。
**原设想（保留）**：Tester 写完测试后，**让强模型独立重算每个用例的期望值**（不同提示、不看原答案），不一致的用例标记并回到 Tester；成本极小（只有测试数据）。也可以让模型在测试里写出推导（如 `// "hello world\n" = 11+1 = 12`），审阅时可见。**状态**：Diagnoser 侧已做；“Tester 写完后独立重算”这一半未做。

### #13（新）补丁修不动时，整体重写实现
**状态：✅ 已实现。** 连续 2 轮没有改善（未解决条目数不降）且最强模型已试过 ⇒ 工作流走 `rewrite` 节点：最高等级丢弃现有结构，对着冻结的测试把实现重写一次（给全部实现文件而不是按诊断裁剪，并带“前几轮摘要”避免重复失败的做法）。每个任务最多一次；有改善的任务从不触发。

**动机**：弱模型选了易错的方案（逐行 `bufio.Scanner` 计数），之后每个补丁都在修补一个错误的结构；Agentless 的做法是“多次独立生成再验证”而不是无限补丁。
**方案**：同一类失败连续 N 轮没有改善且已用过最强模型时，**丢弃当前实现、由最强模型对着冻结的测试整体重写一次**（并带上 Diagnoser 对“方案为什么不对”的结论）。**状态**：未做。

### #14（新）反馈不要用像“字段”的写法给弱模型
**状态：✅ 已实现（确定性检查那一半）。** `leaks.py`：源码里出现我们自己的提示词字段名/固定句子（`previous_attempt_error`、`failure_evidence`、`previous_files`……）即判失败并带原因就地重写（生成、修复、测试修订三处都查）。这种泄漏在语法上是合法的 Go（在字符串里），所以语法门抓不到，必须独立检查。提示词里也加了“这些字段名是对你的指示，绝不能抄进源码”。
**动机**：`previous_attempt_error` 这个字段名被弱模型抄进了源码字符串。
**方案**：反馈用自然语言段落包裹并明说“以下仅供参考，不要出现在代码里”；并在语法门之外加一条确定性检查：生成的 Go 源码里出现我们自己的提示词字段名（`previous_attempt_error`、`failure_evidence` 等）就直接判定失败重写。**状态**：未做，很便宜。
