# 方案：让低质量模型完成高难度工作（上下文、反馈与自学习）

2026-10-04。前置：[进展011](progress/PROGRESS_2026-10-04_003_m1-diagnoser-declarative-fix-flow.md)。约束：没有比 DeepSeek v4-pro 更强的 API，只能在 runtime 里想办法。

## 1. 现在的工作流是什么

```
需求 ─► Triage(本地,只告警) ─► Planner(澄清/规格) ─► Tester(测试方案) ─► 人审/自动批准
      ─► Developer 逐文件生成(本地起步) ─► [新] 逐文件语法门 ─► gofmt ─► 冻结测试 + Go 验证(build/vet/test/gofmt)
      ─► 失败 ─► fix-v1 子图: 归属分析 ─► (必要时 Diagnoser) ─► 修实现 / 改测试 / 仲裁 ─► 新版本 ─► 再验证
      每个“模型调用”经 Router：本地优先、失败后按等级逐级上推、任务级预算、切换即释放本地模型
```

**本次调整（对应“高等级出 plan 和 test，低等级写代码，逐级上推”）**：默认 `prefer_highest_roles = [planner, tester, diagnoser]`。规格与测试决定下游一切（测试写坏，再多轮“修实现”都无效），而且 token 很少，所以走最高等级；Developer/Repair 仍从最低等级起步，失败逐级上推。可在“路由默认值”里改回。

## 2. 为什么“文本统计 CLI”没有自我修复（证据：任务链 862a3670…2ce25af4）

账本里那条链的事实：
1. **冻结的测试文件自始至终有语法错误**：`stats_test.go:51:238: string literal not terminated`。文件里那一行是 `t.Fatalf("… % previous_attempt_error: The file … could not be processed because it failed to compile …`——**弱模型把提示词里的 `previous_attempt_error` 反馈文本抄进了字符串**。
2. 之后每一轮“修复实现”都真实推进了实现（错误 7 条 → 3 → 1 → 1），但**测试文件的语法错误只有“修订测试”能改，修复实现被禁止碰冻结的测试**。我们按“实现优先”排序，4 轮自动修复额度全被实现占满，测试问题始终没轮到。
3. 没有任何阶段在**生成时**就发现测试文件根本不能解析：`_gofmt` 失败时静默保留原样，第一次发现是几分钟后的完整验证。

结论：**不是执行（runner）问题，也不是 plan 问题；是 test 在生成阶段被写坏，而 agent loop 缺少“生成后立刻确定性自检”和“两侧同时有阻塞时的调度”。** 低成本修在源头：

| 层 | 已做 | 说明 |
|---|---|---|
| 生成 | **逐文件语法门**（本次） | 每个 Go 文件写完立刻 `gofmt -e`，带行列号让模型就地重写（最多 2 次，本地免费）；整包再兜底，云端单次生成走阶段重试/升级 |
| 路由 | **Planner/Tester 用最高等级**（本次） | 弱模型写测试是这类失败的根源 |
| 修复 | 归属分析（上一步） | 两侧都阻塞时仍是先实现后测试，见 §5 待办 |

## 3. 运行报错是否返回给了模型

是，但有取舍：
- **返回的内容**：修复调用收到 `failure_evidence`（每个检查的 `diagnostics` 最多 24 条关键行 + 截断后的 stdout/stderr，stdout 超过 8000 字符保留头 3000/尾 5000）、归属分析给的“只关注你这一侧”的提示、用户反馈、全部相关源码。
- **没返回的内容**：① 之前几轮**试过什么、为什么没用**（每次修复都是“失败证据 + 当前文件”的新对话，没有尝试历史）；② 模型被禁止改的一侧的错误会作为证据出现，但它不能行动——这就是弱模型最容易乱改的场景；③ 编译器错误只给行列号，不给**出错行附近的源码片段**。

## 4. 上下文与窗口现在如何管理

- **准入**：每次调用前估算输入 token（`domain/tokens.py`，以真实调用校准的下界估计），加上 `min(max_output, 4096)` 与候选窗口比较；放不下的候选被路由跳过。
- **硬拦截**：本地模型（Ollama 会静默截断）在估算下界已超窗口时发送前直接拒绝，不会让模型“看着被截断的输入乱答”。
- **输入裁剪**：修复调用用 `intelligence.repair_context`：按诊断里提到的文件 + AST 候选选源码，保留 `go.mod` 与全部测试，记录被省略的文件清单；没有定位证据则回退完整输入。
- **没有**：对话压缩/摘要、跨任务记忆、技能库、尝试历史。每个角色调用都是无状态的“结构化输入 → 结构化输出”，这对可恢复性很好，但对弱模型意味着每轮都在重新犯同一类错。

## 5. 主流做法与建议（针对“弱模型 + 高难度任务”）

下面按**投入产出比**排序，标注是否适合本项目。

| # | 做法 | 主流依据 | 本项目建议 |
|---|---|---|---|
| 1 | **确定性自检前移**：生成后立刻跑解析器/编译器/linter，把报错喂回同一个模型（Aider 的 lint-then-fix、SWE-agent 的 ACI 检查、Claude Code 的诊断反馈） | 几乎所有编码 agent 的第一条经验：机器能判的事不要等到集成验证 | **已做语法门**；下一步：逐文件 `go vet`/`go build ./...`（用已有 runner），把“包能编译”也前移到生成阶段，错误行附近源码一并给出 |
| 2 | **失败反馈的格式**：给“出错行 ±N 行源码 + 编译器原文 + 期望”，而不是整段输出（SWE-agent 的 ACI） | 弱模型对长日志极不敏感 | 在 `concise_failure_evidence` 里为每条 `file:line:col` 附 ±5 行源码片段；这是最便宜的一项，建议下一步先做 |
| 3 | **尝试历史（scratchpad / reflexion）**：每轮把“试过什么、结果是什么”压成 2–3 行追加给下一轮（Reflexion、Voyager 的 critic 记忆） | 防止弱模型在两个错误之间来回翻转；成本几乎为零 | 失败链里已有每次修复的结果与签名，直接生成“前几轮摘要”放进修复上下文；与 fix-v1 的 `fix_log` 事件天然契合 |
| 4 | **测试先行 + 测试锁定 + 测试自检**：高等级写测试，低等级写实现；测试在冻结前必须“能编译、且在空实现上会失败”（TDD agents、AlphaCodium 的 test anchors） | AlphaCodium 证明：迭代“生成测试 → 通过测试”优于一次性生成 | 已有冻结测试；本次让最高等级写测试；下一步加“冻结前红灯检查”：用存根实现跑一次，测试必须编译通过且至少一个失败，否则退回 Tester |
| 5 | **小步 + 最小可运行骨架**：先生成能编译的骨架（类型/函数签名），再逐个函数填充，每步都编译 | “repo-level” 代码生成的主流分解；弱模型一次写 200 行出错率远高于写 30 行 | 现在是“逐文件”，可再细到“逐函数”；对 4B–35B 本地模型收益明显，但改动较大，放 M2 |
| 6 | **多样本 + 选择**（best-of-n / 自一致 / 以测试结果投票，AlphaCode、CodeT） | 弱模型最有效的“换算力换质量”办法，不需要更强的模型 | 本地模型免费，适合：失败时本地并行/串行生成 2–3 个候选，在隔离副本里都跑验证，取通过最多者；需要 runner 并发，放 M2 |
| 7 | **经验库 / 技能（Voyager 技能库、Claude Skills、Cursor rules）**：把“踩过的坑”存成短规则，按任务相关性检索注入 | 跨任务学习的主流低成本形态：**不训练模型，只积累提示** | 建议做“可审阅的经验卡”：失败签名 + 根因 + 一句规则（例如“字符串里不要出现提示词字段名”“只用标准库时不要引入未使用的 import”），由 Diagnoser 在**修复成功**后产出，人审后入库，按角色/语言检索 ≤5 条注入。关键是**只存验证过的**（修复后 Gate 通过）以免污染 |
| 8 | **上下文压缩**：长历史做滚动摘要，保留“不变量 + 未决问题 + 最近证据” | 长会话 agent 的标配 | 本项目调用是无状态的，需要的是第 3 项的“尝试摘要”，而不是对话压缩；不建议引入通用压缩 |
| 9 | **约束解码 / 结构化输出**（JSON schema / grammar，Ollama 支持 `format`） | 弱模型最常见的失败是 JSON 不合法（本次也遇到） | 本地模型用 Ollama 的 `format` 传 schema，几乎可以消灭“JSON invalid”；建议下一步做（改动小） |
| 10 | **自我修改提示（DSPy / 提示优化）、微调/LoRA** | 需要离线评测集与算力 | 现在不做；但应**先攒评测集**：每个真实任务的（需求、失败链、最终是否通过）已在账本里，可导出为回归基准 |

| 11 | **规格里钉死边界语义 + 实现提示**（来自 spec-driven / design-doc-first 做法） | 弱模型会选易错方案；强模型便宜地给出“怎么做”比反复修更省 | 本次真实运行的最后一个失败正是这个：建议 Planner 的 `acceptance` 必须覆盖边界（空输入、无结尾换行、超长行），并附 2–3 句“实现提示”；Developer 提示词引用它 |

**推荐顺序（只做 M1 范围）**：2（证据带源码片段）→ 3（尝试摘要）→ 9（本地约束解码）→ 4（冻结前红灯检查）→ 7（经验卡，先只存不注入，攒一批再评估）。1 的“包能编译”前移、5、6 属于 M2 的 runtime 能力。

## 6. 本次实现（含后续真实运行中追加的）

- `generation._syntax_errors`、`SYNTAX_RETRIES`：逐文件语法门（本地就地重写，整包兜底）。测试：`SyntaxGateTests`。
- 默认路由：Planner/Tester/Diagnoser 最高等级。测试：`test_by_default_spec_and_tests_use_the_strongest_level_while_code_starts_low`。
- 子进程不弹 cmd 窗口：见进展 012。
- **测试先行，由强模型写**：本地起步时 Tester 等级先写测试并定义公共 API，本地模型对着冻结的测试实现；`RoleRuntime.call(freeze_key=…)` 让不同职位各自冻结配置。
- **测试修订/仲裁用最高等级**：`project_test_revision` 在默认 `prefer_highest_roles` 中。
- **按进展延长修复轮数**：基础 4 轮，每次未解决条目数创新低多给 1 轮，最多再加 4 轮。
- **最强模型对实现连续无改动 ⇒ 转去修订测试一次**（`flip_to_tests`）。
