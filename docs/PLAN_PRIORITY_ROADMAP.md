# 长期路线：生成、审核并运行完整项目

2026-09-28 权威路线。历史 P1-04b 等已归档，不再阻塞可用产品闭环。

目标：Evidence-driven Software Engineering Agent Runtime。用户描述项目，在浏览器审核结构与代码，harness 创建版本、执行验证和程序、展示证据，通过反馈迭代。Self-Optimizing 是远期评估目标。

## 不可混淆的四个概念

| 概念 | 职责 | 不应承担 |
|---|---|---|
| 角色 | Planner 规划，Developer 提案修改，Tester 设计验证方案，Reviewer 审查 | 自行授予工具权限、自称测试已通过 |
| 检查节点 | 执行单元测试、vet、格式、未来集成测试等具体动作 | 被包装成独立的 Agent 角色 |
| Runtime | 校验计划与请求、路径、快照、预算和允许动作，调度并记录证据 | 无条件执行模型给出的 shell |
| Gate | 独立核对当前版本的真实结果、必需检查覆盖和明确的审核策略 | 仅凭 Agent 的 ready/passed 声明成功 |

当前新生成任务和重跑使用 tool 类型检查节点，完全复用 Runtime 执行与独立 Gate；旧 live 验证图保留兼容。完整角色语义计划尚未接入，先不为每个检查额外调用模型。

## 分阶段交付

| 阶段 | 优先级/状态 | 最小交付与验收 |
|---|---|---|
| A 工作台 | 必须，基础版完成 | 审核/结果/过程分区；同一已审核版本一键重验；新记录保留来源；真实日志可读 |
| B 项目规格与验证计划 | 必须，基础版完成 | Planner 结构化 ProjectSpec、Tester CheckPlan、Runtime 校验编译、前端编辑确认；暂未验收真实上游模型质量，不创建实现文件 |
| C 多文件生成 | 必须 | Developer 产生有界文件集合；逐文件人审；批准后原子发布完整版本；真实 test/vet/fmt；可导出项目文件夹 |
| D 运行程序 | 必须 | 固定入口 go run、结构化参数、输出/退出码/停止；首版短命 CLI，不托管 HTTP 服务 |
| E 反馈与审查 | 应做 | 失败证据与反馈生成新版本；Reviewer 有明确证据引用与 verdict；最多一轮受控修复，旧版本保留 |
| F 代码理解优化 | 应做 | 文件/符号级上下文、版本失效、角色定向交接；用定位率、上下文字节和开销衡量效果 |
| G 模板与依赖扩展 | 可选 | 明确批准的依赖安装、HTTP/Python 模板、模型路由；标准库闭环完成后再做 |
| H 经验与自优化 | 远期可选 | 检索经验、有限重规划、独立样本策略对比；证明改善才声称自优化 |

每阶段允许分几轮，每个验证通过的独立增量及时提交。角色按需串行，不强制每次启动四个 Agent。验收检查是实际工具执行；模型生成的测试不能冒充独立业务验收。

## 简单而可扩展的实现

React → Python Console → Runtime/提案服务 → Go Runner。继续使用 SQLite、本地 artifact 和版本目录，不增加微服务。

Python 负责模型、规格、提案、审批与编排；Go 负责索引和受控工具/进程，适合学习者逐步扩展。Runtime 保持唯一执行状态权威，沿用 run/snapshot/artifact/event。

ProjectSpec 描述目标、模板、入口和验收项；CheckPlan 描述允许操作及其验证目的；ProjectProposal 绑定规格/基线和文件集合。批准绑定提案摘要，任何文件变化需重新批准。多文件准备完成并校验后发布版本指针，不能简单放宽当前单文件 Patches 的限制。

首版标准库 Go CLI、少量文本文件，不自动安装架构依赖。未来依赖必须给出模块版本和清单，批准后执行可审计的固定操作。
