# MASA 项目说明：它要解决什么，以及怎样一步步完成

## 1. 可以用你提出的名字，但要区分目标与当前能力

**Evidence-driven Self-Optimizing Software Engineering Agent Runtime** 适合描述最终方向。中文可以理解为“由证据驱动、能改进执行策略的软件工程 Agent 运行平台”。平时继续叫 MASA，名称不会改变后续 Python 包和 Go 工具的边界。

目前 P0 运行框架已实现，能进行离线的真实 Go 检查、状态记录与恢复，尚无自动代码修复。操作见 [P0 使用说明](USER_P0_QUICKSTART.md)。做到 P1 核心 demo 后，适合称“Evidence-driven Adaptive Runtime”；完成经验提出策略、独立评估、采用新策略与回退后，才有依据称 self-optimizing。

这里的“优化自己”是改进工作方式，例如先查哪些代码、采用哪种流程、什么时候升级模型。它不会偷偷修改自己的源码，也不需要训练一个新的基础模型。

## 2. 这个项目真正的主线

让 AI 修一个小 bug 并不难展示；更有价值的是解释：它为什么修改这些文件，是否读过相关调用方，旧结论是否过期，各角色如何交接，测试失败后为什么换了执行路径。

MASA 的主线是：**读到可靠证据 → 给合适角色足够的信息 → 修改与验证 → 保存结果 → 用结果改善下一次策略。**

“证据”可以是当前版本的函数、调用线索、diff 或真实测试结果。模型说“我认为好了”只是意见，不能替代这些证据。

## 3. 用一个实际任务理解系统

假设一个 Go Todo 服务的分页参数 size=0 出错，而且另一个导出接口也会调用同一段逻辑。

| 步骤 | 系统做什么 | 你可以观察什么 |
|---|---|---|
| 了解代码 | Go 提取结构，Python 检索 handler/helper/export | 找到哪些文件、为什么相关、哪些关系还不确定 |
| 规划 | Planner 提出小范围计划，runtime 选择合法图 | 为什么先补证或直接开发 |
| 修改 | Developer 只在工作副本修改 | patch 和新代码版本 |
| 测试设计 | Tester 根据两个接口的规则补边界测试 | 验收项是否被覆盖 |
| 验证 | GoCheck 跑工具，Reviewer 独立审查 | 相同代码版本上的测试与审查结果 |
| 修复 | 当前证据失败就追加有限修复步骤 | 失败原因、图变化、剩余预算 |
| 记录 | 形成一次 Experience | 做过什么、哪里失败、花了多少成本 |
| 后续优化 | 比较“先查调用方”和“直接修改”等策略 | 是否真的少走弯路，而非仅靠模型自评 |

最终得到一份补丁和可追溯报告，而不是一段“任务已完成”的聊天回复。

## 4. 为什么还保留模板，却又支持动态工作流

框架从一开始执行“图数据”：哪些节点需要先完成，哪些可以并行，每个节点读写什么。最初只提供一张可靠模板，这是为了先验证执行器；以后 Planner 可以按规则选择图、插入补证、拆分未执行任务或追加修复。

允许动态调整，不等于允许删掉所有测试来省钱。已经执行的历史不能抹掉，用户要求不能被改写，正在运行的写操作也不能随意换目标。

这种受约束的自适应已经能展示架构能力。完全自由的图搜索需要更多数据、预算和故障处理，不适合当个人项目第一步。

## 5. 三种容易混淆的“记忆”

**当前工作记忆**：这个任务已经做了什么、还没验证什么。

**代码知识**：当前版本有哪些函数和依赖，哪些结论在代码修改后已经失效。

**经验**：以前遇到过哪类任务，采用什么流程，结果和成本如何。它能提示下一次先检查什么，却不能把旧代码位置直接当成现在的事实。

例如，经验告诉系统“改公共分页函数前，检查另一入口”是有用的；记住“第 24 行必须改成 1”通常不可靠。文档要求将这两者分开。

## 6. 多模型值得做，但不是越多越好

第一版只需要一个实际模型，加一个离线 scripted provider 来测试机制。以后再根据风险、跨文件复杂度、上下文需求和预算选模型。

弱模型便宜，但如果经常写错、重试、再升级，总费用可能更高。强模型也不必承包所有任务。格式化和测试直接运行 Go 工具，根本不需要模型。

因此 Model Router 先是可替换的选择函数，后续再通过同一组任务测量收益。缺少第二个模型账户不会阻塞核心项目。

## 7. 自优化怎样才算成立

至少能展示这一条链：系统记录过去结果 → 提出一个明确策略变化 → 用隔离任务对比旧策略 → 满足规则才采用新版本 → 遇到回归能退回。

如果只写了一句“下次应先跑测试”，这是经验总结。如果下一次真的按它执行，属于经验复用。如果还通过对照证明它在特定任务上更好，并管理策略版本和回退，才构成可信的自优化实验。

样本少时可以说“在这几个任务中观察到改善”，不需要包装成所有软件工程任务上的最优路径。

## 8. 怎么避免做成过大的个人项目

| 阶段 | 你最终拿到什么 | 必须完成吗 |
|---|---|---|
| P0 框架 | Python 调度图，调用 Go 工具，有状态和恢复 | 是，最优先 |
| P1 核心 demo | 代码理解、记忆失效、角色上下文、多 agent 修复和受约束重规划 | 是，项目主体 |
| P2 优化版 | 历史经验影响策略、可选模型路由、离线晋升与回退 | 希望达到，但不阻塞 P1 交付 |
| P3 扩展 | 完整类型图、向量检索、Web/IDE、分布式等 | 按需要选做 |

原来较重的增量消息、自动摘要、增量索引都后移。先做完整有界交接、结构化压缩、小仓库全量索引，仍能清晰证明核心机制。

## 9. Go 在项目里负责什么

Go 是一块可独立解释和测试的工具模块：执行命令、处理超时和取消、限制输出，以及解析 Go 源码的 AST。Python 管流程、LLM、记忆和检索。

你的学习路径是 JSON 与结构体 → 文件和进程 → context/错误处理 → 测试 → AST 遍历。暂时不需要同时掌握 Gin、gRPC、ORM 和分布式调度，也不会为了“Go 占比”把整套 runtime 重写。

## 10. 简历与面试可以展示什么

完成 P1 后，可以展示自研图执行内核、证据版本管理、上下文预算、多角色职责和真实 Go 工具链。完成 P2 后，再增加经验驱动策略对照、模型选择与回退。

最值得准备的演示是：一次错误修复如何改变流程，一条旧记忆为何失效，一个策略为什么被接受或拒绝。数据使用真实用例和日志，没实现的组件不写进完成描述。

## 11. 以后每轮怎样继续

你可以对下一轮 LLM 说：

> 阅读 docs/LLM_IMPLEMENTATION_GUIDE.md、docs/STATUS_PROJECT.md 和 docs/PLAN_PRIORITY_ROADMAP.md，从下一项开始实现。完成后更新状态并写一份 docs/progress 下的中文进展报告。

每份报告会告诉你：这轮完成了什么、怎么验证、还缺什么、下一步做什么。即使任务中断或没全部完成，也要如实留下接续信息。只要入口和状态文件被读取，就不需要依赖某一个聊天窗口一直保存上下文。

所有项目 Markdown 已集中在 docs，原始愿景在 archive。先看 [优先级表](../PLAN_PRIORITY_ROADMAP.md) 和 [当前状态](../STATUS_PROJECT.md)，需要深入时再看两份专项设计。
