# 使用 MASA 项目工作台

在仓库根目录启动：

```powershell
.\.venv\Scripts\python.exe -m masa ui --port 8765 --open
```

浏览器打开 `http://127.0.0.1:8765`。若重构前的服务仍在运行，先关闭旧服务再启动；前端改动后在 `frontend` 执行 `npm run build`，刷新页面。

1. 点击「API 管理」，添加提供商、Base URL、模型与密钥。启用本地保存后重启可复用；输出 token 应足够容纳整套代码。
2. 点击「新建项目」，选择已配置 API，填写用途、输入输出和边界，点击开始。
   - 默认模式：分别确认方案和整套代码。
   - 勾选「自动生成、检查并最多修复四轮」：系统采用符合结构契约的草稿，直接运行 Go 检查；失败时按证据修改实现或建立新的测试修订。最多 7 次模型调用，达到上限会停止并保留失败证据。自动模式会跳过人工批准，请在最终版本检查业务语义与测试断言。
3. 图上观察 Planner / Tester 的真实调用状态。图下查看结构化结果，修改规格和验证说明，然后「确认方案并生成代码与测试」。
4. Developer 完成后逐文件查看代码。点击「批准整套代码并验证」后，系统创建项目文件夹并运行真实 Go 检查。
5. 查看 Executor 和 Gate 状态、检查输出；「打开代码文件夹」定位文件。「重新验证」创建新的验证记录；可继续暂停的验证。
   - 验证结果下方的「本次验证的代码」按文件展示已批准快照，方便把失败证据和实际代码对照；它不会读取后来手动改过的工作区文件。
6. 失败时可使用受控修复，审核修复代码后再次验证。测试和模块保持冻结，不能通过删除失败断言来伪造通过。

左侧按项目显示，底部「版本记录与执行日志」可切换历史、读取并复制整体日志。日志是所选版本来源链的有界汇总；修复的新分支需要选择对应版本。

## Tester、Go test 与 Gate

- 图上的 **Tester** 是模型角色：它阅读 Planner 的结构，提出测试方案和用例。此时没有生成完整项目，也没有运行 `go test`。若这里显示失败，通常是模型响应不符合方案契约，例如用例字段格式错误；从日志中的 `model_failed` 可确认。
- **Developer** 生成实际 Go 代码与 `_test.go`。人工模式下，只有你批准整套代码后才发布项目快照。
- **Executor** 才在发布的隔离快照中运行 `go test`、`go vet` 和格式检查。Go test 失败可能是测试源码无法编译、程序没有通过断言，或环境依赖问题；界面展示真实退出码和失败线索。
- **Gate** 不调用模型，也不执行第二份测试；它核对已批准检查节点的真实状态和结果。任一必需检查失败，Gate 失败。Gate 通过说明选定检查通过，不保证需求在测试以外的行为都正确。

普通实现修复不能修改冻结的测试。如果失败来自 `_test.go` 的循环导入、未使用导入或测试启动方式，可选「修订测试（新版本）」。新版本只能改既有测试文件，页面会展示改动；请核对断言仍对应原验收标准。自动模式也会记录每轮来源和工具结果。

当前支持标准库 Go CLI 项目，3–20 个计划文件。这里的「验证」是 test / vet / 格式检查；输入参数并启动生成应用的入口仍在下一阶段。角色图随真实事件更新，只展示当前版本的一条主线；旧尝试在版本记录中。自动任务运行在服务进程中，重启不会续传模型调用；关闭服务前应等待任务结束。
