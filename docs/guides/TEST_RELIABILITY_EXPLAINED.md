# 测试可靠性：这些测试到底在测什么、怎么读、怎么跟面试官讲

给自己看的“白话版”。每一节都先说**它在问什么问题**，再用一个具体例子，再说**数字怎么读**和**哪些话不能说**。所有数据的来源：真实 API 评测（DeepSeek Pro + Flash），原始数据在 `.masa/` 下，汇总表在设置页“实验结果”和 [reference/TEST_RELIABILITY](../reference/TEST_RELIABILITY.md)。

## 0. 先搞清楚：什么是“测试可靠性”

这个系统让模型写代码，再让模型**写测试**来验证代码。问题是：**测试也是模型写的，也会写错。**

> 例子（wc 任务）：需求是“统计行数、单词数、字节数”。模型写的测试说“`你好 世界
` 的字节数应该是 13”，但正确答案是 14（每个汉字 3 个字节，加空格和换行）。实现其实是对的，测试是错的。系统看到“测试不通过”，就去“修实现”——越修越错，或者白白转圈。

所以“测试可靠性”= **测试里写的期望值有多大概率是对的**。我们的失败分类（账本里 121 次失败）显示：云端强模型的主要失败不是“代码写错”，而是“测试的期望算错”（约 37%，加上没解决的断言约 51%）。提高测试可靠性，是**对准真实失败原因**的改进。

## 1. 实验一：模型当“出题人”，答案准不准？（期望推导准确率）

- **问什么**：给模型一个任务的需求和一组输入，让它写出“正确输出应该是什么”，再跟**独立的 Python 参考实现**（我们自己写、不是模型写的）比。答对的比例 = 准确率。
- **类比**：让一个人出考试题并写标准答案，然后用真正的标准答案去批改他的标准答案。
- **做了什么**：23 个任务、每个任务 Flash 采样 5 次、Pro 采样 3 次（并行）。共 184 次调用，约 ¥0.57，每次 1–3 秒。
- **结果**：单次 Flash 78%、单次 Pro 76%——**贵的 Pro 并没有更准**。让 Flash 做 3 次、取多数一致的答案（“多数表决”），准确率 92%。
- **怎么读**：同一个问题问 3 次，如果有 2 次答案一样，那个答案对的概率就很高；3 次各说各的，就**弃权**（不下结论）。便宜的多次表决 > 贵的单次。
- **不能说**：不能说“Flash 比 Pro 强”。是**这个任务（算期望值）**上 Pro 没有优势（我们把 Pro 的“思考”关了），以及表决带来了提升。

## 2. 实验二：能抓到“被故意改错的答案”吗？（审计实验）

- **问什么**：我把正确的答案**一半原样、一半故意改错**（数字加一、两行换位、大小写改了……），让“审计者”判断哪些是错的。抓到多少 = **召回**；把对的说成错的 = **误报**。
- **类比**：往答案册里**故意埋几个错答案**，看校对员能挑出几个、会不会冤枉好答案。这是最直接的“校对员水平”测试。
- **结果**（93 个被改错的 / 93 个原样的）：
  | 做法 | 抓到错的（召回） | 冤枉对的（误报） |
  |---|---|---|
  | 直接问“这个答案对不对？”（Flash 单次） | 26% | 22% |
  | 直接问（Pro 单次） | 33% | 12% |
  | **盲推导**：不给它看答案，让它自己算，再跟答案比（Flash×3 表决） | **91%** | **8%** |
- **怎么读（最重要的一条）**：直接问“对不对”几乎没用——模型**被你给的答案带偏了**（叫**锚定**）：你写 14，它就倾向于认为 14 没问题。办法是**不让它看到答案**，自己算，我们再用程序比较。
- **面试能讲的洞察**：这和系统里 Diagnoser 被测试带偏是**同一个现象**，所以审计角色设计成“盲推导 + 机械比较”。

## 3. 实验三：在真实的测试用例上做同样的事（真实用例审计）

- **问什么**：实验二用的是我们自己造的题。这次用**系统真实生成的测试用例**（期望是模型写的自由文本，如“Count returns lines=1, words=2, bytes=12”）。
- **做了什么**：对账本里 7 个任务的 79 个真实用例，把期望文本里的第一个数字加一（造错），看审计抓到多少；原样用例里被判“可疑”的有多少。
- **结果**：被改错的抓到 **85%**（66/78）；原样用例判可疑 **6%**（5/79）——这 6% **不一定是误报**，里面有 Tester 自己真的写错的。约 ¥0.12。
- **不能说**：不能说“误报率 6%”，只能说“可疑率 6%，是误报的上界”。

## 4. 实验四：接进流程以后，整体通过率变了吗？（配对 A/B）

- **问什么**：把“用例审计”做成一个开关（`test_audit`），同一个任务**关着跑一次、开着跑一次**，比较结果和花费。
- **为什么要“配对”**：模型每次输出有随机性，任务难度又不一样。**同一个任务**前后对比，比“开 20 次、关 20 次再比平均”更公平。
- **审计做了什么**：Tester 写完测试用例后，让 Flash 只看**输入**（不看期望）独立推导 3 次，再比较；多数认为跟 Tester 的期望不一致的用例被**丢掉**（至少保留 3 个）。每个任务多花约 ¥0.01。

## 5. 其它几个“看起来没用”的实验——这同样是结果

| 实验 | 做法 | 结果 | 结论 |
|---|---|---|---|
| 指挥者（让模型选下一步） | 25 次配对 | 通过率没提高，更贵（每次 +24%～+96%） | 保留为开关，默认关 |
| best-of-N（多采样几个修复，挑通过的） | 6 个任务 | 4/6 对 4/6，费用 +15%；额外采样只触发 1 次 | 保留为开关，默认关；因为主要失败是“测试错”而不是“实现错” |
| 经验库（记住以前的失败和解法） | 训练 4 个任务，留出 6 个任务测 | 留出任务上**命中 0 次**，没有可测的效果 | 最小版已搭好，用来积累数据 |
| 上下文预算（简单任务原样全给，大任务才裁剪） | 用 30 次真实输入重放 | 窗口 ≥32k 时一次都不触发（行为不变）；窗口 12k 时平均省约 850 token、必需内容一个不丢 | 框架已搭好，默认不接入 |

## 6. 名词表

- **账本**：系统把每一步发生了什么都记下来（谁调用了什么、结果是什么），可以事后翻。
- **Gate**：独立裁判。成功不是模型说了算，而是检查结果（编译、测试、格式）说了算。
- **独立判官 / 参考实现**：评测用的、不是模型写的标准答案，用来判断“系统说通过的东西到底对不对”。
- **假通过**：系统（Gate）说通过，但独立判官说不对。
- **召回 / 误报**：错的里抓到多少 / 对的里冤枉了多少。
- **多数表决 / 弃权**：多次独立回答里超过一半一致就采纳；没有就不下结论。
- **锚定**：给了模型一个参考答案，它就倾向于同意。
- **配对 A/B**：同一个任务前后对比的实验。

## 7. 怎么跟面试官讲

**30 秒版**：
“我的系统让模型写代码和测试，再用独立的 Gate 验证。我发现主要失败不是代码写错，而是**测试的期望值算错**。所以我用真实 API 做了一系列实验：先量化模型当出题人的准确率，发现便宜模型多次表决比贵模型单次更准；再发现直接问‘这个答案对不对’几乎抓不到错（召回 26–33%），因为模型被答案锚定，改成‘不给答案、让它自己算再比较’后召回到 91%。把它做成一个可开关的用例审计，在 17 个配对里 5 个更好、0 个更差，平均费用降 36%。同时我也如实否决了指挥者和 best-of-N——它们没有收益。”

**2 分钟版**（加上）：
- 为什么这么做：先看**失败分类**（账本里 121 次失败）再决定做什么，不是凭感觉加功能；`go doc` 工具因此被我砍掉（标准库用法错只占 2%）。
- 怎么保证不吹牛：独立判官（不是模型写的参考实现）、配对评测、费用上限、默认关闭、差分检查证明默认流程没变。
- 学到什么：**机制要用数据证明有用；多一次 LLM 调用不免费；验证者不能看到被验证的答案。**

**可能被追问的**：
1. *为什么不直接用更强的模型？* → 我们量了：Pro 单次 76% < Flash 表决 92%，价格还贵 9 倍。
2. *样本这么小，结论可靠吗？* → 不够，我明确标成“默认关闭的实验”，并写了每个限制；17 个配对里 0 个更差是方向性证据，不是统计显著。下一步是扩大到每组 30+。
3. *参考实现怎么保证是对的？* → 它是我们写的 Python 代码，期望不是手写；但它也可能有歧义（kvtx 两个模型全错，我怀疑是题面歧义），这是我们对“难度”的一个解释而不是定论。
4. *会不会过拟合评测题？* → 审计用的是“盲推导”，不看题目答案；但评测题库是固定的，所以经验库实验我专门分了训练题和留出题——结果是留出题上 0 命中，我如实记录而没有宣称有效。
5. *审计会不会把好用例误删？* → 可疑率 6% 是上界；而且设计上最少保留 3 个用例，不够就一个都不删；每次丢弃都写进账本。

**不要说的**：不要说“提高了通过率 X%”（样本小）；不要说“62% 成本下降”（这个数字没有真实依据，本次实测是约 −36%，也只在小样本里）；不要说“经验库有效”；不要把“MCP 用 Claude Desktop 验证过”当成事实（我们用官方 MCP 客户端 + 子进程在协议层验证过，没用 Claude Desktop）。
