# best-of-N（验证选择的多次尝试）

2026-10-07。策略 `best_of_n`（1 = 关，默认；设置页“路由与预算”里可调，范围 1–5）。

## 做了什么
- 在**修复实现**阶段：第一个候选被接受后，如果它没有通过验证，就让**最便宜的合格模型**（路由器对一条新链从最低等级起步）再生成 N-1 个候选；每个候选都真实验证（Runtime + Gate）；选“通过 > 未解决条目最少 > 先来的”。第一个候选就通过则不再多花钱。被选中的候选已验证过，主循环直接复用那次验证（`job['preverified']`），不重复验证。
- 每个额外候选的调用都经过路由与预算（`best_of_n` 链），预算不够就用已有的候选；账本事件 `best_of_n`（候选数、各自是否通过、未解决条目数、选了哪个）；前端活动日志与报告“修复过程”可见。
- **不对修订测试采样**：评测里发现 `best_of_n` 也触发在 test_revision 阶段，而“按通过来选测试”会偏向迁就有缺陷实现的测试（假通过风险），所以限定为 `fix:implementation`（回归测试）。
- 调优器的搜索空间加入 `policy.best_of_n`（1–4）。

## 真实 A/B（6 个任务 × 关/开 N=3，费用 ¥3.26，Pro + Flash，api）
| 任务 | 关 | 开(N=3) | 额外采样 |
|---|---|---|---|
| wc | 通过 ¥0.37 | **未通过** ¥0.30 | 触发 2 次，每次 3 个候选，**未解决条目都是 1**，没有改善 |
| wordfreq | 通过 ¥0.07 | 停止（单任务 token 上限）¥0.51 | 只有 1 个候选 |
| csv_sum | 通过 ¥0.12 | 通过 ¥0.29 | 事件在 test_revision（现已排除） |
| roman | 通过 ¥0.15 | 通过 ¥0.09 | 未触发 |
| lcs | 未通过 ¥0.39 | 通过 ¥0.34 | 事件在 test_revision（现已排除） |
| knap | 未通过 ¥0.41 | 通过 ¥0.22 | 未触发 |
合计：关 4/6 通过 ¥1.52；开 4/6 通过 ¥1.74（约 +15%）。

## 结论（诚实版）
- **没有证据表明 best-of-N 提高了通过率**：4/6 对 4/6。开组在 lcs、knap 上赢、在 wc、wordfreq 上输，但 **额外采样真正触发的只有 wc**（4 次额外调用，3 个候选的未解决条目完全一样，没有改善），其余差异是模型本身的随机波动（两组在这些任务上的代码路径其实相同）。
- 原因（与失败分类一致）：wc 的失败是**测试/规格里的期望算错**，多采样“实现”无法修复；best-of-N 只对“实现写错且每次写错不一样”有用。云端强模型的实现错误本来就少（逻辑错只占 10%）。
- 所以：保留为可选开关、默认关闭；**不要宣称提升**。如果要继续，应该针对“测试更可靠”（路线图第 2 步），而不是更多的实现采样。
- 另一个观察：额外候选会增加验证轮数的统计（报告里 wc 显示 7 轮），评测的“轮数”指标在开启时不可直接比较。
