## 1. 真实 Ollama 被杀演练（`scripts/drill_ollama.py`，手动、占 GPU）

| 场景 | 观察到的事实 |
|---|---|
| R1 客户端被杀（我们的进程在请求中途被硬杀） | Ollama **会取消**被抛弃的请求，不会一直占着 GPU。但下一次请求被**延迟约 6.6 秒**（两种不同请求都是 6.6 秒，说明是取消后重载模型的固定开销，不是等生成跑完） |
| R2 服务端被杀（请求中途杀 `ollama serve`） | 我们这边 5 秒内收到“没有响应”，账本里这次调用记为 `failed`、没有任何响应，任务随之失败；托盘程序**有时**会自己拉起服务，有时不会（这次演练里它没拉起，脚本自己拉起了） |
| **R2 的副作用（用户提问时发现）** | **杀掉 `ollama serve` 会留下孤儿 `llama-server.exe`，继续占着显存和内存**：一次演练遗留 6 GB 显存，两次共 6.3 GB 显存 + 17 GB 内存（工作集）。我当场清理了，显存 6318 → 1495 MiB，并把它做成了产品功能（§2） |

R2 之后用**真实任务**再验证：任务进行中杀 `ollama serve` → 第一次 Planner 调用记为传输失败（`model_failed.transport=true`）→ `transport_retry` 事件 → 服务恢复后重试成功 → 整个任务无人工干预、Gate 通过。

## 2. 孤儿模型进程：检测与一键清理

`infrastructure/orphans.py`：只检测并清理“**确认父进程已不存在的 Ollama 自带 `llama-server.exe`**”，别的进程一律不碰；清理每个 pid 前**再次核对**（可能已被接管）。

- 本地运行时页面新增“模型运行进程”卡片：自动检测（15 秒刷新），有孤儿时显示 PID、内存、模型、启动时间，并提供“清理 N 个孤儿进程”。
- 端到端验证：加载模型 → 杀服务 → **检测到孤儿（1.7 GB）→ 清理 → 显存 10325 → 1593 MiB**。
- 演练脚本现在结束前一定清孤儿。

## 3. M0.5 剩余项

- **同级轮换**：同一等级有多个候选时，失败次数作为轮换序号，交替使用（换一个模型比重复同一个更可能得到不同结果）。
- **按角色起始等级**：`start_level_by_role`，例如 Planner 从 L2 起；该等级没有可用候选就退回任意等级。
- **预算/策略可编辑**并持久化（`routing.json`）；设置页「路由与预算」可改；新建任务可覆盖 API token 上限和参与的模型。
- **顶栏预算条**：API token、调用次数，≥70% 变黄、≥90% 变红；显示升级次数。
- **估算校准**：`scripts/calibrate_tokens.py` 用真实调用拟合系数，Console 启动时加载 `token-calibration.json`。用 60 个真实样本重新拟合的结果（ASCII 0.276、非 ASCII 0.496 token/字符）与内置系数一致，所以没有覆盖它。
- **`previous_files` 计入估算**：逐文件生成时按每个已生成文件约 4000 字符估计。**副作用要知道**：8K 窗口的本地模型（如 gemma4:12b 的默认配置）在多文件项目的生成阶段会被判“放不下”而改用 API；想让它生成，把该模型的上下文上限调大（设置 → 模型配置）。

## 5. API 账户页（`/settings/accounts`）

一把 key 往往能用多个模型。按“地址 + key 的哈希”把云端配置归为账户（**key 只在后端，页面和接口都不返回**）：

- 向官方 `GET /models` 实时查询这把 key 能用的模型：名称、上下文、最大输出、是否支持图片、推理档位。真实结果（DeepSeek）：`deepseek-flash`（V4.1-Flash）与 `deepseek-v4-pro`，上下文均 1M、最大输出 384K。
- **勾选 = 启用**（没有配置会自动添加；取消勾选只停用，已有设置保留），“应用勾选”一次生效；默认模型不变。
- **并排对比**表：每列最优值高亮（上下文最大、输出最大、价格最低）。
- **余额**：DeepSeek 的 `GET /user/balance`（可用/不足、币种、充值/赠送）；其它服务没有已知接口时明确显示“没有已知的余额接口”，不猜。
- **价格是建议值**：来自官方定价文档（2026-10-04 抓取，USD/百万 token，取高峰期、缓存未命中的保守值，出处会显示在页面上）；**文档是通过网页抓取+摘要得到的，请核对**。`GET /models` 才是模型与上下文的权威来源。
- 系统上限：上下文最多按 262,144、单次输出最多按 8,192 token 计，更大的值会被夹到这个上限（页面注明）。

## 6. M1 ① 崩溃自愈：免费的重试，付费的保护

**原则**：能安全重试的才重试。

| 情况 | 本地（免费） | 云端（付费） |
|---|---|---|
| 没收到任何响应（连接被拒、服务被杀） | **等服务恢复（最多 15 分钟，可配）→ 重试**，不计入失败链、不触发升级，最多 6 次 | 结果仍视为未知，**不自动重试** |
| 进程崩溃时请求在途（账本里 `running`） | 标记旧尝试为“被放弃”，作为**同一次调用的新尝试**重试（不占预算） | **永不重放**，明确停下 |
| 已收到响应但被校验拒绝 | 走原有“带原因重试 → 升级” | 同左 |

实现：`TransportFailure` 类型化异常（穿过各阶段包装）；`ChatProvider.wait_until_reachable`；账本层 `_free_retry`（必须是本地 + 策略允许 + 确实没拿到响应）；事件 `model_failed.transport`、`model_abandoned`、`transport_retry`；任务报告里“被放弃”的调用单独显示。固定模式保持旧行为。

恢复演练的四个场景现在是：A 验证中途崩溃 → 不重复、状态保留、升级成功；B 本地修复请求丢失 → **重试**；C 本地生成请求丢失 → 已完成的规划不重做、生成**重试**；D 云修复请求丢失 → **不重放，明确停下**。

**演练中又发现并修了一个缺陷**：崩溃发生在“发出请求”和“记录这次由谁修复”之间，恢复后路由器不知道本地已试过，于是又选了一次本地。现在**发请求之前**就持久化“这次由谁修复”。

## 7. M1 ② 确定会失败的项目

### 7.1 可行性预检（执行前，零成本）

**历史证据**：真正“确定会失败”的是 `实现 Go 函数 Clamp…保留 package solution`（失败 6 次）——它要的是库包，而 harness 只能验证 `cmd/app/main.go` 的命令行项目，**任何模型都不可能通过**。

确定性规则（`application/triage.py`）只依据 harness 的硬约束，命中且未被否定词抵消才算：

| 判定 | 规则 |
|---|---|
| **确定会失败** | 非 Go 语言；第三方依赖；网络/外部服务/数据库/爬虫；GUI/网页/硬件；要库而不是命令行 |
| 有风险（只告警） | 交互/实时/终端界面；并发与时间；性能指标；范围很大；主观要求；需求过长/过短 |

- **用全部历史需求回测：0 个误杀**（成功过的都放行），并正确拦下两条 Clamp 需求；2048 小游戏只给“有风险”（它实际成功过）。
- 命中“确定会失败”：**不调用任何模型**，留下一条可读的失败记录（原因 + 改写建议），任务页有专门状态“预检拦下”；新建任务页**输入时实时预检**，禁用开始按钮，勾选“我了解风险，仍然继续”才能开始（`force`）。
- **本地模型复核（可选，默认开启于 ladder）**：只用本地模型、只能把判断升级为“有风险”（它说“不可行”也会被降级），失败不影响规划。弱模型不能误杀好需求，也不会花 API。
- 真实验证：必败需求 **0 token、0 次调用、2 秒结束**。

### 7.2 失败签名“卡死”检测

把所有失败检查的诊断去掉文件名、行列号和数字，得到**失败签名**。同一签名连续出现 N 次（默认 4）**并且最强的模型已经试过**，就停下交给人，不再继续花钱。固定模式关闭（保持旧行为）。

## 8. 没做 / 已知限制（诚实清单）

1. **Diagnoser**（升级前先让高级模型只做诊断，输出 `{class, 原因, 指导}`，让本地模型照着修）**没做**；它需要新角色、提示词、真实模型验证。
2. **声明式工作流 + 通用引擎**、**API/Worker 拆分 + 租约 + 命令表 + 崩溃后自动续跑**没做。当前“崩溃自愈”是：手动重新启动服务后恢复任务（`resume`）时，账本层对本地调用自动重试；**没有常驻 supervisor 自动拉起**（已确认手动启动即可）。
3. 本地复核模型只在 ladder 且有本地候选时运行；规则的关键词表是中英文常见写法，覆盖有限（回测 0 误杀，但漏报是可能的）。
4. 失败签名只看 Go 工具输出的诊断行；运行期 panic 的栈只取前几行。
5. 孤儿检测只支持 Windows，且只认 Ollama 默认安装目录下的 `llama-server.exe`。
6. 价格是文档抓取的建议值；币种可能与余额币种不同（USD vs CNY），预算的“费用”以你填的价格币种为准，系统不换算。
7. 恢复演练用假模型 + 假执行器；真实的“杀进程再恢复整个任务”只验证了 Ollama 被杀这一种。
8. 8K 窗口的本地模型在多文件项目的生成阶段会被判放不下（§3）。

## 9. 下一步建议

1. **Diagnoser**（含真实本地+云验证）：升级前先诊断，诊断后让本地照着修，再不行才让高级模型直接写。
2. **声明式工作流**（先接管失败后的修复子图）+ 通用引擎。
3. **Worker 租约 + 命令表**（API 与执行拆进程），崩溃后可自动续跑。
4. M2：`httpx` 流式与真取消、资源信号量。
