# Runtime 主动需求澄清设计（待实现）

本文是后续 LLM 实施契约，不代表功能已上线。目标是让角色在缺少业务事实时暂停提问，得到回答后继续；它与方案审批、测试通过判定严格分开。

## 1. 用户体验

输入“写一个随机数生成器”后，Planner 可以提出一组影响接口和验收的问题：

- 数值类型：整数（建议）/小数；支持补充文字。
- 范围和边界：0–99 且包含两端/自定义范围；自定义填写上下界。
- 输出：每次一个数/指定数量；文本或 JSON。

不要每次都问所有问题：已经明确的需求不再提问，不影响行为的文件命名由角色自行决定。如果是安全令牌用途，随机源选择属于重要澄清；普通演示不能自动升级为复杂安全产品。

图上的 Planner 显示“等待你的回答”，问题卡片出现在当前阶段下方并自动定位。用户选择选项或自由填写，点击“提交回答并继续”。不得把预选项、关闭卡片或等待超时当作回答。回答记录可在日志复制。自动验证模式也必须停在真正的需求问题，不能由模型替用户回答。

Tester 同样可问：“重复值是否允许？”而不是凭空写出“多次运行输出必须不同”的不可靠断言。项目已明确允许重复时不再问，直接使用范围/格式等确定性验证。

## 2. 角色输出协议

采用显式带类型的角色结果，不从自然语言里猜问号：

```json
{
  "kind": "clarification_request",
  "reason": "范围与边界会影响 CLI 参数和测试断言",
  "questions": [
    {
      "key": "number_range",
      "title": "默认随机数范围是什么？",
      "options": [
        {"id": "zero_99", "label": "0–99，包含两端"},
        {"id": "custom", "label": "自定义"}
      ],
      "allow_text": true
    }
  ]
}
```

另一分支为 kind=completed，携带原角色 payload。优先适配 Planner，再适配 Tester；迁移期间旧 completed 数据保持可读。Runtime 分配 question_id、run_id、step_id、requirement_revision，不接受模型自行指定关联运行或权限。每组最多 3 问、最多 3 个选项，长度限制由 Runtime 校验；自由文本保留原文，不转成可执行命令。

## 3. 执行和恢复语义

状态路径：running → waiting_for_input → ready → running → completed。模型成功返回问题意味着本次 Attempt 已完成，不是错误或重试；逻辑 Role Step 尚未完成。独立角色调用须引入 invocation_id/attempt_no，不能继续用 (run_id,purpose) 唯一键保存多个回答后的调用。

保存模型结果后，原子写入澄清记录、等待状态和事件。后台线程退出释放资源，不占用 HTTP 请求或循环轮询模型。Jobs 重启只把 running 标记 interrupted，waiting_for_input 应保持等待。新进程通过数据库找回问题，不重新问模型。

回答接口建议 POST /api/runs/{id}/clarifications/{question_id}/answer，提交 expected_revision、idempotency_key 和各问题的 option_id 或 text。事务中检查问题仍 pending、版本匹配、选项合法及回答完整，然后保存不可变回答 artifact，标记 answered 并写入待继续状态。重复相同请求返回已有结果；冲突回答拒绝；旧页面不能回答新版本问题。

回答提交与后台启动之间可能崩溃：先持久化 ready，再由启动入口显式拾取；不能依赖 HTTP 内存回调作为唯一继续机制。继续调用包含原问题、原回答和需求版本，使用新的 invocation_id；不得覆盖旧角色输入或把缓存响应误当作新回答结果。

## 4. 需求版本、上下文和 Gate

答案属于用户约束，保存在 requirement_revision 中，由 ContextBuilder 传给受影响角色。回答与已有明确需求冲突时显示冲突并要求明确变更，不能静默覆盖。规划前的回答形成首份有效需求；Tester 或 Developer 中途澄清若改变行为，则产生新规格版本并使旧测试/代码提案失效，回到必要规划步骤。第一版采用整条下游链失效，暂不实现精细图传播。

旧快照、检查结果和 Gate 结论保留供审计；它们不能验证新需求版本。Gate 始终核对对应版本的实际工具证据。回答“应该通过”不等于测试通过。禁止通过澄清请求取消失败证据或修改测试来迎合代码。

## 5. 预算和异常

每次模型请求正常计费；等待用户本身不计 token。建议每个角色最多两组澄清，达到上限转为 needs_attention，不自行猜测。运行 deadline 保持原语义：过期保留问题和答案，提供显式续期/新版本入口，不隐式延长无限运行。用户取消终止后续执行，保留历史。

## 6. 与既定路线合并

| 优先级 | 增量 | 验收条件 |
|---|---|---|
| P0 当前 | 拆分检查点规则、统一角色 Step/Attempt 与调用标识 | 旧运行可读，恢复不重放，预算不重置 |
| P1 紧接 | Planner 澄清协议、持久等待与回答接口 | 模糊随机数任务提问；明确需求直接规划；重启可回答 |
| P1 同批 | 前端问题卡片、图等待状态、自动模式暂停 | 选项/自由文本可提交，旧答案和重复提交有确定行为 |
| P2 | Tester 澄清与需求版本失效 | “是否允许重复”决定测试策略，旧证据不冒充新证据 |
| P2 原主线 | 独立测试评审 | 识别随机性断言、构建 cwd、越界常量，不随意放宽测试 |
| P2 原主线 | 上下文收益评估 | 相同任务固定输入，比较全量/检索上下文，报告质量和实际 token |
| P3 原主线 | 中型仓库任务 | 行数统计、配置校验、跨包修改，多文件和接口回归 |
| 延后 | 任意角色并发问答、局部精细失效、自适应图 | 前述闭环稳定后再实现 |

这不是额外新建一个聊天系统：沿用 SQLite、现有事件/Artifacts 和 React 工作台，无消息队列或新服务。

## 7. 测试矩阵

确定性测试先覆盖两种结果、非法问题、重复回答、过期版本、取消、deadline、响应后崩溃、问题保存后崩溃、回答后启动前崩溃、多个浏览器同时回答、自动模式必须等待。真实 API 用旧随机数案例对照：模糊需求提问，明确范围/格式不重复问，答案进入 Planner 与 Tester；最后真实 go test/vet/Gate 和 CLI 输出验证。每轮记录提问次数、成功率与费用，不承诺所有模糊需求都能识别。
