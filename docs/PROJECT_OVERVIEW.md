# 项目总览（先读这一份）

2026-10-06。这份文档用白话讲清：这个项目是什么、解决什么问题、一次任务怎么跑、每个术语到底指什么、Gate 是什么、做到哪了、没做什么。
其它文档（STATUS、PLAN_*、progress/*）是历史记录，细节以代码和这份为准；路线见 [ROADMAP](ROADMAP.md)，简历写法见 [RESUME_PROJECT_DESCRIPTION](RESUME_PROJECT_DESCRIPTION.md)。

## 1. 一句话

**让“能力一般的模型”可靠地写出能用的程序，并且把“它到底做成没有”交给运行时而不是模型来裁决。**
输入一句需求（“实现 CSV 费用汇总命令行”），系统自动：规划 → 写测试 → 写代码 → 在隔离环境里真的运行测试 → 失败了就找原因再修 → 最终给出“通过 / 没通过”以及证据；整个过程用多个模型分工（便宜的本地小模型先试，不行再升级到贵的云端模型），并且受预算限制、崩溃后能续跑。

## 2. 它在解决哪几个具体问题

| 问题（任何 Agent 项目都会遇到） | 常见做法 | 这个项目的做法 |
|---|---|---|
| 模型说“我做完了，测试都过了”，其实根本没跑 | 信模型的话，或让另一个模型“打分” | 成功与否由运行时**真的执行**测试后根据账本推出，模型无权宣布成功（见 §4 Gate） |
| 全程用最贵的模型，成本失控 | 固定一个模型 | **有界升级**：本地小模型先试，失败逐级升到更强的模型；整个任务有 token/时间预算，到顶就停并保留证据 |
| 一次长任务跑到一半进程崩了 | 从头再来（重复花钱） | 每次调用先记账再发请求；崩溃后**已完成的不重做，付费调用结果未知时不盲目重发**，免费的本地调用自动重试 |
| 不知道改了 Agent 的某个设计到底有没有变好 | 凭感觉、看几个例子 | 自建**评测**：23 道分 10 个难度等级的题，由**独立判官**真的运行产物并统计假通过率 |
| 弱模型反复犯同类错误（漏 import、测试期望算错……） | 多问几次 | 把能用工具判定的错误交给**确定性工具**（语法门、import 修复、入口检查），其余才问模型 |

## 3. 一次任务怎么跑（以“CSV 费用汇总”为例）

```
需求 ──► 预检（本地模型，只告警）
      ──► Planner（最强模型）：把需求写成“验收项”，例如“按金额降序”“表头不算数据”
      ──► Tester（最强模型）：先把测试写出来并**冻结**（之后谁也不能为了通过而改测试）
      ──► Developer（本地小模型起步）：对着冻结的测试逐文件写实现
             每写完一个文件，立刻做确定性检查：能不能解析、import 对不对、main.go 有没有偷读输入
      ──► 验证：在隔离副本里运行 go test / go vet / gofmt（Go runner，受控子进程）
      ──► Gate：根据账本裁决 通过 / 失败 / 需要人看
      ──► 没通过：分析失败属于“实现”还是“测试”→（必要时 Diagnoser 诊断）→ 修实现 / 改测试 / 整体重写
             每次修复先由本地模型试，没改善就升级到更强的模型；预算耗尽就停
      ──► 报告：每个角色用了哪个模型、花了多少 token 和时间、走过哪些修复步骤
```

## 4. Gate 到底是什么（重点，容易被误解）

### 4.1 先说结论
**Gate ≠ 测试。测试是“一项检查”，Gate 是“决定成败的那个裁决程序”。** 它回答的问题不是“代码对不对”，而是：

> “凭账本里这些**不可篡改的执行记录**，这次任务能不能被宣布成功？”

测试只提供“代码行为对不对”的证据；Gate 负责保证“**证据本身可信、完整、对得上这份代码**”，并且把任何异常都判成“不通过”，绝不判成“通过”。代码在 `src/masa/runtime/engine.py::_gate`。

### 4.2 Gate 具体检查什么（四条，都是代码里真的做的）
1. **该跑的检查都跑完了**：必须的检查（`go test` 必有，`go vet`、`gofmt` 按 Tester 方案）每一项都已到终态且成功；有一项没跑完、缺结果，整体不通过。
2. **证据对得上这份代码**：每条结果里记录的快照编号必须等于当前这次验证的快照编号，否则判 `stale_evidence`（过期证据）。——防止“代码改了，却还拿着上一版的通过结果”。
3. **节点摘要和工具账本一致**：把节点上报的结果与工具账本（真实执行记录）逐项比对，不一致判 `integrity_error`。——防止“上报的结果和真实执行的不一样”。
4. **每个结果都是真的跑完且退出码为 0**：状态必须是 completed 且 exit_code==0；超时、未知、被中断一律不算通过。
另外：**Gate 节点永远由运行时加上，模型的方案里没有、也删不掉它**；模型提出的检查只能从白名单（go_test/go_vet/go_fmt_check）里选，不能提交 shell 命令。

### 4.3 “现在不是必须通过 test 才算成功吗？Gate 还有什么用？”
你说得对：**正常路径上，测试全过 ⇒ Gate 通过，二者看起来一样。** Gate 真正起作用的是**不正常的路径**，这些在 Agent 系统里恰恰是常态：

| 情形 | 没有 Gate 的朴素做法 | 有 Gate 时 |
|---|---|---|
| 验证跑到一半进程被杀（崩溃/断电） | 当作“失败”去修，或者误当“通过” | 状态不确定 → 标 `needs_attention`，**重新验证**（工具是幂等的）而不是去“修”一个并不存在的失败（真实踩过：见进展 `reverify`） |
| 重新验证/恢复后，账本里混着上一版的结果 | 把旧结果算进来，可能把过期的“通过”当成这版的 | 快照编号对不上 → 过期证据，拒绝 |
| 模型想“让测试通过”而去改测试 | 测试被改弱，照样绿 | 测试在批准后**冻结**（内容哈希）；修复提案里改了 `_test.go` 直接被拒绝（`repair cannot change tests`） |
| 节点上报的结果和真实执行记录不一致（bug 或篡改） | 照单全收 | 与工具账本比对，不一致即 `integrity_error` |
| 检查只跑了一部分（比如 vet 没跑） | 只要 test 绿就算过 | 方案里要求的每一项都必须成功 |

一句话：**Gate 把“成功”从“模型说的 / 某个节点报的”变成“能从账本里推导出来的”。** 这和 CI 里“合并门禁”、SWE-bench 的评测 harness（在干净容器里跑指定测试，`FAIL_TO_PASS` 和 `PASS_TO_PASS` 都过才算解决，模型看不到测试）是同一类思想：**生成和验证分离，验证由确定性的执行完成**。

### 4.4 它的局限（面试时主动讲更可信）
**Gate 的强度 = 测试的强度。** 如果测试是模型自己写的、而且漏了东西，Gate 一样会放行。这不是推测，是这个项目**实测出来的**：自建评测里，系统 Gate 通过的结果有约 17%（4/23）被独立判官推翻——例如 `wc` 的 `main.go` 里 `io.ReadFull(os.Stdin, input)` 往空切片读，永远读到 0 字节，输出 `0 0 0`，但测试只测了内部包，`main.go` 从没被执行，所以 `go test`、`go vet` 都过。
我们的应对：① 提示词与确定性检查要求 `main.go` 只做薄薄一层、读输入的逻辑必须放进被测试覆盖的包；② 用**独立判官**（不是模型写的，而是评测自带的参考实现，真的构建并运行产物）度量“假通过率”；③ 规划里（M3）让 Gate 自己用 Tester 的 CLI 用例真的跑一遍产物，并做测试追溯矩阵。
**所以最好的讲法不是“我有个 Gate 所以结果可信”，而是“我有 Gate，并且用独立评测发现它会放行 17% 的错误，然后定位根因、修了，把假通过率压下来”。** 这体现的是对“验证本身也会出错”的认识。

### 4.5 面试怎么讲（30 秒版）
> “Agent 最大的问题是模型会自报完成。我把‘完成’的定义从‘模型说完成’改成‘运行时在隔离环境真的跑完测试，并且证据能和账本、快照对上’——这个裁决单独成一个 Gate 节点，模型无权跳过。它和测试的区别是：测试判断代码对不对，Gate 判断‘证据可不可信、是不是这一版、有没有被篡改或漏跑’。我还自建了带独立判官的评测，发现 Gate 在入口代码没被测试覆盖时会漏过约 17% 的错误，针对性修了。”

## 5. 术语表（简历里出现的每个词）

| 术语 | 白话 |
|---|---|
| **账本（ledger）** | 一个只追加的 SQLite 事件日志。每次模型调用、每次工具执行、每次状态变化都写进去。任务状态由它推导，崩溃后靠它恢复 |
| **快照（snapshot）** | 把待验证的代码文件打成不可变的一份（带哈希）。验证永远针对某个快照，证据和快照绑定 |
| **冻结的测试** | 测试批准后内容锁定。后面的“修复”只能改实现，不能为了通过而改测试 |
| **测试先行（tests-first）** | 先让最强的模型把测试写好并冻结，再让（较弱的）模型对着测试写实现；测试成了“规格” |
| **有界升级（bounded escalation）** | 先用便宜的本地模型，失败后按等级升到更强的模型；升级次数、花费有上限，到顶就停，不会无限烧钱 |
| **预算（先预留后结算）** | 每次云端调用前先按最坏情况预留额度，返回后按实际用量结算；调用没返回用量时按上限预留，保证不低估 |
| **付费调用永不重放** | 模型调用不是幂等的（花钱、输出还可能不同）。发请求前先写“意图”，收到结果后写“结果”；崩溃后如果某次付费调用“发出了但没存结果”，**不重发**，而是停下来让人决定；免费的本地调用则自动重试。类似数据库的 write-ahead log / 外发箱（outbox）模式 |
| **exactly-once** | 每个角色调用在账本里只被“完成”一次，恢复时不会重复执行已完成的调用 |
| **Diagnoser** | 修复多轮没进展时，让最强模型判断“是实现错了还是测试错了”，并给具体修改指示 |
| **整体重写** | 补丁连续没改善时，不再补，让最强模型对着冻结的测试把实现重写一遍 |
| **独立判官（oracle）** | 评测里用的“标准答案”：每个题有一份手工参考实现，评测把系统生成的程序真的构建运行，逐用例比对。它不依赖系统自己的测试 |
| **假通过** | 系统的 Gate 说通过，独立判官说不对。是衡量“证据可靠度”的指标 |
| **稳定等级** | 通过率 ≥ 67% 的最高难度等级，比“最高通过等级”更不受运气影响 |
| **runtime 机制计数** | 评测里统计各个机制被触发了几次（自动修 import、Diagnoser、整体重写……），用来判断某个改动到底有没有在线上起作用 |
| **流式 / 真取消 / stall 检测** | 模型回答边生成边读；点“停止”能立刻断开连接让模型停止生成；一段时间没有任何字节就判卡死（本地可重试，云端不重放） |

## 6. 模块地图

| 目录 | 职责 |
|---|---|
| `src/masa/runtime/` | 引擎（图执行、Gate）、角色调用（exactly-once）、实时进度 |
| `src/masa/application/` | 协调器（规划→生成→验证→修复循环）、路由与预算（`routing.py`、`router.py`）、声明式工作流（`flow.py`、`workflows.py`）、归属分析、Diagnoser、各种确定性检查（`goimports.py`、`leaks.py`、`testlint.py`、`entrypoint.py`、`snippets.py`、`attempts.py`） |
| `src/masa/infrastructure/` | 模型调用（`llm.py`、`streaming.py`）、SQLite 账本、设置、Ollama 控制、Go runner 的 Python 侧 |
| `src/masa/bench/` | 评测：任务库、独立判官、汇总与对比、运行器 |
| `runner/`（Go） | 受控执行：在 Windows Job Object 里启动 `go build/test/vet`，超时取消、进程树 kill-on-close |
| `frontend/`（React+TS） | 任务图、代码查看、报告、设置（模型次序、路由预算、评测） |
| `tests/` | 404 项 Python 测试 + 31 项前端测试；很多是“修复前确认会失败”的回归测试 |

## 7. 做了什么 / 没做什么

| 状态 | 内容 |
|---|---|
| ✅ 已实现并验证 | 账本与 exactly-once；崩溃恢复（含真实硬杀进程的演练）；Gate；Go runner 隔离；多模型路由+预算+有界升级；声明式修复子图；Diagnoser；测试先行；确定性检查；评测（23 题、独立判官、三层上限、一键运行）；流式+真取消+stall 检测+实时进度；前端工作台 |
| ⚠️ 实测发现的问题 | 混合（本地起步）目前**不如纯云端**（通过率 57% vs 79%，云端 token 基本持平，慢 1.75 倍）；Gate 放行约 17% 的错误；Tester 偶发无效输出；L9 题没通过 |
| ⏳ 还没做 | 动态角色的收益（RoleSpec、指挥者、调优器、MCP 已实现；指挥者真实评测未见收益、默认关闭；调优器未做真实运行；MCP 未用真实客户端验证）、Worker 租约与自动续跑、GPU 调度、验证选择的多样本取优（best-of-N）、逐函数生成、经验库；OpenTelemetry 导出；Gate 自己执行产物的 CLI 用例；非 Go 语言 |

## 8. 怎么运行

```bash
python -m masa serve --port 8765            # 后端
cd frontend && npm run dev                  # 前端
python scripts/eval/bench.py --suite canary      # 5 分钟评测（会调用模型）
python -m unittest discover -s tests        # 全部测试（不调用真实模型）
```
