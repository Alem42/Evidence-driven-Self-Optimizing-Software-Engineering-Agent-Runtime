## 2. 标准版（约 1400 字，简历正文通常取其中 4–5 条；其余放作品集/面试讲稿）

**Verdict（原 MASA）｜可验证、可恢复、成本可控的编码 Agent Runtime｜个人项目｜2026.08–Now**
**技术栈：** Python、Go、SQLite（事件溯源）、React/TypeScript、Ollama、DeepSeek/OpenAI 兼容 API、SSE/NDJSON 流式、MCP（FastMCP）、OpenTelemetry/Langfuse、LangGraph、Pydantic、GitHub Actions、Docker

面向“用本地小模型完成编码任务、必要时才调用云端大模型”的场景，独立设计并实现 Agent Runtime，覆盖需求规划、测试与代码生成、隔离验证、失败修复、成本控制与评测。

- **执行验证（不信模型自报）：** 把“完成”的判定从模型自述改为运行时在隔离环境（Go 受控子进程、Windows Job Object）真实执行 `go test / vet / gofmt` 后，依据不可变代码快照与事件账本裁决；校验证据与快照一致、与工具记录一致、检查不缺项，异常一律判不通过。测试批准后冻结，修复无法通过改测试蒙混。
- **多模型路由与成本控制：** 纯函数路由器实现“本地优先、有界升级”（本地→中等→最强）；任务级 token/时间/费用/调用数预算采用“先预留后结算”；规格、测试与诊断用最强模型，实现与修复从低等级起步逐级上推。同任务较全云端，云端 token 降低 58%。
- **持久执行与崩溃恢复：** 事件溯源账本 + 角色调用 exactly-once；调用先写意图、后写结果，崩溃后已完成调用不重做，**付费云调用结果未知时不盲目重发**，免费本地调用自动重试；用真实 `kill -9` 演练 50 次，全部恢复且零重复计费。
- **流式、取消与卡死检测：** 读取 NDJSON/SSE 流，读取线程+队列使取消在数据块之间即可生效，连接关闭后服务端停止生成（取消延迟 P95 < 1.5s）；“首字前/回答中”两级静默阈值识别卡死，本地可重试、云端不重放。
- **面向弱模型的质量工程：** 强模型先写并冻结测试、弱模型对着测试实现；逐文件语法门、确定性 import 修复、入口检查；失败按“实现/测试”归属分析，修复子图用声明式工作流表达，并由 Diagnoser 逐条核对期望、补丁停滞后整体重写。
- **动态角色：** 角色以数据（RoleSpec：提示词、输出 schema、工具权限、默认等级）注册，由确定性规则选择，并允许最强模型在已注册角色内提议下一步；提议须过白名单、预算与步数校验，且由评测决定是否启用；可与 Claude Code subagent、OpenAI handoff 定义互相导入导出。
- **评测与可观测：** 自建 10 个难度等级 23 道题的评测，**独立判官**（手写参考实现，真实构建并运行生成的程序）复核系统自己的结论并统计“假通过率”，三层 token/时间上限；据此定位入口代码未被测试覆盖等 5 类缺陷，假通过率 17%→2.6%，L0–L6 通过率 93%（纯本地小模型 38%）；账本事件导出为 OpenTelemetry trace 并接入 Langfuse，MCP 服务暴露验证、评测与路由工具。
- **工程交付：** 404 项后端测试与 31 项前端测试，缺陷修复均配“修复前会失败”的回归测试；React 工作台提供任务图、代码审阅、实时生成进度、报告与一键评测；Docker 与 GitHub Actions。

## 3. 面试问答（每个术语都能讲清）

### Q1. “不信模型自报 / 验证”是什么意思？Gate 和测试有什么区别？
> 模型经常说“测试都过了”但根本没跑。我把成功与否的决定权从模型手里拿走：运行时在隔离环境里**真的执行**测试，把每次执行都写进账本，最后由一个独立的裁决步骤（我叫 Gate）依据账本决定通过与否。
> **区别：测试判断“代码对不对”；Gate 判断“这些证据可不可信”**——该跑的检查是否都跑完、证据是不是针对**这一版**代码、节点上报的结果和真实执行记录是否一致、有没有超时/中断。正常路径上测试全绿 Gate 才会过；它的价值在异常路径：验证跑到一半崩溃、恢复后账本里混着旧版本的结果、模型想改测试让自己通过——这些情况下 Gate 保证“只要有疑问就不通过”。
> 类似 CI 的合并门禁，或 SWE-bench 的评测 harness（在干净容器里跑指定测试，两类测试都过才算解决，模型看不到测试）。

**追问：那 Gate 是不是只在“节点不合法”时才有用？**
> 不止。它是一个架构边界：成功是**从账本推导出来**的，而不是任何 Agent 宣布的。我自己的评测也证明了它的局限——Gate 的强度等于测试的强度：评测里有约 17% 的“系统判通过”被独立判官推翻（比如入口 `main.go` 读输入的 bug，测试只覆盖内部包所以没发现）。我因此做了入口检查、让最强模型写测试并冻结、并用独立判官度量假通过率，把它压到 3% 以下。

### Q2. “付费调用永不重放”是什么？
> LLM 调用既花钱、输出又不确定，不能像普通幂等请求那样直接重试。我采用类似数据库 write-ahead log 的做法：**发请求前先把“意图”写进账本，收到结果后再写“结果”**。如果进程在中间崩溃，恢复时看到“发出去了但没有结果”的付费调用，**不重发**，而是停下来让人决定；而免费的本地模型调用可以安全地自动重试。这样已完成的调用不重复做、付费的不盲目重复花钱。我用真实的 `kill -9` 子进程做过演练，不是 mock。

### Q3. “测试先行”是什么？为什么让强模型写测试？
> 就是 TDD：先写测试并冻结，再让实现去通过它。为什么用强模型写：测试是后面所有步骤的“规格”，写错了，实现再努力也没用；而测试的 token 很少，用最强模型成本低、收益高。实现用便宜的小模型起步，失败再逐级升级。我踩过的坑：让弱模型写测试，它把期望值算错（字节数多 1、降序写成升序），整个修复循环都在“修一个本来正确的实现”，所以后来让 Diagnoser 先独立推导期望再和测试比对。

### Q4. 评测体系是干什么的？“独立判官”“假通过”是什么？
> 回答“我改了 Agent 的某个设计，它到底变好了没有”。23 道题分 10 个难度等级，每题有手写的参考实现；评测把系统生成的程序**真的构建并运行**，逐用例比对。“独立”是指它不依赖系统自己生成的测试——否则就是自己给自己判卷。系统判通过、判官判不对，就是**假通过**，用它度量验证本身的可靠度。还有三层上限（单次/整体/随时停止）控制评测的 token 和时间，以及机制触发计数，用来看某个改动有没有在线上起作用。

### Q5. 为什么自研而不是用 LangGraph？
> LangGraph 的 checkpointer 保存的是状态数据，不是“执行”：进程死了需要有人检测、决定从哪一步重入并重启，Temporal 官方也这样区分。我需要把保证细化到“单次付费调用”这个粒度，所以先自己做出来理解它要保证什么；同时我做了 LangGraph 适配，证明这套语义能落到主流框架上。

### Q6. 路由和 LiteLLM / RouteLLM 有什么关系？
> LiteLLM 偏网关（统一接口、预算、降级），RouteLLM 偏“请求该用强模型还是弱模型”的判断。我做的是级联：先弱后强，失败才升级，并且有预算上限。我也评测了它的代价——级联在困难样例上会因为重复上下文而增加调用，所以后来把起步等级做成可配置、并按角色区分。

### Q7. 动态角色你是怎么做的，为什么这么选？
> 调研了六条路线（固定角色+条件路由、OpenAI 的 handoff、orchestrator-workers、角色即配置、运行时由 LLM 生成角色、自动搜索工作流）。我选“角色即数据 + 确定性选择 + 在已注册角色内的受限提议”：因为系统的核心是可验证、可恢复，运行时生成的角色/流程没法预先验证；本地小模型也做不好“自由生成”；而已有的声明式工作流引擎正好承接。并且用自己的评测比较“固定图 vs 允许提议”，有收益才启用。Anthropic 的建议也是：流程能写死就别上 agent。

### Q8. 你踩过的最有代表性的坑？
> ① 弹窗问题：我先给自己的子进程加了无窗口标志，用户说还弹；后来写了进程监视器实机抓，才发现是自己的演练脚本用 DETACHED_PROCESS 重启了 Ollama，无控制台的服务每次加载模型都会让子进程各弹一个窗口——教训是先复现再下结论。② 流式取消：以为设短读超时就能轮询，结果套接字超时后响应对象不能再读；改成读取线程+队列后又发现同步 close 会被读线程卡住，取消延迟从 14 秒降到毫秒级。③ Diagnoser 被测试带偏。

### Q9. 和你另一个 RAG 项目的关系？
> RAG 项目偏“知识与检索”：LangGraph、混合检索、证据引用、MCP。这个项目偏“Agent 的工程化底座”：多模型路由与成本、执行验证、评测、持久执行与流式取消。两个项目合起来覆盖从“Agent 能做什么”到“怎么让它可靠、便宜、可度量”。

## 4. 项目的特点（给自己看的定位）

- 不是“又一个 Agent 应用”，而是 **Agent 可靠性与评测工程**：执行验证、独立评测、成本路由、持久执行。
- 与主流岗位要求一一对应：多模型路由与 token 经济学、图/状态机编排、supervisor-worker、“验证而不是信任输出”的评测、可观测与韧性（见 [ROADMAP §2](ROADMAP.md)）。
- 独特之处不在单个零件，而在**闭环**：验证 + 评测 + 路由 + 持久执行放在一个小系统里，并用自己的评测证明哪些有用（见 ROADMAP §3.1）。
