## 2. 详细版（放作品集 / README / 面试讲稿）

### 一句话
一个**把“模型会犯错”当作前提**来设计的软件工程 Agent Runtime：不靠更强的模型，而靠**更强的验证、更聪明的路由和更可靠的执行**，让本地小模型完成原本做不到的任务。

### 问题与思路
- 现有编码 Agent 的两个通病：**自报完成**（模型说“测试通过了”但没跑）和**成本失控**（全程用最贵的模型）。
- 反过来想：验证是确定性的、便宜的；贵的是“推理”。所以把**最强模型只用在少而关键的地方**（规格、测试、诊断），把**大量试错交给免费的本地模型**，再用独立的证据链裁决结果。

### 架构
```
React/TS SPA ──HTTP──► Python 控制面 ─────► Go runner（受控执行、Job Object）
  任务图/代码/报告/评测     │  路由 · 预算 · 工作流引擎         go test / vet / gofmt
                           │  事件溯源账本（SQLite + 内容寻址 artifact）
              本地 Ollama ◄─┤  Worker 租约 · 自动续跑 · GPU 调度
              云端 API   ◄─┘  流式 · 真取消 · 独立判官（评测）
```

### 核心设计（每条都可以展开讲 5 分钟）
1. **Evidence Gate**：完成与否由不可变快照 + 工具账本 + 独立 Gate 决定；Gate 不依赖模型的任何自述。
2. **多模型路由**（纯函数 `route()`）：本地优先、有界升级、同级轮换、按角色起始等级、预算耗尽即停并保留证据；`route()` 是纯函数，决策表可以直接单测。
3. **预算账本**：云端 token / 活跃时间 / 费用 / 调用数；对“没有返回用量”的调用按上下文上限**预留**，不低估；结果可在报告里逐次对账。
4. **崩溃一致性**：exactly-once 角色调用；崩溃落在“请求已发出”和“结果已保存”之间时，**付费调用不重放、免费本地调用自动重试**；用真实 `kill -9` 的子进程做恢复演练，而不是 mock。
5. **失败归属与修复子图**：把验证输出解析成条目并标注归属（实现 / 测试 / 不明）；声明式 `fix-v1` 工作流（节点、边、已注册 guard、可达性校验、步数上限）；每类问题有独立的失败链，修好了自己那类的本地模型不会因另一类问题被错误升级。
6. **面向弱模型的技术栈**（每项都对应一个真实踩过的坑，见 PLAN_LOW_MODEL_QUALITY）：测试先行由强模型写；逐文件 `gofmt -e` 语法门；确定性 import 修复；提示词泄漏检查；失败证据带源码片段；账本事实驱动的尝试摘要；Diagnoser 的逐条期望核对 + 确定性改判；补丁停滞后整体重写；多样本并行验证取优。
7. **评测体系**：10 级 17 题，期望由 Python 参考实现算出，**独立判官**真的构建并运行生成的程序；报告“假通过率”（系统 Gate 通过但判官不认）、稳定等级、加权得分、每次通过的云端 token、各 runtime 机制的触发次数；三层上限（单次 / 整体 / 随时停）。
8. **资源与运维**：GPU 信号量与“一键让出显卡”；模型切换/任务结束即卸载；孤儿 `llama-server` 的发现与回收；子进程无窗口；Windows Job Object kill-on-close。

### 可以讲的“踩坑故事”（最能体现工程判断）
- **“误判了根因”**：弹出的 cmd 窗口，我先给自己的子进程都加了无窗口标志，用户反馈没好；改为写一个进程监视器实机抓，发现是自己的演练脚本用 `DETACHED_PROCESS` 重启了 Ollama，**无控制台的服务每次加载模型都会让子进程各弹一个窗口**。教训：先复现再动手。
- **“被测试带偏的诊断”**：强模型把“按金额降序”的测试写成了升序，Diagnoser 看了测试后编出理由，判成实现问题，流程把轮数全花在修一个正确的实现上。修法不是换更强的模型，而是**强制它先独立推导期望并让结论服从自己的核对**，同时发现并修了“测试源码从未送进 Diagnoser”的 bug。
- **“假通过”**：只看系统自己的 Gate 会高估能力，所以评测另有独立判官。
