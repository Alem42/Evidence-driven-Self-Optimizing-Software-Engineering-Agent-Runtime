## 1. 硬上下文拦截

### 1.1 为什么要做、为什么不能事后检测

我用真实 Ollama 实测（gemma4:12b）：

| num_ctx | prompt | 返回的 `prompt_eval_count` | `done_reason` |
|---|---|---|---|
| 2048 | ~900 字符 | 222 | stop |
| 2048 | ~5400 字符 | 1222 | stop |
| 2048 | **~18000 字符（远超窗口）** | **1027** | **stop** |
| 4096 | **~45000 字符（远超窗口）** | **2051** | **stop** |

超出窗口时 **Ollama 不报错、不告警**，静默截断到约一半窗口，而且 `prompt_eval_count` 没有可靠特征（合法的 1027 token 提示长得一模一样）。所以**只能事前拦截**，不能事后检测。

### 1.2 估算器是用真实数据拟合的

之前的“每 token 2.5 字节”是拍脑袋的。我用历史上 **57 次真实本地调用**（Ollama 返回的 `prompt_eval_count` 对输入字节）拟合：

- ASCII 约 **3.6 字符/token**；非 ASCII（中文）约 **0.54 token/字符**；
- 估算/真实比值范围 0.88–1.71，中位数 1.21（`domain/tokens.py`）。

两个估算：
- `estimate_tokens`（偏高）：路由准入、预算预留——宁可多留。
- `estimate_tokens_lower`（偏低，0.20/0.40）：硬拦截——**只有“几乎一定溢出”才拒绝**，避免误杀本来能跑的请求。

### 1.3 行为

- `ChatProvider.respond` 在发请求前，对**本地模型**（`model_type=local`）检查下界估算是否超过 `context_limit`，超过就抛 `ContextOverflow`（真实验证：0.001 秒内拒绝，没有发请求）。
- **云端模型不拦**：它们溢出时会明确报错，不会静默截断。
- 异常类型穿过各阶段的 `raise … from None` 包装（`stage_error`）。
- ladder 模式：协调器把“这个候选放不下”记为一次失败，用估算出的真实输入量重新路由，路由器自动跳过窗口不够的候选，升级或停止；固定模式没有别的候选，直接把明确的错误交给用户。

## 2. 崩溃恢复演练

`tests/test_recovery_drill.py` + `tests/drill_child.py`：**真的起一个子进程，用 TerminateProcess 硬杀（没有任何清理机会），再用全新进程恢复同一个状态目录**。跨进程用调用日志计数，断言“每个模型调用恰好发生一次”。

| 场景 | 被杀的时刻 | 恢复后的结果 |
|---|---|---|
| A 验证中途 | 本地修复已完成，第二次验证正在运行 | 不重复任何模型调用；失败链（`route_history`）与 `pending_fix` 保留；重新验证后失败 → **升级到云** → 成功。**这个场景发现了缺陷 #1** |
| B 修复调用中途 | 本地模型修复请求已发出、结果未知 | **不重放**；任务明确失败：`revision result unavailable; create an explicit retry revision` |
| C 生成调用中途 | 本地模型生成代码请求已发出、结果未知 | 已完成的规划/测试方案**不重做**；生成**不重放**；任务明确失败：`role call running: result unavailable` |

### 缺陷 #1 的修复

被杀时正在验证的 run，恢复后被引擎保守地标为 `needs_attention`（`uncertain_tool_state`，不重放工具）。这是对的，但协调器把它当“验证失败”去修复，于是报 `repair requires a failed … verification`。现在：检查工具在隔离副本里运行、结果幂等，所以协调器对同一份已发布快照**新建一个验证 run**（与手动“重新验证”相同，`ProjectGeneration.reverify`），最多两次；其它原因的 `needs_attention` 则停下并写明。

### 这个演练说明了什么、没说明什么

- 说明：已完成的工作不会丢、不会重复；未知结果的请求**不会被悄悄重放**；路由与预算状态跨崩溃保留。
- **没有说明“崩溃后自动续跑到成功”**：场景 B/C 里任务是**明确失败**，需要人处理。对**免费的本地调用**这太保守——见 §7 的 M1 项（幂等分级）。

## 3. 真实本地→云升级验证（GLM → DeepSeek）

候选：GLM-4.7-flash（L1 本地）+ DeepSeek（L2），预算 API token 120k，任务“区间归并”。

**第一次（修复前）**：Planner 在 GLM 上被契约拒绝两次 → **升级到 DeepSeek 重新规划** ✓（真实升级发生了）；生成仍从本地开始 ✓；随后暴露缺陷 #2（澄清 + 重规划）、#3（修复轮次被挤占）、#4（准入过严，修复一上来就用 API）。
**修复后**：见 §3.1。

### 3.1 修复后的运行（真实）

任务同上；12 次模型调用、201 秒、**本地 30,340 token、API 14,413 token**（预算 120,000，未触及）。升级 2 次：

| 链 | 角色 | 用的模型 | 原因 |
|---|---|---|---|
| 规划 | Planner | GLM（L1） | 从最低等级开始；Tester 也在本地完成 |
| 生成 | Developer | GLM（L1） | 从最低等级开始，响应被校验拒绝 |
| 生成 | Developer | GLM（L1） | **同级再试（带原因自修）**，仍被拒绝 |
| 生成 | Developer | DeepSeek（L2） | **升级**（本地用完 2 次尝试） |
| 修复 | 修复 | GLM（L1） | 从最低等级开始（**修复前这里一上来就用 API**） |
| 修复 | 测试修订 | DeepSeek（L2） | **升级**（本地修复后验证仍失败） |

最终结果仍是**未通过**：同一条断言连续失败三次，规则停下并交给人（规格/测试期望可能有矛盾）。这是模型质量问题，不是自动化流程问题——与你说的“质量问题先搁置”一致。要点是：**升级阶梯、预算、停止规则、解释都按设计工作**，且没有浪费预算。

对比修复前的同一任务：规划重试占掉了修复轮次，修复阶段本地被误判放不下直接用 API，且澄清后重规划直接报错。

### 3.2 决策可解释性

升级决策现在带 `detail`，例如 `跳过：glm-4.7-flash（输入放不进它的上下文窗口）`，报告里与原因一起展示。之前看起来像“凭空升级”。

## 4. 设计取舍与已知限制

1. **硬拦截只覆盖本地模型**，且用下界估算，所以“几乎一定溢出”之外的临界输入仍会发给服务端（可能被截断）。更准的办法是用服务端分词（Ollama 新版本可能提供），或用历史 `prompt_eval_count` 在线校准——列入后续。
2. **准入只为“预期输出”预留 4096 token**（`CONTEXT_OUTPUT_RESERVE`），不是整个 `max_output`；预算预留仍按完整 `max_output`（保守）。这是一个调参结论，不是理论值。
3. 恢复演练用**假模型 + 假执行器**（确定性）；真实模型的崩溃行为（比如 Ollama 在被杀后仍在占用显存）没有演练。
4. 演练里被杀的是协调器所在的整个进程；**API 与 Worker 分离**之后的崩溃语义（租约过期、接管）是 M1。
5. 场景 B/C 说明：**免费本地调用**结果未知时仍需人工处理——M1 的“幂等分级”要解决。
