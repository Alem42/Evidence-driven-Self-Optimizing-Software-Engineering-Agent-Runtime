# 进展011：M1 后半 · 失败归属、Diagnoser、声明式修复子图、无进展拒收、持续自动修复

2026-10-04。分支 `feature/multi-model`。前置：[进展010](PROGRESS_2026-10-04_002_m05-complete-and-m1-first-half.md)。

## 0. 起因：任务 c903b2b7（CSV 费用汇总命令行）暴露的问题

| 用户观察 | 真实原因（从日志与账本核实） |
|---|---|
| 系统无法自行修复到可用 | **主要是 agent loop 的问题**，其次才是模型质量。分类器把“测试有 import cycle”和“实现有语法错误”同时出现时全部归为“修订测试”，连续 4 轮；实现里 `processor.go:47` 的语法错误**从未被修** |
| 用户不知道该修实现还是改冻结测试 | 界面只给两个按钮，没有说明归属。现在系统先给出归属分析，并提供“自动修复（推荐）” |
| 修订测试后仍失败也没有升级模型 | 修订被模型“空改”（`changed=[]`）后照样去验证；并且自动流程固定一个模型、没有 router。“失败”被笼统计数，部分修复也算失败 |
| 升级到 API 应释放本地模型，再回本地要再加载 | `_pick` 切换时之前没有释放。现在切换/任务结束/手动任务结束都释放（`router.release`、`Console._release_local_models`） |
| 自动失败后继续要一步步人工批准 | 新增“从这次失败继续自动修复”（`POST /api/runs/<rid>/auto-fix`），跳过规划与生成，失败历史从版本链重建 |

## 1. 做了什么

1. **失败归属分析**（`application/ownership.py`）：把验证输出拆成条目，每条标注 实现/测试/不明 × 编译/准备/断言/格式。实现编译/语法错误先修；每个归属有**自己的失败链**（`fix:implementation` / `fix:test` / `fix:ambiguous`），只有“该类问题仍在”才算该等级失败，所以本地模型修好了自己那一类不会因另一类仍在而被升级。
2. **声明式工作流引擎**（`application/flow.py` + `workflows.py`）：失败后的子图 `fix-v1` 是**数据**（节点、边、已注册的 guard），引擎负责校验（入口、可达、兜底边、guard 存在）和有界执行（最多 12 步）。每一步写 `workflow_node` 事件。**绞杀式**：规划/生成仍是 go-cli-v1，只替换最乱的“失败后做什么”。可通过 `GET /api/workflows/fix-v1` 读取。
3. **Diagnoser 角色**：永远用最高等级，只读，输出归属（实现/测试/两者/规格/不明）+ 具体指示；规格/不明 → 停下交给人。诊断失败不致命（`diagnosis_failed`，按规则继续）。
4. **无进展拒收**：修订没有任何改动 → 不去验证，走 图中的 `noop_diagnose → noop_retry（路由器换更强模型）→ halt`。
5. **持续自动修复**：`Console.auto_fix`；前端失败卡有主按钮“自动修复（推荐）”，手动选择折叠。本地+云端都启用时默认走 ladder。
6. **显存卫生**：切换到云端/另一个模型时释放其它本地模型；任务结束（含异常）释放；手动任务结束释放；`keep_alive=120s` 兜底。

## 3. 真实模拟（本地 GLM → DeepSeek，ladder，云端上限 150k token）

任务：“实现 CSV 费用汇总命令行：按类别求和并按金额降序输出。”，本地 glm-4.7-flash，云端 deepseek-flash / deepseek-v4-pro，ladder。

**第一次运行发现一个真实缺陷**：DeepSeek 返回被截断的 JSON（`model action JSON invalid`），`llm.py` 只抛错而没有标记“响应已收到”，协调器据此当作传输失败直接中止，**没有带原因重试也没有升级**。已修复（标记 `contract_diagnostic`），并加回归测试（修复前确认失败）。

**第二次运行（修复后）**，15 次调用、云端 36k token：
- 升级链：`glm-4.7-flash(L1) → deepseek-flash(L2) → deepseek-v4-pro(L3)`；`deepseek-flash` 一次返回无效 JSON 后带原因升级，而不是中止。
- 修复链全程是 `fix:implementation`；3 次修复仍失败后，**Diagnoser（v4-pro）**给出“实现里 writeCSV/writeCurrency 重复定义”，随后图走 `diagnose → repair`。
- 释放：`models_released`（`reason: switching`）在切到云端时触发；结束后 Ollama `/api/ps` 为空、显存 1.2 GB、无孤儿 `llama-server`。
- 终局：达到自动修复上限，结果仍为“失败”——**这是模型质量问题，不是流程问题**（强模型 5 轮也没修好这个任务）。

**继续自动修复**（`Console.auto_fix`，对第二次的失败版本）：
- 失败历史从版本链重建，路由器直接在 L3 起步，没有重走 GLM。
- 出现一次 `noop_revision`（无改动拒收）→ 再次 Diagnoser（结论“解析没跳过表头”）→ 再修复。
- 修复归属变化时，`fix:test` 链按**独立链**从 L1 起步再升级（设计如此：测试的失败记录与实现分开），代价是多一次本地调用。
- 结束同样释放本地模型，显存干净。

结论：用户的几个痛点在流程层面均已解决（归属可见、自动升级、无空挂模型、失败后一键继续）；剩下的失败来自模型本身，需要更强的测试/实现生成或更细的 Diagnoser 指令，见 §4。

## 4. 后续优化（未做）

- **继续修复时的测试链起点**：`fix:test` 从 L1 起步浪费一次本地调用；可按“同一任务已在更高等级失败过”直接抬高起点。
- **Diagnoser 指示的落实检查**：现在只作为提示传给修复者，没有验证修复者是否照做。
- **强模型 5 轮仍失败**时，应提示“需求/测试可能本身有问题”并建议人工审阅冻结测试。

- Worker 租约/命令表与进程崩溃后自动续跑；httpx 流式与真取消（M2）。
- 报告页显示修复子图轨迹（`workflow_node`）与诊断；设置页用 GraphView 画 `fix-v1`。
- 历史播种按归属细化；Diagnoser 结论的准确率统计。
- 规划/生成阶段也迁入声明式图，最终取代 go-cli-v1。
