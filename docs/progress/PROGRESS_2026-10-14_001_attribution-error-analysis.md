# PROGRESS 2026-10-14 · 001 — 一次“最长公共子序列”运行的归因错误分析
# Attribution-error analysis of one "longest common subsequence" run

**这份文档回答**：这次运行具体卡在哪、哪些 token 是白花的、是不是归因错了、怎么发现、怎么避免重复。每个数字都来自账本，复算脚本：[`scripts/eval/task_ledger_report.py`](../../scripts/eval/task_ledger_report.py)（逐调用报告）与 [`scripts/eval/replay_signals.py`](../../scripts/eval/replay_signals.py)（信号回放）。
**样本说明**：下面是**一次运行**的细查，加上 `ab2` 评测账本里同类事件的对照；n 很小，信号的“可靠度”只作方向，后面会逐条标出。
**方案与路线图**见 [design/ATTRIBUTION_AND_COST.md](../design/ATTRIBUTION_AND_COST.md) 与 [ROADMAP §9](../ROADMAP.md)。

## 0. 结论（先看这里）

1. **分析 Agent 的核心判断成立**：24 次模型调用里，约 **73% 的输入 token（14 次工人调用）花在“反复修一个本来就正确的实现”上**（我复算 70.0k / 96.0k）。
2. **根因链比“Tester 算错 + Diagnoser 判错”更长**：源头是 **Planner 写的验收条款缺了数值**（第 2 条只写到“……最长公共子序列长度 ”就结束了），Tester 只好自己猜；之后三个独立环节（Tester、Diagnoser、断言期望本身）互相锚定。
3. **有一个分析 Agent 没提到的更严重后果**：第三个错测试（`"abc   \ndef   \n"` 期望 0，真值是 3）把**实现带歪了两次**：首版（glm 看着测试写）用了 `bytes.TrimSpace`；Flash 工人重写时去掉了它，这条测试变成失败（实际 3、期望 0），它又用 `strings.TrimRight(a, " \t\r")` 加了回去，失败数 3→2，被当作“进步”交出。最终 Gate 通过，但**交付的程序对“带尾部空格”的输入是错的**（我真实运行确认：输出 0，应为 3）——一次**假通过**。错测试被留下来，是因为最后只修订了失败的两条，第三条早被被污染的实现“满足”了，没有任何失败去提醒它。
4. **Flash 工人其实发现了矛盾**（它的 `note` 里写着“Test arithmetic wrong … LCS=6”），但**系统没有任何通道接收这种申诉**；它的 `note` 只回到它自己的下一步上下文里。
5. **发现归因错误不需要更聪明的模型，需要更好的信号**。最便宜、最可靠的是“**实际值稳定**”：改了代码，失败断言的实际输出却一点没变（这次一直是 2 和 6）。它免费、确定性、在本次运行里**第 4 次工人调用时**就能触发，而不是第 23 次。
6. **单个裁判也不够**：我用真实 Flash×3 回放了断言裁判，它对 `"a b c"` 判对了（2/3 票），对 `"abcabcabc"` 的 6 对 5 **3 票全错**（LCS 的心算对 LLM 就是难）。所以**证据要叠加**（审计 + 实际值稳定 + 裁判），而不是押一个。
7. **“失败次数 4→2”“增加本地尝试”都治标不治本**，原因见 §6。真正有效的是三件小事：**开审计、让“实际值稳定”触发仲裁、把失败测试的源码放进修复上下文**，按账本回放估计，这次运行能从 96k 降到约 55k（只做 S1）或 25–40k（再加审计）——**都是投影，不是重跑**，见 §7。

## 4. 这是归因错误吗？是，而且是**系统性的**，不是偶然

两层：
- **模型层**：Diagnoser（Pro）看到了“实际 2、期望 1”，仍判实现错。我们自己的测量早已给出原因：**“这个期望对吗”这类问法被声明的值锚定，召回只有 26–33%**；而“盲推导再比较”召回 91%（[TEST_RELIABILITY](../reference/TEST_RELIABILITY.md)）。
- **机制层**：系统里**已经有**正确的组件——`test_audit`（盲推导审计）、`assertion_referee`（A/B 盲选），都是**默认关**的；默认路径上第一道“仲裁”恰恰是锚定型的 Diagnoser。**我们对这个问题的测量结论没有进入默认流程。**

同类事件不是第一次（`ab2` 账本与旧记录里都有）：

| 任务 | 错在哪 | 出处 |
|---|---|---|
| 本次 LCS | 三个期望算错（1/5/0） | 主账本 |
| grades（ab2 r1/r5） | `89*7+92` 写成 91.125；`91,91,92` 平均写成 91.13（真值 91.33） | PROGRESS_2026-10-13_004 #15/#16 |
| wc（ab1 v1y） | 示例对真实程序只通过 5/7，判官却通过 | PROGRESS_2026-10-13_003 §3 |
| 旧记录 | “强模型把期望算错（20 写成 19、降序写成升序），Diagnoser 被测试带偏” | memory：recurring-failure-patterns |
| `test_audit` 配对评测里的 lcs ×3 | 关：gate_fail ¥0.67 / stopped ¥1.15 / gate_fail ¥0.55；开：pass ¥0.09 / pass ¥0.08 / gate_fail ¥0.39 | TEST_RELIABILITY §配对评测 |

对照一次**归因正确**的运行：同一天的 csv_sum（Python）：1 次 Diagnoser + 3 次 Flash 工人，¥0.05，3 次调用修好 `__main__.py` 的真实 bug。**归因对了，系统本身很便宜。**

## 5. 怎么发现归因错误（信号表）

“信号”= 一个便宜、尽量确定性的证据，说明“再改实现不会有用”。

| # | 信号 | 成本 | 在本次运行里何时触发 | 可靠度（本次实测） |
|---|---|---|---|---|
| S1 | **实际值稳定**：同一条断言的实际值，在 3 次连续观察里相同，且其间代码改过 ≥2 次 | 0（解析已有输出） | 第 **4** 次工人调用（共 14 次工人调用） | 回放 10 个有工人修复的任务：触发 3 个，其中 2 个之后确实修订了测试，1 个是真·实现卡死（bank）；没有误伤“好”的 csv_sum；没触发却修订了测试的有 2 个（召回 2/4） |
| S2 | **多实现一致**：不同模型写的多版实现输出同一个值，而期望只有一个 | 0（同上，跨版本比较） | 与 S1 同时（glm、Flash×3、Pro 都输出 2/6） | 是 S1 的“跨模型”加强版：CodeT 的“双重执行一致”思想 |
| S3 | **盲推导审计**（Flash×3，只看输入） | ¥0.002（4 307 prompt + 779 completion token） | **开跑前**，写任何实现之前 | 真实回放 2 次：第 1 次抓到 3/3 个错用例 + 1 个误报；第 2 次抓到 2/3 + 1 个误报。**有随机性**，所以不能单独依赖 |
| S4 | **断言裁判**（A/B 盲选 ×3） | ¥0.003 | 第一次验证失败时 | 真实回放：`2 vs 1` 判对（2/3）；`6 vs 5` **3/3 票全错**；退出码那条判对。单次 80%、三次多数 88% 的历史数字成立，但**遇到“要心算的值”会成片出错** |
| S5 | **工人自己的申诉**（note 里“测试错了”） | 0 | 第 4 次工人调用（Flash 的 note） | 本次是对的；但弱模型的 note 不可全信，所以只能当**触发仲裁**的线索，不能直接改测试 |
| S6 | **通过后的验收一致性检查**（Flash 读验收+最终代码，找“验收没写的行为”） | ≈¥0.003 | 通过之后 | 本次若有，会指出 `TrimRight` 与“可含空格”冲突；**未实测**，是设计 |

**本地模型能当独立投票者吗**（我现场测了一次，n=1 个任务、3 个错用例，只作方向）：

| 本地模型 | 用时 | 抓到的错用例 | 误报 |
|---|---|---|---|
| gemma4:12b | 74 s | 2/3 | 0 |
| qwen3.5:9b | 19 s | 2/3 | 2 |
| glm-4.7-flash | 37 s | 0/3 | 0 |
| （对照）Flash×3 | 6.7 s，¥0.002 | 3/3 与 2/3（两次） | 1 |

含义：**glm 不适合做审计**；gemma4/qwen 有些信号但还不能替代 Flash。要不要把本地模型加进投票，需要在 184 条审计数据集上免费跑一轮再决定（路线图 H8）。

## 6. 怎么避免无意义的重复

**原则：重复的预算按“信号”而不是按“次数”分配。** 每一次重复前问一句：“上一次的失败和这一次有什么不同？”如果实际值没变，重复就是浪费。

| 现状（本次） | 为什么浪费 | 改法 |
|---|---|---|
| Flash 工人 5 步里 3 次重写同一个文件，实际值一直 2/6 | 没有“值没变”的刹车（我的 `unchanged` 提示在修复模式里被关掉了，只在生成模式有） | S1 触发 → 停工人，进入仲裁（§7 H2） |
| 升级到 Pro 后**范围放大到 `cmd/app`**（`widened: true`，因为是第 2 次修复） | 证据只指向 `internal/lcs`，放大没有依据；换了模型缓存也清零（#14–16 命中 0%） | 放大范围要有证据（失败路径涉及的包），不是“第 2 次就放大” |
| 三轮 Pro 修复各 2–4 步，各自 stuck、原样返回 | “没有改动”被当成“模型不愿改实现”，要攒够 3 次 noop 才改测试 | stuck 且 S1 触发 = **立刻**仲裁；不再攒 noop |
| `read_file 失败的测试`（4 次修复里 3 次，各占一步） | 失败的测试源码本来就该在上下文里 | 修复上下文直接带失败测试函数的源码（H3） |
| Diagnoser #1 因 `requirement_says` 超 300 字符被整条拒绝 | 校验过严；同类问题之前修过一次（reason 只截断不拒绝） | 截断而不是拒绝（H4） |
| “best state = 失败最少”把被错测试污染的实现当成进步 | 失败数不能区分“修好了”与“迎合错误测试” | 改动要有来源：S1/S3 标记为可疑的断言不计入“进步”；通过后做 S6 |

**为什么“把失败次数 4→2”不够**：这次两批工人共 14 次调用，其中真正的“失败次数”只是协调器的 `noop` 计数。把上限砍一半，只是把浪费从 14 次变 8 次，而且会误伤真正需要多试几次才能修好的实现缺陷（csv_sum 那类 3 次调用修好的是少数，大项目里更常见需要多轮）。**换成按信号停**，既更早（第 4 次调用）也更准。

**为什么“增加本地尝试”不行**：本地 glm 当修复工人是我们 7 次实测里卡住的那一个（PROGRESS_2026-10-13_004 §4）；本地尝试多一次只增加墙钟时间，不减少云端调用。

## 9. 数据补充：编辑 vs 重写，到底花在哪

`ab2` 全部轮次（1 160 次工人调用，含修复前的早期版本）：

| 工具 | 次数 | 平均输出 token | 平均输入 token |
|---|---|---|---|
| write_file | 383 | 804 | 4 934 |
| edit_file | 140 | **149** | 6 518 |
| read_file | 323 | 17 | 5 230 |
| run_check | 201 | 10 | 4 969 |
| note | 67 | 215 | 6 188 |
| finish | 46 | 6 | 3 819 |

- **每次调用的成本被输入主导**（≈5k 输入 vs ≤0.8k 输出，输出单价约为输入的 4 倍，折算后 write ≈ 8 150、edit ≈ 7 114 个“输入单位”，差 13%）。所以“少重写”**省的是风险（误改别处、回归）而不是钱**。
- **非生产性步骤占大头**：read_file + note + finish 合计占工人输入 token 的 **38%**（read 单项 27.8%）。很多读取是在读自己的文件或重复读，被“读了也没用”的拒绝回应（后期已加）；**修复上下文里直接放失败测试的源码**能去掉其中最稳定的一类。
