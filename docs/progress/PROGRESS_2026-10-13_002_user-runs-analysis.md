# 两次真实运行的复盘：为什么“大写转换”和 FizzBuzz 要折腾那么多轮

2026-10-13。数据来自主状态库（`.masa`）里 01:33–01:42 的两次任务，逐条对过账本事件与 Ollama 的 `server.log`。**先说结论：这两次失败都不是“Tester 写得差”或“Planner 不够强”，而是四个不同层面的小问题叠加；其中最耗时的一个是基础设施问题，已经修了。**

## 任务一：大写转换（Python，用时 3 分 36 秒，花费约 ¥0.011，账本里 10 个 run、17 次模型调用）
模型分工：规划与 Tester、测试文件的作者 = deepseek-flash；实现 = 本地 glm-4.7-flash；Diagnoser、第二次修复 = deepseek-flash。

| 时间 | 发生了什么 | 原因 |
|---|---|---|
| 01:33:50 | Planner、Tester 正常；本地“预检复核”（triage）调用失败 | 见下面的①；预检只是建议，不影响流程 |
| 01:34–01:36 | **生成阶段连续失败 4 次**：每次都是“测试文件由 flash 写成功 → 本地 glm 写实现时 `model transport failure: no response received`”，每次整个生成从头再来（测试文件被重写 4 遍） | ①②③，全是基础设施 |
| 01:36:38 | 第 5 次终于成功（glm 的冷加载 11 秒 + 预填充 12 秒，没超过 30 秒） | |
| 01:37:06 | 验证失败：1 条测试断言 `test_no_final_newline`（输入 `hello` 没有结尾换行，测试期望 `HELLO\n`，实现输出 `HELLO`） | ④ 规格里的矛盾 |
| 01:37 | Diagnoser（flash，一次调用）判定“测试对、实现错”；本地 glm 修复返回原样（61 个 token，没有改动）→ 路由升级到 flash → 修复通过验证 | 流程按设计工作 |

**①②③ 为什么连续失败 4 次（有证据）**
- 本机的 glm-4.7-flash 有 17.9 GB，显卡 16 GB，Ollama 必须把一部分放进内存，冷加载要 15–35 秒。
- Ollama 在**模型加载完之前不会发响应头**。我们的 HTTP 客户端“连接阶段”的时限写死 30 秒（`llm.py`），而本地模型明明允许 900 秒的首字等待。Ollama 日志：`499 … 30.9s “client connection closed before llama-server finished loading, aborting load”`，其余几次是 `500 … 30.0017s`——全都精确地停在 30 秒。
- 每次失败后日志里紧跟一条 4.5 毫秒的 `/api/generate`（卸载模型）。原因是路由器“切换模型就释放本地模型”的规则：一个生成阶段里，**云端先写测试、本地再写实现**，每次切到云端都把 glm 卸载，切回来就是一次冷加载——所以第 2 个文件调用**每次**都是冷启动，每次都赌 30 秒。
- 失败之后的重试逻辑是“服务器暂时不可达就等它恢复再重试”，策略默认允许 6 次。但这里服务器完全可达，只是在加载，于是**用同样的条件原样重复**，直到某一次碰巧快一点。

**修了什么（已提交 `e255533`）**
1. 本地模型的连接阶段时限改为首字时限（900 秒）；云端仍是 30 秒。真实冷调用验证：加载 16.0 秒，整个调用 20.9 秒，成功。
2. 同一阶段里本地模型马上还要用，切到云端写测试时**不再卸载**它（任务结束、换成别的本地模型、等人时仍然释放）。
3. 本地服务器探测可达、同一请求却连续两次没有响应：**记一次失败让路由器升级到下一个候选**，不再原地重复 6 次（服务器真的不可达时仍按原样等待）。
4. 有测试：连接时限、重试升级。

**④ 真正的质量问题：规格里的矛盾**
- Planner 的 `summary` 写“**保留行尾换行符，原样输出**”，验收第 5 条写“最后一行没有结尾换行符时，仍然作为一行处理并输出”。后者没说输出要不要补换行。
- Tester 按验收条款推出 `HELLO\n`；实现者 glm 按 summary 写成了 `HELLO`。两个都有道理，规格没有钉死。
- 这正是 Planner 提示词里“把边界语义钉成具体的验收项”要避免的事，但它没有做到，也没有机制发现 summary 与验收互相矛盾。
- 流程处理得对：1 次验证失败 + 1 次诊断 + 2 次修复，约 30 秒、不到 ¥0.006。

## 任务二：FizzBuzz（Python，用时 1 分 13 秒，账本里 6 个 run、8 次模型调用）
模型分工：这次你选的是 glm + Pro，Planner、Tester、测试作者 = deepseek-v4-pro，实现与修复 = glm。

| 事件 | 原因 |
|---|---|
| **第一次方案失败**：`provide 1..16 concrete test cases` | Tester 的回答被校验拒绝。账本里这次失败的原始回答没有保存（只有 598 个输出 token），但这个错误只会在某个检查的 `cases` 数组长度不在 1..16 时出现——最常见的就是对静态检查写了 `"cases": []`（提示词写明要省略，模型常常不听）。模拟用户测试里 5 次规划有 3 次也撞上同类错误。 |
| 重试只重做 Tester（规格复用），第二次通过 | 机制正常 |
| **工具验证失败**：整个测试模块 `ImportError: cannot import name 'run' from partially initialized module … (most likely due to a circular import)` | 本地 glm 写的 `fizzbuzzcli/app/app.py` **第一行是 `from fizzbuzzcli.app.app import run`——从自己导入自己**。测试模块一导入就失败，所以只跑了 1 个测试就整体报错。这是弱模型的低级错误。 |
| 本地 glm 修复一次就改对，第二轮验证通过 | 修复链正常 |

**修了什么**：①空的 `cases` 数组现在在校验前直接丢掉（不再为一个没有信息的空数组整次拒绝、再付一次费）；②Python 包新增确定性检查“文件导入自己”（在生成当下就地重写，不用等整轮验证）。

## 你的几个问题
**Tester 写得不好吗？需要先改 Tester 还是 Developer？**
这两次都不是。任务一的 Tester 用例与验收条款一致（Diagnoser 也这么判），问题是规格本身含糊、实现者读到了另一句话；任务二的失败，一个是 Tester 的输出格式（空数组），一个是实现者的低级错误。流程里“谁错了”已经由 Diagnoser 判：它是最高等级模型、只在断言失败时被叫一次，任务一里这一次判断约 ¥0.003。

**需要一个高级“管理员”在测试失败时判断改 Tester 还是 Developer 吗？吃 token 吗？**
已经有了，就是这个 Diagnoser（只回答“谁错：实现 / 测试 / 规格”）。它便宜（这次实测：输入 1892、输出 379 token）。真正贵的不是“判断”，而是**判断错之后的重新生成**，以及**基础设施问题导致的整阶段重做**（任务一里 4 次，占了总时间的一半以上）。再加一层“每一步都问管理员下一步去哪”的大模型，我们之前测过（指挥者，3/7 通过 vs 规则 6/7，费用高 24%–96%），结果更差。结论：**判断环节用窄问题的裁判（现在的 Diagnoser）+ 确定性规则，不要让大模型自由决定走向。**

**Planner 不应该由最高级模型写吗？**
任务二就是 Pro 写的，任务一是 Flash（因为那次你的模型选择里没有 Pro）；两次的规格质量并没有因此不同：任务二的规格没问题，任务一的矛盾 Pro 也未必能避免——它是“写完没有人核对”的问题，不是“能力不够”。更值得做的是**让 Planner 额外产出具体示例（输入→输出）作为唯一的期望来源**（V2 设计里就是这样），让含糊的地方在最上游被迫写成具体的例子。

**Planner–执行的架构是不是不适合写代码？**
对**多文件、多包**项目它有价值（10 文件 bank 的失败正是规划自相矛盾放大的结果，所以才加了规划约束）；对**一个函数就能解决的小任务**它是纯开销：这个“大写转换”任务无故拆成 6 个计划文件（pyproject、两个 `__init__`、入口、app、测试），产生 10 个 run、17 次调用，而理想路径是 3–5 次。**小任务应该走“一个工人 + 工具”的快路径**：规划（可以是便宜模型）→ 工人写代码和测试、跑真实检查、读错误、改 → 完成。V2 的“小任务合成一个包”就是这条路径的雏形（之前在 Python 的 4 个小任务上，V2 每个 20–34 秒、¥0.027–0.063，均在第一轮验证通过——但样本很小、没有与 V1 同条件对照，不能当作结论）。

**要不要重新引入简单的多角色，或者一个一直审查图走向的管理员？要不要加工具？**
我的建议是**三个角色，不是更多**：
1. **Planner**（一次，最高等级）：规格 + 具体示例；
2. **Worker**（循环，本地/Flash）：自己写代码与测试，用工具（写文件、跑真实检查、读错误）迭代，直到通过或卡住；
3. **Referee**（只在“同一个断言反复失败”或“测试与实现互相矛盾”时叫一次）：就是现在的 Diagnoser/断言裁判。
走向由**确定性规则**决定（检查通过→完成；卡住→换更强的模型；预算到→停），不是由一个大模型每步审图。这正是 V2 在做的方向，这次又补了依赖顺序和卡住检测。

**我担心的：项目把简单问题复杂化了**——数据支持这个担心：**复杂度主要伤害简单任务**（固定开销：规划 + Tester + 逐文件生成 + 预检 + 诊断）。建议的改动不是“再加角色”，而是“**按任务大小选路径**”：小任务走 V2 solo（已实现，未对照评测），大任务按包推进。

## V2 这次补的两项
- **依赖顺序**：按规格里每个文件“用途”提到的别的包（包名/文件名出现在用途里）推断依赖，叶子先写、入口最后；这是启发式不是证明，推错了也不致命：
- **推迟**：一个包的真实检查因为“依赖的文件还没写”失败（如 `No module named 'calc.parser.parser'`）时，工人被推迟到那个包之后（每个包最多一次），已写的文件保留；账本事件 `package_order` / `package_deferred`。
- **卡住检测**：同一个失败签名（去掉行号与数字）连续 3 次，或连续 4 个被拒绝/无意义的动作 → 提前判定卡住（不烧完 16 步），第 2 次重复时先在结果里警告“换个思路”；卡住后生成阶段失败，路由器升级到更强的模型，**上一次已封包的包直接沿用，卡住的包带着写了一半的文件由更强的模型接着做**（账本 `worker_stuck` / `package_reused`）。
- 以上都有零 token 测试（14 个 V2 测试，覆盖顺序、推迟、卡住、复用）；**还没有用真实模型做多包任务的验证**。

## 还没解决的（诚实）
- 规格矛盾（summary 与验收冲突）没有机制发现。可行的便宜办法：让 Planner 的 summary 只写设计理由、不写规则，规则只出现在验收与示例里（提示词改动，需要评测验证）。
- 本地预检复核（triage）依赖本地模型，冷加载失败时只是静默跳过；它的价值没有被测量过。
- V2 与 V1 在“同一批小任务、同一预算”下的对照还没做；在做之前不应把 V2 设为默认。
