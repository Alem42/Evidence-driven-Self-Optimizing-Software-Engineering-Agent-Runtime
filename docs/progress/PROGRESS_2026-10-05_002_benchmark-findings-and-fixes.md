## 2. 混合 vs 纯云端：真实对比（同一提交 a1cb09a，标准套餐 14 题 ×1）

| | 纯云端 flash→pro | 混合（本地 glm 起步→flash→pro） |
|---|---|---|
| 通过 | 11/14（79%） | 8/14（57%） |
| 假通过 | 0 | 1 |
| 云端 token/次 | 34.6k | 32.7k |
| 耗时/次 | 65 秒 | 114 秒 |
| 稳定等级 | L5 | L4 |

更早的两次（不同提交）：纯云端 12/13（92%）；混合 19/28（68%，含 4 次假通过）。**样本量 1 次/任务，噪声大**，用范围看。

**结论（诚实）**：在这套任务上，**本地起步的混合模式目前没有比纯云端更好**——通过率更低、慢约 1.75 倍，云端 token 基本持平（只少约 5%）。本地承担了约 1/3 的 token，但没换来云端成本下降，因为本地失败后的修复轮次又把云端拉了进来，而强模型一次生成的成本本来就低。所以简历里原先的占位说法“云端 token 降低 62%”**不成立**，已删除。要让这个价值主张成立，需要 W3（本地多样本取优，用免费算力换质量）、W4（逐函数生成）等，**做出来并测到之前不要写**。

## 3. 评测抓到并修复的缺陷（这就是评测的价值）

1. **假通过 ×4：程序入口 `main.go` 从来没被执行过。** 系统的测试只覆盖内部包，入口的接线错误能一路通过 `go test/vet`：`wc` 的 main 用 `io.ReadFull(os.Stdin, input)` 往 nil 切片里读（永远 0 字节，输出 `0 0 0`）；`lru` 的 main 只读了第一行、容量写死成 1。→ `entrypoint.py`：main.go 里不许读 stdin/解析输入，违规带模板就地重写；提示词要求薄 main + `Run(args, stdin, stdout, stderr)`。**修复阶段只拦新引入的违规**——第一版规则误伤了修复（原有问题把整个修复卡死，lcs 失败一次），已改并加测试。
2. **Tester 重试和第一次一模一样。** 规划阶段重试 Tester 时没带上次被拒绝的原因（只有 Planner 重试带），同样的输出会连续被拒三次（hello 两次、csv_sum、bigint 失败）。→ 重试带上具体原因和契约要求；回归测试修复前会失败。重跑里 hello 2/2、csv_sum 2/2 通过；但 Tester 仍偶有无效输出（`invalid test case expected` 等），**仍是已知的剩余问题**。
3. 云端输出被截断不重试（见 §1）。
4. 修复实现的模型反复改冻结测试 → 整任务失败（进展015）。
5. `hello` 的退出码被当成要输出的文字（进展015）。
6. 评测失败账本被清掉 → 现在保留最近 3 份。

## 4. 仍然存在的问题（诚实列出）

- **混合模式质量**：本地起步仍落后于纯云端（§2）。
- **Tester 偶发无效输出**（规划阶段失败，占 ~5–10% 的运行）：重试已带原因，但未根治。
- **maze（L6）两种模式都过不去**；**coins** 在纯云端有一次死于“生成的 Go 文件不能解析”（语法门兜底在云端整包模式下重试耗尽）；**L9（regex、sudoku）都没过**。
- **Evidence Gate 的更彻底方案**未做：让 Gate 自己把构建出的程序用 Tester 的 CLI 用例真的跑一遍，需要 Tester 给出精确期望 stdout（现在是自由文本）→ M3，与追溯矩阵一起（PLAN_LOW_MODEL_QUALITY #15、#16）。
