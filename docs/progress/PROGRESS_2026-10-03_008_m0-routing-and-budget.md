# 进展008：M0 任务级预算与模型路由（本地优先，有界升级）

2026-10-03。分支 `feature/multi-model`。方案见 [PLAN_MULTI_MODEL_RUNTIME](../PLAN_MULTI_MODEL_RUNTIME.md)，使用方法见 [USER_ROUTING_AND_BUDGET](../guides/USER_ROUTING_AND_BUDGET.md)。

## 0. 先说结论

M0 的目标是让“大部分工作由本地模型完成，疑难才升级到 API，并且花多少钱/多少时间有上限”**可运行、可审计**。做到了，但有一项关键验证被我主动放弃（见 §6）：

- 已有：任务级预算、路由策略、修复阶梯、上下文准入、本地权重摘要校验、路由与预算的报告展示、新建任务时的策略选择。
- 保持不变：**固定模型模式**（默认）的行为与此前完全一致，原有 191 项测试一项没改就全部通过。
- 已验证：离线测试 210 项通过（含“本地修复失败 → 升级到 API → 成功”的确定性集成场景）；真实 DeepSeek 跑通 ladder 全链路（快照、路由事件、预算花费与报告一致）。
- **没验证**：真实“本地小模型失败 → 真实升级到 API”的端到端。你需要显卡，我停掉了正在跑的本地模型并卸载了它，这一项只靠假模型的确定性测试覆盖。

## 1. 设计：把策略和执行分开

```
Coordinator（流程）──每次要调用模型前──► Router.decide(role, chain, history, spend, need)
                                              │
                                              ▼
                              routing.route()   ← 纯函数：无网络、无存储、无副作用
                                              │
                      Decision{use|stop, candidate, level, reason, escalated}
```

- `application/routing.py`：**纯函数**。候选、策略、预算、`route()`、`spend_from_report()`、token 估算。可以单测，结果可复现。
- `application/router.py`：把纯函数接到存储、提供方和事件上；负责冻结快照、恢复、权重摘要、记录决策。
- `application/coordinator.py`：每个调用模型的位置都改为“向路由器要模型”，其余流程（失败分类、gofmt、仲裁、三次相同断言停止）不变。
- `application/usage.py`：报告新增 `routing` 区块；花费**从已有事件算出来**，没有新建任何花费状态表。

### 1.1 策略（`route()`）

| 规则 | 说明 |
|---|---|
| 起点 | 满足角色、上下文、预算的**最低等级**候选（本地优先） |
| 每级尝试次数 | `planning` 2、`generation` 2、`fix` 1（初次 + 自修一次；`fix` 链的“初次”就是前面的生成，所以只给 1 次自修） |
| 升级 | 当前等级用完尝试次数 → 去**严格更高**的等级里第一个可用候选 |
| 最高等级 | 不限次数，由调用方总轮次（4 轮修复）约束 |
| 当前等级被上下文/预算挡住 | 直接升级，不原地空转 |
| 停止 | 预算耗尽、没有更高等级、升级次数到顶（默认 2）、上下文放不下 → 返回 `stop`，**不是异常** |
| 角色限制 | 候选的 `roles` 非空时只服务这些角色 |

### 1.2 任务级预算

| 项 | 默认 | 说明 |
|---|---|---|
| 模型调用次数 | 40 | 本地和云都算 |
| API token | 200,000 | 只算云；调用前预留“输入估算 + 输出上限” |
| 运行时间 | 3600 秒 | 模型耗时 + 工具耗时；**不含等你确认的时间** |
| 费用 | 不限 | 设置后要求候选有价格，没价格的云候选直接不可用（不能假装有保证） |

- **预留-结算**：事前按保守上界预留，事后用真实用量结算。
- **未知用量不当 0**：请求发出但没有用量（崩溃、断线），按该调用的上下文上限计入预留。
- 花费 = 对整个任务（版本链所有成员）的报告求和，所以修复、重规划都不会重置额度。

### 1.3 路由快照（`RoutingSnapshot`）

任务开始时冻结：候选集合（等级、优先级、角色、上下文、价格、本地权重摘要、各自的无密钥配置快照）、策略、预算。**不含密钥**，凭据仍取自存活的同一目的地址的配置。作为 artifact 保存（`job.routing_ref`），也存在任务检查点里，所以恢复时用的是原集合，中途改配置不会隐式换模型。

### 1.4 失败链（决定“是否升级”）

路由器需要知道“同一件事已经失败几次、在哪一级”，用三条链：

| 链 | 记录的失败 |
|---|---|
| `planning` | Planner/Tester 的响应被契约拒绝 |
| `generation` | Developer 的响应被校验拒绝 |
| `fix` | 修复/测试修订的响应被拒绝，**或修复后验证仍失败**（`pending_fix`） |

历史存在任务检查点里（`route_history`、`pending_fix`），跨重启保留。

### 1.5 升级是“新 invocation”，不改旧调用

一次调用内模型不变（原有 “role input or provider changed” 保护保留）。升级发生在**新的修复 run**（本来每次修复就是新版本），所以旧调用完整保留、报告里能看到每一级的用量。

### 1.6 事件与报告

新增三种事件，写在任务的 run 上：`task_budget`（限额、策略、候选、价格）、`route_decided`（每次决策：链、角色、模型、等级、原因、是否升级、当时的花费）、`task_stopped`（为什么停）。报告的 `routing` 区块和前端“路由与预算”都是它们的投影。

## 2. 用户可见变化

- **新建任务**：选「固定模型」（默认，行为不变）或「本地优先 · 有界升级」（需「自动执行」）；可填 API token 上限。
- **任务报告**新增“路由与预算”：预算条（API token / 调用 / 时间 / 费用）、候选链、每次决策与升级原因、停止原因。
- **设置 → 路由与预算**：显示默认预算与策略、候选顺序。
- 后端：`/api/projects/plan` 接受 `routing: "ladder"` 与 `budget`；`/api/bootstrap` 返回 `routing_defaults`。

## 4. 已知限制（诚实清单）

1. **没有真实的本地→云升级端到端**（§0）。升级逻辑被确定性集成测试覆盖：本地一次自修失败 → 路由到云 → 修复成功；预算耗尽 → 停止且云零调用；本地一次就修好 → 不升级。
2. **恢复路径只测了持久化内容，没做“杀进程再恢复”的真实演练。** 路由快照、失败链、`pending_fix` 都在任务检查点里，恢复时 `_provider_of()` 会按保存的调用身份找回当初的模型；但这条路径没有端到端测试。
3. **上下文准入只是估算**（每 token 2.5 字节，保守）。只在路由层做，没有在提供方做硬拦截；规划阶段只估目标文本，生成阶段估“目标 + 已批准规格”，不含逐文件生成时越来越长的 `previous_files`。
4. **权重摘要只在恢复时比对**，任务中途模型被覆盖不会发现；Ollama 不可达时跳过检查，不阻塞任务。
5. **同一等级有多个候选时只用第一个**（按优先级、id），不轮换。
6. **路由事件在任务的第一个 run 出现之前缓存在内存里**，那段时间崩溃会丢这几条事件（决策本身不丢，因为只影响记录）。
7. **仅自动模式**：逐步确认模式没有路由。
8. 费用预算要求配置价格；货币单位由你配置的价格决定，系统不换算。
9. 每次决策都会重算一次任务报告（约几十毫秒），任务很长时可能需要增量化。

## 5. 后续优化（按建议顺序）

**M0.5（小而值得，建议紧接着做）**
- 做一次真实的“杀 worker 再恢复”演练并补成自动化测试（限额、失败链、`pending_fix` 跨重启）。
- 提供方侧的**硬上下文拦截**：超过 `num_ctx` 的请求在发出前拒绝，不再被服务端静默截断。
- 把逐文件生成的 `previous_files` 计入估算；估算按语言/模型校准（用真实 `prompt_eval_count` 回填修正系数）。
- 同级多候选轮换与“按角色的起始等级”（例如 Planner/Tester 默认从 L2 起）。
- 顶栏常驻预算条；Inspector 里按节点显示路由原因。
- 设置页可编辑默认预算与策略，并在新建任务时按任务覆盖。

**M1（图与诊断）**
- 失败**签名**驱动升级：不只数次数，而是“同一签名重复 / 分类为 unknown”才升级。
- `Diagnoser`：升级前先让高级模型只做诊断（输出 `{class, 原因, 指导}`），让本地模型照着修，再不行才让高级模型直接写。
- 声明式工作流与通用引擎（先接管失败后的修复子图，保留 `go-cli-v1`）。
- API/Worker 拆分、租约与心跳、命令表、崩溃后自动续跑（已确认：手动启动即可，崩溃可续跑）。
- 免费本地调用结果未知时自动重试，付费云调用保持保护。

**M2 / M3**
- `httpx` 流式与真取消（已放行依赖）、资源信号量、`RoleSpec` 注册表与受限子图提议。
- 评分卡：用每模型每角色的真实通过率驱动同级优先级；benchmark 套件对照“固定 API / 本地优先 / 带诊断”。

## 6. 为什么没有做真实本地升级验证

我先启动了一次真实的 GLM（L1）+ DeepSeek（L2）跑天梯；你随后说需要使用显卡，我立即终止了测试进程、卸载了 Ollama 中已加载的模型，并确认没有模型驻留。之后的真实验证只用了 DeepSeek 单候选，不再占用 GPU。要补这一项，需要在你不用显卡时再跑一次：

```powershell
.\.venv\Scripts\python.exe scripts\e2e_live.py --state <临时目录> --routing ladder --keep <本地id>,legacy --goal "…"
```
