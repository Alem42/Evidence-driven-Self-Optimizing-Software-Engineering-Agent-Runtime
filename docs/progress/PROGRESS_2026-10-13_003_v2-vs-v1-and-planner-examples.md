# PROGRESS 2026-10-13 · 003 — V1 与 V2 同预算对照；Planner 示例是否有用
# V1 vs V2 same-budget pairs; do Planner examples help?

数据 / data: `.masa/ab1/summary.json`（三轮）、`.masa/ab1_round{1,2,3}.log`；脚本 / script: `scripts/eval/ab_eval.py`。
设置 / setup: Python 语言包；6 个小任务（upper、fizz、sum、wc、join、roman）；本地 glm-4.7-flash 起步，Flash 兜底并担任 Planner/Tester/Diagnoser，**不使用 Pro**；单次上限 0.3 元；独立判官（oracle）判定；任务内交替臂的先后顺序。
累计花费 / spent: 约 2.94 元（ab1 全部三轮，含两次冒烟）。

## 1. 诚实声明 / Caveats first

- **样本极小**：每个臂每轮 6 次，且同一任务、同一模型反复使用，不是独立样本。差一个任务（1/6）不是显著差异。
- **第 1 轮在修复前**：当时 Tester 格式被拒、工人协议问题（缺 `content`、不封存）尚未修复，只用来暴露问题，**不与后两轮合并比较**。第 2、3 轮是修复后（提交 `0dd50ba`、`7e0de81`）。
- **y 臂只有第 3 轮**（每臂 6 次），x 臂有第 1、2 轮。
- 没有做显著性检验；下面的“差异”只是方向性证据。

## 3. 结论 / Findings

1. **V2 与 V1 通过率持平（12/12 对 11/12，差异在噪声内），V2 平均快约 37%（39 秒对 62 秒），元/通过略低（0.033 对 0.042）。** 代价是调用次数约多 80%（17.5 对 9.7）——调用多但每次小、且大多落在本地模型上。因此 V2 的优势是**时间**，不是质量，也没有证明省钱（费用差在噪声内）。
2. **Planner 示例没有显示出收益。** 把示例合并进测试（x 臂）通过率反而偏低（9/12 对 v1/v2 的 23/24）、费用更高：示例让测试集更大更严，而示例里的期望值本身有时是错的（wc/v1y 的示例对真实程序只通过 5/7，而判官通过）。示例仅作指引（y 臂）v1y 6/6 且最便宜，但 v2y 5/6 且最贵（失败是预算），**两者互相矛盾，n=6 不能下结论**。
3. 示例值与真实程序的一致性：27 次有示例的运行里 26 次示例全部通过真实程序——说明模型给出的示例**多数是对的**，但“多数对”不足以把它当作唯一真值：错的那一例会直接让测试和程序互相矛盾。
4. 评测过程中暴露并已修复的真实问题（比比较本身更有价值）：Tester 检查计划 39 次调用有 17 次因格式被拒（现在确定性归一化）；Flash 返回 JSON 后带多余文本、glm 的 write_file 缺 `content`（容错解码 + 只检查形状的校验器 + 工具给出精确回答 + 严格的逐工具 schema）；工人不封存（工具自己跑完剩余的必需检查并封存）。
5. 小任务上 V1 的 1 次失败是修复阶段的提案格式问题，而不是生成问题——与上一篇“用户两次真实运行”的结论一致：**问题多在边界（格式、基础设施、规格矛盾），不在“角色不够多”。**

## 4. 决定 / Decisions

- `planner_examples`、`examples_as_tests` **保持默认关闭**；没有证据支持打开。保留代码与开关，因为它是一个可测的机制，且 y 臂的方向（示例仅作指引）值得更大样本。
- V2 保持**可选**（`request.runtime=v2`）。建议在“想要更短的墙钟时间、本地模型占多数”时使用；不要宣称它更准或更省。
- 默认流程不变（黄金提示词与 `loop_equivalence` 保持 IDENTICAL）。
