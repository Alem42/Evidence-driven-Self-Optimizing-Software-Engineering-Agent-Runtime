# 进展017：M2 · W1 流式传输、真取消、stall 检测

2026-10-05。分支 `feature/multi-model`。前置：[进展016](PROGRESS_2026-10-05_002_benchmark-findings-and-fixes.md)。计划：[PLAN_MULTI_MODEL_RUNTIME §10 W1](../PLAN_MULTI_MODEL_RUNTIME.md)。

## 1. 做了什么

| 能力 | 之前 | 现在 |
|---|---|---|
| 取消 | 请求是一次阻塞调用，“停止”要等当前调用返回才生效（最长几分钟），期间还在花钱/占 GPU | 每个数据块之间检查取消标志；取消时关闭连接，Ollama 随之停止生成。本地回环服务器集成测试：取消后 3 秒内返回、服务端检测到断开 |
| 卡死检测 | 分不清“慢”和“卡死”，只有整体超时 | 两个阈值：**首字前**（本地模型加载/预填充可能很慢：本地 900 秒、云端 240 秒）与**开始回答后**（本地 180 秒、云端 90 秒）没有任何字节就判 stall。**语义**：本地免费调用→`TransportFailure`（可安全重试）；云端付费调用→结果未知、**不自动重放** |
| 实时进度 | 看不到“正在生成” | `runtime/live.py` 记录每个 run 当前调用的已生成字符数与用时；`project_job` 带 `live`；顶栏显示“生成中 N 字”，评测进度卡也显示 |
| 响应格式 | 一次性 JSON | Ollama 原生 NDJSON、OpenAI 兼容 SSE（`stream_options.include_usage`）；一个完整的非流式 JSON 响应也能解析（就是只有一个块的流），旧测试替身和不支持流式的服务仍可用；profile 里 `streaming=false` 可回到一次性 |
| 配置 | — | `stall_seconds`（5–3600）、`first_token_seconds`（5–7200）、`streaming`（bool）进入配置校验（之前未知键会被静默丢弃，这三个旋钮会不生效——测试发现） |

**没有引入 httpx**：urllib 的响应本来就可以增量读，不需要 async 重构；httpx 留给以后真需要并发/连接池时。

## 2. 实现中踩到的三个真实坑（都有测试）

1. **套接字读超时之后，同一个响应对象不能再读**（`cannot read from timed out object`），所以“给套接字设短读超时再轮询”这个直觉做法行不通——而且它会让“本地 stall”测试**碰巧通过**（抛的是别的传输错误）。→ 改成**读取线程 + 队列**：主循环带超时地从队列取，取消/stall 才有机会生效。测试里断言错误信息确实是 stall。
2. **同步 `close()` 会被读取线程卡住**：`BufferedReader.close()` 要等读取线程释放读锁，而它正阻塞在 `recv`——stall 在 5 秒检测到，连接却又等了 9 秒才关。Windows 上对带超时的阻塞 recv 做 `shutdown` 也唤不醒它。→ 异常退出时 `shutdown` 套接字，再把 `close()` 交给后台线程，**调用方不等待**（`streaming.abandon`）。
3. **配置旋钮被静默丢弃**：见上表“配置”。

## 3. 验证

- 离线：解析（任意字节边界、keep-alive 注释、末尾用量、无结尾换行、截断流、流内错误）、读取循环（取消在静默期间也能响应、两种阈值、整体时限、字节上限、进度单调）、**真实本地 HTTP 服务器**（NDJSON/SSE 结果与用量、进度回调、中途取消+服务端看到断开、stall 本地/云端语义、关闭流式）。Python 404 项、前端 31 项通过。
- 真实服务：DeepSeek（SSE，用量与进度回调正常）、Ollama（NDJSON，用量与 tok/s 正常）。**没有**在真实 Ollama 上做“中途取消”（三角测试里用的预检角色输出太短，来不及取消），取消行为由本地回环服务器的集成测试覆盖。

- 流式下不再需要一次性读入整个响应，但仍保留 1MB 上限；超大输出的逐文件生成已经由 per_file 模式承担。
