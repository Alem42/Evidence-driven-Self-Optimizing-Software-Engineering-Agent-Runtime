# 经验库停用、规模自适应分层上下文接入、第一次 10 文件项目实测

2026-10-10。预算：这次只花了 ¥0.29（一次真实运行），累计约 ¥19.6，仍在用户批准的 ¥20 内；按用户要求，需要大量 token 的重复测试不做。

## 做了什么
1. **经验库停用**：流程里的所有接入点失效（`orchestration/coordinator.py::_library()` 恒为 None，原实现留在注释里）；`intelligence/library.py` 与它的单元测试保留；设置页的经验库控件隐藏；策略键 `library` 仍被接受但不起作用。理由：留出任务 0 命中，训练出的签名太泛。
2. **规模自适应分层上下文接入**（策略 `context_budget`，默认关闭）：
   - `orchestration/context_plan.py`：必需 / 重要 / 可丢三层；规模规则：全部内容 ≤ 窗口 35% → 小任务，原样全给；否则按预算（窗口 50%）裁剪。新增**轮廓降级**：可丢文件先变成“只有声明、没有函数体”的轮廓（`outline_go`），仍放不下才整项丢。
   - 接入 `generation.py`：逐文件生成时，同目录的文件（含它的冻结测试）和 go.mod 保持完整，其它目录的实现降级为轮廓，其它目录的测试直接丢；修复阶段，失败证据里点名的文件完整，其余变成只读轮廓（放进单独的 `other_files_outline_readonly` 键，不可编辑，避免模型改一个只有轮廓的文件）。每次实际裁剪都写 `context_plan` 事件进账本。
   - 零影响的保证：关闭时 `_fit_files` 直接返回原对象；打开但任务小时也原样返回；差分检查与改动前逐项相同，提示词没改（轮廓用注释头放在同一个 `previous_files` 里）。单元测试覆盖关闭、小任务、大任务三种情形。
3. **大项目任务 `bank`**（等级 10，`bench/tasks_large.py`，不在任何套餐里，按 id 运行）：多包银行账本 CLI，要求拆成 解析 / 存储 / 转账规则 / 报表 四个包、每包带测试，跨包有一套固定的错误优先级规则；Python 参考实现用手算答案钉住（`tests/test_bench_large.py`）。

## 第一次 10 文件项目的真实运行（默认流程，Pro + Flash，¥0.29，102 秒）
结果：**未通过**（Gate 失败，3 轮验证，没有升级）。规格里确实是 10 个文件（go.mod、main、4 个包各带测试）。

| 指标 | 10 文件项目 | 对照：小任务（L2–L5） |
|---|---|---|
| 云端 token | 117k | 约 10–60k |
| 模型调用数 | 15 | 约 4–10 |
| Developer 每个文件的输入 | 平均 5.2k，最大 10.2k（随已生成文件数增长） | 平均 1.5k |
| 修复 / 修订测试的输入 | 14.4k / 14.6k | 7.4k / 7.2k |
| 费用 | ¥0.29 | ¥0.1–0.5 |

失败过程（账本）：第 1 轮 `module_path`——`main.go` 导入了规格里根本不存在的包 `example.com/bank/internal/app`，另有两个断言失败；Diagnoser 判“测试错”（一个测试期望“bad command”，而验收标准明确是“bad amount”先于其它检查）；测试修订后，同一个断言仍失败：`Apply("transfer alice bob 1000") = "error: unknown account", want "error: insufficient"`——很可能是测试没先开户，实现的检查顺序是对的；第 3 轮未解决，停止。

## 发现的问题（按重要性）
1. **跨包契约不一致**是 10 文件项目的主要难点，不是上下文大小：各包的测试和实现是分开生成的，包与包之间的接口、错误优先级规则只存在于自由文本的验收项里。首轮就出现“导入不存在的包”和“两个包对同一规则理解不同”。
2. **“测试期望/测试数据写错”依然是收敛不了的那一类**：Diagnoser 判对了（测试错），但测试修订没能修好——和小任务里 wc/wordfreq 的失败模式相同。说明测试可靠性（用例审计）还没覆盖到 Developer 写出来的 Go 测试代码本身，只覆盖了规划阶段的用例。
3. **上下文随规模线性增长，但在云端大窗口下完全不是瓶颈**：10 个文件时 Developer 的最大输入 10k、修复 14k，远小于 262k 的窗口；用真实输入重放分层预算：窗口 16k 时只有 2/9 次调用被判为“大任务”，且都在预算内，**省 0 token**；窗口 ≥32k 时一次都不触发。结论：分层预算对 10 文件项目没有作用，对 16k 窗口的本地模型要到约 20+ 个文件才开始有作用。框架的价值在更大的项目，目前**没有数据能证明**它有用，所以默认关闭。
4. **成本和时间的放大是可接受的**：token 约 4.7 倍，费用只是 ¥0.29（Flash 干活），102 秒。

## 优化方向（按“证据 → 做法”，都不需要大量 token 去验证）
1. **导入检查（确定性、零 token）**：生成每个文件后检查它导入的项目内部包是否在规格的文件列表里，不在就带着“只能导入这些包”的提示就地重写——和已有的语法/导入就地重写是同一机制，直接挡住首轮的 `module_path` 失败。
2. **接口契约进规格**：让 Planner 在规格里为每个包写出导出函数签名和跨包规则的优先级（结构化，而不是自由文本），Tester 的用例按契约写，Developer 的测试/实现都以契约为准；加一个确定性检查“测试只调用契约里的签名”。这对准跨包不一致，是大项目最值得做的一项。
3. **把测试可靠性做到 Go 测试代码上**：失败时对失败输入做盲推导投票，把独立证据交给 Diagnoser（路径 B），并在测试修订之后要求“失败断言必须变化”；目前小任务和大任务都卡在这里。
4. **上下文**：先不接入分层预算；等有 ≥20 个文件的项目、或者本地小窗口模型成为主力时再用影子重放决定。已经够用的是：同目录文件完整 + 其它包只给轮廓这一规则。
5. **评测**：再补 2–3 个大项目任务（带独立判官），每个跑 1–2 次即可看出趋势；不需要像小任务那样大样本。
