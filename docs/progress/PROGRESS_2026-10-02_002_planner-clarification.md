# Planner 主动澄清首版

2026-10-02。

## 可以做什么

Planner 发现业务边界不清时可返回结构化问题，每轮最多三个问题，每问最多三个选项，始终支持自由文本。工作台显示问题卡片，图中 Planner 显示等待回答；没有默认提交。用户回答后继续 Planner，再交给 Tester，最终仍需要正常方案审核。

自动模式也暂停等待，不替用户作答。等待不占模型调用；问题和答案保存在运行元数据及事件中。回答事务提交后可重启续行，同一问题相同回答幂等，冲突答案与旧问题标识拒绝。新调用使用独立 invocation_id，总预算为三次调用，deadline 不重置。

首版只支持规划阶段一轮澄清，Tester/Developer 运行中提问、需求变更后的下游失效、多轮问答尚未实现。不是完整任意角色 Human-in-the-loop。既有旧运行保持旧调用输入以兼容缓存。

## 验证事实

125 项 Python 完整回归通过；随后澄清与项目视图相关测试再次通过。前端 4 项测试及 Vite 构建通过。没有浏览器视觉/点击验收。

真实 DeepSeek 运行 3c893f93cafe4d46a94c09921455a3bd：模糊随机数需求 → waiting_for_input → 测试脚本提交明确答案 → 数据库关闭重开 → Planner 与 Tester 完成 → awaiting_review；共三次模型调用。答案由验证脚本提供，不冒充真实用户点击。此次只验证规划，不生成或执行新的 Go 项目。

第一次真实运行 0901e92f06c94cddb18f3573030836ed 的澄清与回答后规划成功，Tester 的 cases 数量协议未通过；保留失败记录。数量校验也会拒绝空数组，因此提示补充静态/格式检查不要输出空 cases。第二次完整规划通过，未放宽校验。

## 使用

重启本地 masa ui 服务加载新版，输入边界不明确的需求。模型决定需要澄清时会展示问题卡片；填写后点击“提交回答并继续”。若回答保存后服务中断，在角色恢复入口继续；自动任务仍保留原任务检查点。该版真实模型测试显式要求先提问，尚不能据此宣称模型能稳定识别所有自然歧义。
