## C：最小可用整项目生成

| 增量 | 实现 | 验收 |
|---|---|---|
| C1 Developer 提案 | 只消费已批准的 ProjectSpec 与 CheckPlan；返回路径到完整文本的文件集合；约束为标准库 Go CLI | 文件集合必须匹配批准目录；拒绝路径逃逸、额外脚本、缺文件、超限；不写工作区 |
| C2 多文件人审 | 文件树、逐文件代码预览/编辑、一次批准；绑定规格与代码摘要 | 修改任何文件都需重新批准；旧页面不能批准新提案；刷新能恢复持久化提案 |
| C3 版本落盘与验证 | 临时版本目录准备全部文件，清单校验后发布；使用已批准检查图启动 Runtime | 失败不发布半个项目；重复批准幂等；test/vet/fmt 真执行，Gate 独立核对；保留来源方案 |
| C4 使用交付 | 工作台提供项目位置/安全导出与结果；按需小额真实模型测试 | 从一句话到可打开的 Go 文件夹；模型生成测试与用户验收标准区分展示 |

角色职责：Planner 决定结构；Developer 提交代码；Tester 设计验证方案；Reviewer 后续审查。检查节点是动作，不能混成角色。Runtime 校验计划与权限，Gate 不能采信模型自称通过。

## 实现限制与接续提示

- 复用 project_plan 的 approval_ref，不从未批准的 spec_ref 直接生成。
- 首版最多 20 文件、单文件 60 KB、总计 300 KB。集中定义限制；当前规格 JSON 40 KB、检查方案 16 KB。
- 不放宽已有 Patches 到任意文件写入；新项目文件集合用独立受控发布逻辑，保留现有单文件流程。
- 先实现标准库、固定 Go CLI；第三方依赖安装、HTTP 常驻服务、自动多轮修复后置。
- D 再接固定 go run ./cmd/app、结构化参数、超时/取消/输出上限。
- 本轮尚未用真实上游模型评估 Planner 质量；下一轮具备会话密钥时，优先用小型 CLI 需求验证方案合理性与 token 开销。
- 每个通过验证的增量及时提交；结束更新状态、本计划和易读进展报告。
