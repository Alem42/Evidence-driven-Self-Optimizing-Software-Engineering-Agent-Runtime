# Runtime V2：按包推进的自主 agent 循环（设计，未实施）

状态：**设计稿；第一个切片已实现（包工人循环作为生成策略，实验、默认关闭，见 [PROGRESS_2026-10-13_001](../progress/PROGRESS_2026-10-13_001_language-packs.md)）**；其余里程碑未做。2026-10-12 起草。与现有流程**并存**（`request.runtime = "v1"`（默认）｜`"v2"`），用数据决定是否替换默认。
语言无关：V2 只通过“语言包”（见 [LANGUAGE_PACKS.md](LANGUAGE_PACKS.md)）使用编译、测试、格式化等操作，所以 Go、Python、以后的 C# 共用同一套流程。

## 1. 为什么要做（来自本项目自己的数据）
| 现象 | 数据 | 结构性原因 |
|---|---|---|
| 失败以“期望算错”和“修了没改善”为主 | 失败分类：37% 期望算错、51% 修复后无改善 | 测试期望由模型写、写完冻结，错了要走很长的修订流程 |
| 机制叠加没有稳定收益 | 指挥者、best-of-N、经验库、裁判、契约：均未测出稳定收益 | 它们都在“整条流水线”的缝隙里打补丁 |
| 大项目一轮失败整包重来 | bank 基线：3 轮 × 8 个无用文件，¥1.72，失败 | 验证粒度是整个项目，失败只能项目级重试 |
| 规格自相矛盾 | 规划者写“main 读 stdin”，检查规则禁止 | 规划之后没有一致性检查，弱 planner 的错误会一路放大 |
| 用户看不到过程 | 前端只有阶段与结束后的报错，没有流式输出 | 每个角色是一次性调用，没有可展示的“过程” |

**判断**：问题不在某个角色不够聪明，而在“把一个会反复试错的工作，拆成一次性调用的流水线”。主流做法相反：一个 agent 在带工具的循环里自己读错误、改、再跑，验证是确定性的、立刻可见的。

**要保留的资产**：事件溯源账本与精确一次的角色调用、预算与路由、独立 Gate、带独立判官的评测集、全部确定性检查（导入/入口/格式/测试静态检查）、盲推导表决与断言裁判（用作“仲裁”）、上下文分层预算（`context_plan`）。
**要换掉的**：中间那条 Planner → Tester → Developer → 整体验证 → Diagnoser → Repair 的串联。

> 外部做法的概述（来自通用知识，本次没有逐项核实）：Claude Code / Aider / SWE-agent / OpenHands 是“单个 agent + 工具循环 + 按需读取上下文”；Agentless 是“确定性分阶段（定位→修复→验证）”；AutoCodeRover 按符号检索。我们采用的是：工具循环（前者）+ 确定性闸门（Agentless 的思想）+ 签名摘要代替全文（Aider 的 repo map 思路，我们的 `outline` 已有）。**这只是外部经验，必须用第 9 节的实验验证。**

## 2. 总览
```
需求 ─► 预检（确定性规则 +可选本地复核，已有）
     ─► 规划（只调用一次，最高等级模型；产出“骨架规格”）
     ─► 规划闸门（确定性，0 token；不合格带精确错误回给规划者，最多 2 次）
     ─► 包工人循环（按依赖顺序，叶子包先；每个包一个自主循环）
            工具：读文件 / 写文件(只限本包) / 看依赖接口 / 跑本包检查
            直到：本包测试+静态检查通过（封包）｜卡住（升级模型）｜预算耗尽（停）
     ─► 集成（入口接线，整项目 test/static/format/build）
            失败按归属回到对应包的工人，只重做出错的包
     ─► 黑盒验收（用规划里的示例，经真实入口运行）+ 独立 Gate（已有）
```
四个阶段，没有 Tester / Diagnoser / Repair / TestRevision 这条链。Diagnoser 只作为“卡住时的仲裁帮手”保留（见 6.3）。

## 3. 要不要 Planner？Planner 出问题怎么办？
**要，但只做一件事，并且要被卡住**。没有规划，工人不知道包边界；bank 的失败恰恰来自规划不一致。但弱 planner 不能空烧 token：

1. **规划只产出“骨架规格”**（结构化，由语言包校验）：
   - `mode`: `solo`（小任务，1 个包，跳过按包流程直接一个工人）｜`packages`；
   - 包列表：目录、职责一句话、依赖哪些包（必须无环）；
   - 每个包的**公开接口桩**：用目标语言写的签名声明（Go 的函数/类型声明，Python 的 `def f(...): ...`）。这些桩要能通过该语言的“编译/语法检查”；
   - **示例**（至少 N 个，N 随复杂度）：命令行参数 + stdin → 期望 stdout + 退出码，每个示例带编号。**示例是整个项目里唯一的期望来源**；
   - 入口接线：入口文件只调用某包的 `Run`（规则由语言包给出）。
2. **规划闸门（确定性，0 token）**：语言包的规格校验；依赖图无环、分层合理（入口 → 应用 → 叶子）；桩文件放进临时工作区跑一次语法/编译检查；示例都能解析；未知内部导入为零；入口规则无冲突（这正是 bank 的矛盾）。
3. **失败处理**：闸门失败的原因是机械的，原样回给规划者，**最多 2 次重试，总共最多 3 次规划调用**（硬上限，写进预算）。仍不合格 → 任务以“规划不收敛”结束，报告写清是哪条闸门没过，并让用户选择：手动在界面里改规格后继续、换更强的规划模型、或降为 `solo`。**不继续往下烧钱。**
4. 示例可选地用已有的 Flash×3 盲推导表决校验（约 ¥0.05/任务）：规划者给的期望输出，让独立模型只看需求重新推导、机械比较；不一致的示例标记为“存疑”，不进入黑盒验收的硬判据。

## 4. 包工人（核心）
### 4.1 工具集（全部是语言包操作的包装，没有任意 shell）
| 工具 | 作用 | 限制 |
|---|---|---|
| `read_file(path)` | 读自己包内的文件 | 他包只能看签名摘要 |
| `write_file(path, content)` / `edit_file(path, old, new)` | 写文件；写入前自动做语言包的确定性规范化（Go：gofmt + 导入修复；Python：语法检查） | **只能写自己包目录**；写入立即做“就地检查”（语法、未知内部导入、入口规则、泄漏），失败原样返回 |
| `show_interface(pkg)` | 依赖包的公开签名摘要（`outline`，按文件哈希缓存） | 只读 |
| `run_check(kind)` | `kind ∈ {test, static, format, build}`，范围限定在本包（Go：`go test ./pkg`；Python：对应测试目录） | 输出截断；错误按“文件:行:信息”解析并附出错行附近源码（已有 `snippets`） |
| `finish()` | 申请封包 | 只有本包 `test` 与 `static` 都通过才接受 |

### 4.2 工人写自己的测试，但期望只能来自规划
工人同时写实现和本包测试。**测试里的期望值必须出自规划里的示例或验收条款**；其他断言用“结构性”写法（不依赖具体算出来的值）。执行方式：
- 已有的测试静态检查（空转断言、不会失败的测试）继续用；
- 规划里的示例会被**自动转成该包可用的测试夹具**，不是让模型转抄；
- **争议仲裁**：同一个断言，工人先改测试再改实现、又改回来（同一断言指纹反复 ≥2 次翻转），触发已有的断言裁判（把两个值打乱成 A/B，Flash 独立选 3 次，多数为准，单次 80%、三次多数 88% 的测量见 TEST_RELIABILITY）。这样既不让弱模型的错误期望被冻结，也不让工人把测试改成迎合错误实现。

### 4.3 卡住检测与升级
- **错误指纹**：`归一化(路径, 错误类别, 信息前 80 字符)`。同一指纹连续 3 次，或错误数连续 K 步不降 → 判定卡住。
- 升级阶梯：**本地小模型 → Flash（重建上下文后继续）→ 仲裁帮手（Diagnoser/裁判，一次）→ 停止**。**V2 里不使用 Pro**；Pro 只在规划阶段用一次。
- 升级时不是“整个 transcript 搬过去”，而是重建上下文：任务 + 依赖摘要 + 当前文件全文 + 最近一次错误（见第 7 节）。
- 每个包有硬上限：步数、云端 token、墙钟时间。耗尽 → 该包标记失败，集成阶段不继续，任务以“某包未收敛”结束，报告列出该包的最后错误与已写文件，用户可以接手、加提示后继续（`resume`）。

### 4.4 边界
- 写范围 = 本包目录（工具层强制，不靠提示词）。
- 需要改别的包的**公开接口**：工人不能直接改，而是提交“接口变更请求”（要改的签名 + 理由）。规划闸门的同一套检查通过后，才修改规格里的桩，并把依赖它的已封包的包重新打开（只重新验证，不重写）。这是对“是否要明确边界”的回答：**要，而且要由工具强制。**

## 5. 集成与验收
1. 全部包封包后，写入口接线（通常只有几行，由入口工人完成，同样走工具循环）。
2. 整项目 `build`/`test`/`static`/`format`（沿用现有 Gate 的图：`test`、`vet`、`format` + `gate`）。失败时用已有的归属分析（实现/测试/格式）定位到**拥有那个文件的包**，只重新打开这些包（带错误作为第一条消息）；集成轮数有上限（默认 3）。
3. **黑盒验收**：用规划里的示例，经**真实入口**逐个运行（现有 `app_run` 操作），与期望对比。这抓住 V1 里“测试都过、接线错了”的假通过（评测里 4 个假通过都是这类）。存疑的示例只告警不拒绝。
4. 独立 Gate 不变。**Gate 通过才算成功**，和 V1 完全一致，所以评测可以直接对比。

## 6. 本地小模型 + Flash 怎么用得稳
1. **输出协议**：每步一个 JSON 动作（`{tool, args}`），schema 校验；格式不合法 → 把校验错误原样回给模型，**不计入包的步数**，但每步最多重试 2 次（防止小模型在格式上空转）。
2. **小步、小上下文**：单个工人的上下文目标 ≤ 8–12k token（可按模型窗口配置），由 `context_plan` 的分层分配：必须保留（任务、本包文件、最近错误）> 重要（依赖签名）> 可丢（旧工具输出，压成一行）。
3. **确定性前置**：能由代码做的绝不让模型做——格式化、导入修复、语法检查、未知内部导入、入口规则、示例转夹具、错误解析。模型只做“写逻辑”和“读错误改逻辑”。
4. **选模型靠数据**：用我们已有的“语法就地重写次数/卡住次数/升级次数”作为每个本地模型的评分（每个模型在固定的 5 个小包上各跑一遍，免费）。**具体哪些本地模型能胜任工具调用协议，要先测，不预设。**

## 7. 上下文管理（对应“不同角色如何很快理解别人做的东西”）
每个工人的上下文固定成五段，顺序固定，利于缓存：
```
1 角色提示词（语言包片段 + 工具说明）                      固定
2 任务：本包职责、依赖包名单、相关示例、相关验收条款         来自规划，固定
3 依赖接口摘要：每个依赖包的公开签名（outline）             按文件哈希缓存
4 本包当前文件全文                                          随写入更新
5 最近 N 步的工具往返；更早的压缩成一行（“跑 test：3 失败 → 已修”）+ 工作笔记
```
- **理解别人写的代码** = 读签名摘要，不读实现；接口之外的事不需要知道（这就是边界的价值）。
- **接着开发** = 第 4 段（当前文件）+ 第 5 段的工作笔记。笔记由工人自己用一个 `note(text)` 工具追加（上限 1KB，覆盖式）；崩溃/升级后从笔记和文件恢复，而不是靠对话历史。
- 大项目规模由规划的包数天然限制每个工人的上下文，不需要等窗口爆了才降级；`context_plan` 仍作为兜底。

## 8. 用时间换质量（长时间运行）
- 预算以**墙钟时间**为主，其次云端 token 与 ¥；每个阶段、每个包各有上限，**包是检查点**：封包后其文件与接口摘要写入账本。
- **事件溯源的 agent 循环**：每步的模型输出作为工件写入账本（`invocation_id = w:<包>:<步>`）。崩溃或停机后 `resume`：重放已记录的步骤（工具重新执行，便宜且确定），在第一个没记录的步骤继续调用模型——**已经付过的钱不会再付**。
- 夜间/长时间模式：允许把包的步数与时间上限放宽，让本地模型多轮尝试；云端 Flash 的调用次数仍受 token/¥ 上限约束（卡住才用）。
- 暂停/继续/停止、用户给某个工人加一条提示（作为下一步的用户消息，记入账本）。

## 9. 可见性：前端怎么让人看懂（对应“黑盒、没有流式输出”）
**新事件**（账本，全部可重放）：`v2_phase`、`plan_gate_result`、`worker_started{pkg,model}`、`model_delta`（流式片段，节流写入，不进长期账本，只走实时通道）、`tool_call{name,args摘要}`、`tool_result{ok,摘要}`、`check_result{kind,通过,失败数}`、`file_written{path,行数变化}`、`stuck_detected{指纹}`、`escalated{from,to}`、`package_sealed`、`integration_round`、`acceptance_result{示例号,ok}`。
**实时通道**：复用 `runtime/live.py` + HTTP SSE，增加 token 增量与工具往返。
**界面（“运行视图”）**：
- 左：**包依赖图**，每个节点显示状态（待办/进行中/封包/卡住）、当前模型、已用 token/时间；
- 中：**所选工人的会话流**，像 Claude Code：模型文字流式出现，每次工具调用与结果折叠成一行，可展开看原文；错误与出错行附近源码一并显示；
- 右：该包文件树与**每次写入的 diff**、当前未解决错误；
- 下：**预算条**（按角色/模型的 token、¥、墙钟）+ 控制（暂停、继续、停止、给工人加提示、批准规划、编辑规格后继续）。
- V1 的运行也能用同一个视图：把现有阶段映射成“工人”，没有流就只显示结果。**这一部分不依赖语言包与 V2 循环，可以最先做**。

## 10. 与现有系统的关系（并存方式）
- 入口：`request.runtime`；`v1` 走现有 `WorkflowCoordinator`，`v2` 走新的 `V2Coordinator`（独立模块 `application/v2/`）。两者共用：账本/Store、`RoleRuntime`、Router/预算、Gate（`Runtime.execute`）、语言包、确定性检查、评测。
- 角色：新增 `package_worker`（工人，RoleSpec 数据驱动，提示词由语言包片段拼装）；`project_planner` 输出格式增加 V2 的骨架字段（V1 的规格是它的子集，字段用版本号区分，不改变 V1 的校验）。
- 评测：`bench` 加 `runtime` 臂，同任务、同预算对照。
- 不动 V1 默认行为：沿用 `scripts/eval/loop_equivalence.py` 保证。

## 11. 里程碑与验收
| 里程碑 | 内容 | API 花费 | 通过标准 |
|---|---|---|---|
| M0 | 运行视图 + SSE 流式（先接 V1 现有事件） | 0 | 一次 V1 运行里能实时看到模型文字、阶段、错误 |
| M1 | 语言包 API 稳定（见 LANGUAGE_PACKS P1–P3） | 0 | Go 包通过一致性测试，默认流程等价检查 IDENTICAL |
| M2 | 工人循环骨架 + 规划闸门，**用假模型测试**（脚本化动作） | 0 | 单元测试覆盖：封包、卡住升级、边界拒绝、崩溃续跑不重复付费 |
| M3 | 本地模型冒烟（5 个固定小包） | 0（本地） | 每个候选本地模型的“封包率/卡住率”表 |
| M4 | Flash + 本地，L2–L6 小任务 | 约 ¥2 | 与 V1 默认同预算对照 |
| M5 | bank/inventory/grades 大项目各 3 次 | 约 ¥4 | 见下 |
| M6 | 决策：是否让 V2 成为默认 | 0 | 见下 |

**成功判据（M5，三项都要）**：(1) 通过独立判官的比例 ≥ V1 默认；(2) **失败运行的浪费 ≤ ¥0.3/次**（V1 的 bank 失败是 ¥1.72）；(3) 假通过为 0（黑盒验收）。
**放弃/转向判据**：M4 在 L2–L6 上通过率低于 V1 默认超过 10 个百分点且成本更高 → 先查是哪一环（规划闸门误杀？工人协议？），修一轮再测；两轮后仍不达标，V2 保持实验功能，不继续投入。
**预算**：M4+M5 约 ¥6，只用 Flash 与本地模型，规划复用账本里已有的计划（不再花 Pro），先按“每个臂 1 轮”看趋势，不追求统计显著。

## 12. 风险与诚实的未知
- 本地小模型能否稳定遵守工具协议——**未测**，M3 才有数据；若不行，工人的主力是 Flash，成本模型要重算。
- “工人自己写测试”可能把 V1 的“测试期望算错”问题换了个形式出现；缓解靠“期望只来自示例”与争议仲裁，**是否足够是 M4/M5 要回答的核心问题**。
- 示例本身可能错（规划者算错）：盲推导表决只能降低、不能消除；存疑示例不作为硬判据。
- 集成阶段的接口变更会级联重开已封包的包：设计上限制了次数，实际代价待测。
- 以上不是已验证的结论，是待验证的假设。
