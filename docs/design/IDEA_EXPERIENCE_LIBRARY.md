## 1. 它是什么（回答“算不算上下文 / 学习路径”）
- 是**上下文工程**：把过去验证过的经验在需要时检索出来放进提示词，属于“程序性记忆 / 情景记忆”。
- 也是一种**学习**，但是非参数的：不改模型权重，系统通过积累经验变得更好。学术/工程上叫经验回放、技能库、经验记忆。
- 业界对应物：Voyager 的技能库（把验证过的代码存起来按描述检索）、Reflexion（失败反思放进下一次尝试，项目里的 `attempts.summary` 已是它的确定性版本）、ExpeL / Agent Workflow Memory（从成败轨迹里提炼可复用的规则和流程）、Claude Skills 的“渐进披露”（先只放一行索引，需要时才读正文）、MemGPT/Letta 的分层记忆（小的常驻层 + 大的外部层）。你的 RAG 项目经验可以直接复用检索那一层。

## 2. 你的几个设计点，逐条判断
| 想法 | 判断 |
|---|---|
| 存“曾遇到的问题 + 常见解法” | 合理，**但只存有证据的**：失败签名 → 修复做法 → 这次修复让未解决条目下降/通过了（账本 run id 做证据）。没有证据的“经验”会污染仓库。 |
| 仓库有上限，按所见动态增减 | 合理。用“效用”淘汰：命中次数 × 命中后的成功率 × 新近度，低的先淘汰；按字节限容。这是缓存淘汰问题，不需要 LLM。 |
| 一开始就判断能不能直接用仓库解决 | **只对“确定性可匹配”的条目成立**：如果失败签名与条目的签名完全吻合且该条目是确定性修复（像 goimports），就直接执行，0 token——这其实就是“把经验升级成工具”。否则只是建议，不能直接当解法。 |
| 仓库很大时先让模型生成，卡住再读仓库 | **推荐作为默认**（延迟检索）。理由：多数任务第一次就过（评测里约一半一轮通过），预先读库只会增加每个任务的 token。只在修复阶段（已经失败、有了失败签名）才查库，用签名做精确匹配，命中才注入。和 Claude Skills 的渐进披露同一思路。 |
| 让指挥者来判断用不用库 | **不建议**：指挥者的真实评测已经显示“多一次 LLM 决策”不免费且没收益。用确定性的签名匹配代替 LLM 判断，成本为 0。 |

## 3. 最小可行设计（建议）
- **条目**：`{id, signature, class, pitfall, remedy, evidence_runs, hits, successes, last_used, bytes}`。`signature` = 失败归属类别 + 归一化后的错误信息（去掉路径、行号、标识符）。
- **入口**：只在修复阶段（`classify` 之后）查；命中的条目的 `remedy` 作为一段不超过 N 字的指导，拼进修复指令（和 Diagnoser 的指导同一位置），并写 `library_hit` 事件进账本，保证可重放、可统计。
- **写入**：任务结束后，对“修复使未解决条目下降或通过”的那一轮，抽取（签名，做法）。做法的来源是**确定性的事实**（改了哪些文件、Diagnoser 的结论文本），不让模型自由总结。
- **淘汰**：容量上限 + 效用评分；命中后失败的条目降权，连续失败则移除。
- **升级为工具**：命中率高、做法能写成确定性代码的条目，进入“工具候选清单”——这就把你的两个想法合成一条管线：库负责**发现**该做哪些工具，工具负责**零成本地执行**。（例子：import 缺失 → 已经是 goimports；字节计数期望 → 算期望值工具。）

## 4. 风险（需要在设计里就挡住）
- **过拟合评测题**：存了某个题的解法，下次同一题当然更好——这是背答案，不是学习。评测要分训练题与留出题，库里只存**通用的坑**，不存整题解法。
- **库污染 / 过期**：只收有证据的；条目记录写入时的代码版本，大改后整体降权。
- **成本收益未知**：和指挥者一样，必须用同样的 A/B 配对评测验证；没有收益就关闭。失败分类显示目前云端配置的主要失败是“字符串度量类的期望算错”，库未必能解决——更可能是工具解决。所以优先级建议：**先做确定性工具（有数据支持），库先做设计和最小原型。**

## 5. 建议的下一步（等你定）
1. 先做失败分类里最大类的确定性核对（字符串度量），作为第一个“工具”，单独开关，A/B 验证。
2. 同时在账本里加 `failure_signature` 的统计（0 token），看哪些签名反复出现——这是库的数据基础。
3. 用 1–2 周的真实任务数据再决定库的具体形态。
