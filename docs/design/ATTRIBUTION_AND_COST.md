# 归因与成本：怎么少烧 token、怎么不修错的那一边（方案对比与可落地路线）
# Attribution and cost: waste less, repair the right side

状态：**设计与取舍，未实施**（实施项见 [ROADMAP §9](../ROADMAP.md) 的 H 系列）。证据来自 [PROGRESS_2026-10-14_001](../progress/PROGRESS_2026-10-14_001_attribution-error-analysis.md)（一次真实运行的逐调用核对）和 `ab2` 评测账本。
**读法**：每一节先说“主流怎么做”，再说“我们现在怎样”，最后给**能快速落地**的方案和**停止规则**。凡是需要长期调试、效果无法在回放里验证的方案，都放进“不做”。

## 0. 先把问题说准

用户的几个问题其实是三件事：

| 问题 | 本质 | 本次运行的数据 |
|---|---|---|
| “错误归因”“无意义重复” | **谁错**判断错了，于是对着错的一方花了很多轮 | 14 次工人调用（73% 输入 token）在改一个本来正确的实现 |
| “能不能只改错的代码而不是重写” | **定位**与**编辑粒度** | 这次根本没有错的代码；重写 vs 编辑的钱差 13%（输入主导），差的是风险 |
| “模糊需求”“本地模型换质量”“减少 API” | **用便宜的资源去拿高价值的证据** | 本地模型只做了约 11% 的输入 token，而决定成败的几次判断全在云端 |

三件事的共同答案是同一个：**把“信念”换成“证据”**——判断“谁错”不要靠一个模型的意见，靠**可以复算的信号**；修复不要靠重复次数，靠**信号有没有变化**。

## 1. 主流做法（只列与我们规模相称的）

| 做法 | 核心思想 | 对我们的启发 | 不照搬的原因 |
|---|---|---|---|
| [Agentless](https://arxiv.org/abs/2407.01489) | 不让模型自由探索：**文件→函数→行**三级定位，再用 SEARCH/REPLACE 生成多个候选补丁，用**复现测试+回归测试多数表决**选一个 | 定位与编辑要**结构化、可验证**；候选要用**执行结果**筛，不靠模型自评 | 它修的是“已有大仓库里的真实 issue”；我们修的是自己刚生成的 ≤20 个文件，定位几乎是平凡的（失败的测试名已指向包） |
| [SWE-agent](https://arxiv.org/pdf/2405.15793) 的 ACI | 给模型**为它设计的工具**：编辑命令内置语法检查，失败就拒绝 | 我们的 `edit_file`/`write_file` 已经有“就地检查”（语法、未知导入） | 已有 |
| [Aider 的编辑格式](https://aider.chat/docs/more/edit-formats.html) | 用 **SEARCH/REPLACE 块**只表达改动，比整文件省输出、少误改 | 我们的 `edit_file(old,new)` 就是它 | 已有；省的是输出 token，而我们成本被输入主导 |
| [CodeT](https://arxiv.org/pdf/2207.10397) | 让模型同时生成**多个实现和多个测试**，用**“双重执行一致”**（哪些实现通过相同的测试集合）选最好的实现；错的实现彼此不一致，对的彼此一致 | **多个实现输出同一个值、而期望只有一个**，就该怀疑期望。我们已经有这些实现（glm、Flash、Pro 各写了好几版） | 它假设测试与实现独立采样；我们的测试是单个 Tester 写的，所以要借“实现之间的一致”来反查测试 |
| [AlphaCodium](https://arxiv.org/pdf/2401.08500) | 多阶段**以测试为锚点的迭代流**：先在已知可靠的测试上稳定，再加 AI 生成的测试 | **可靠的锚点**优先：验收条款里的字面量比 Tester 的推导可靠 | 我们已经把验收条款作为首要依据 |
| [ClarifyGPT](https://arxiv.org/abs/2310.10996) | 先检测需求是否有歧义（让模型生成多个解，看**行为是否分歧**），有歧义就**问用户**，再生成 | 模糊需求的处理是“**先检测、再问或做假设并写明**”，而不是硬做 | 完整版要多次生成再比较，贵；我们用本地模型一句话判断就够 |
| [Large Language Monkeys](https://arxiv.org/abs/2407.21787) | 重复采样能提高“覆盖率”，但**瓶颈是验证**：没有可靠验证器时，多数表决/奖励模型很快饱和 | “多采样”只在有**执行验证器**的地方有价值；我们的验证器（真实运行测试）正是被错测试污染的那个 | 我们的 best-of-N 实验也没有收益（已记录） |
| PAL（程序辅助推理，通用知识，**未检索核对**） | 让模型写**代码**去算，而不是心算 | 期望值的“推导”可以让模型**写一段程序再执行**，规避 LLM 的算术弱点 | 需要沙箱执行；作为第二档方案（H6） |

**一句话总结**：主流在“修复”上的共识是 **结构化定位 + 最小编辑 + 用执行结果筛选**；在“测试不可靠”上的共识是 **用独立来源交叉验证**。我们缺的不是修复手段，而是**交叉验证没有进入默认流程**。

## 2. 对我们意味着什么：六个落点

### 2.1 归因：把“谁错”变成证据问题
现状：默认路径上第一道仲裁是 Diagnoser（一个 Pro 模型问“这个期望对吗”）。我们自己的测量说这类问法**召回只有 26–33%**（被声明的值锚定）；盲推导再比较是 91%；而 `test_audit`、`assertion_referee` 正是后者，却默认关。

**证据层次**（由便宜、确定到贵、有随机性）：

| 层 | 信号 | 成本 | 说明 |
|---|---|---|---|
| 0 | **实际值稳定（S1）**：同一断言实际值连续 3 次观察相同、其间改过 ≥2 次代码 | 0 | 触发的是“仲裁”，不是“结论”：可能是测试错，也可能是工人卡住了 |
| 1 | **多实现一致（S2）**：不同模型的实现输出相同的值 | 0 | S1 的跨模型版；也是 CodeT 思想 |
| 2 | **盲推导审计（S3）**：Flash×3 只看输入、不看期望，再比较 | ≈¥0.002–0.01 | 实测抓到 2–3/3 个错用例，有误报与随机性 |
| 3 | **断言裁判（S4）**：A/B 盲选×3 | ≈¥0.003 | 对“要心算的值”会成片出错（6 vs 5 三票错） |
| 4 | **执行为真值（S7，H6）**：让 Flash 写程序算期望再执行 | 一次调用 + 沙箱 | 规避心算；只适合纯函数型任务 |
| 5 | **人**：只在上面都不一致时才问 | 用户时间 | 现有“needs_attention”路径 |

**规则**：证据**叠加**，不押单点；分歧时升到下一层，而不是重复同一层。

### 2.2 无意义重复：预算按信号，不按次数
**定义**：重复 = 在“上一次失败与这一次失败没有可观察差别”的前提下再来一次同样的手段。
**三条硬规则**：
1. 同一失败指纹且实际值不变，最多再给 **1 次**同类手段（S1 触发即停）。
2. **换手段的顺序固定**：已有证据（S1/S2）→ 盲审（S3/S4）→ 另一个模型家族投票（H8）→ 人。不允许“同一个手段 + 更强的模型”作为默认升级。
3. **升级模型必须有“实现错”的证据**（编译/运行时错误、仲裁判实现错）。断言类失败且 S1 触发时，升级的是**仲裁**，不是工人。

### 2.3 精确定位 + 只改错的代码
- 我们的工具已经是 Aider/Claude Code 式的 `edit_file(old,new)`；1 160 次真实工人调用里 `edit_file` 平均输出 149 token，`write_file` 804。**但输入主导成本**（每步重发 ≈5k），所以“少重写”主要买到的是**安全**（不误改别处），不是钱。
- 定位在我们的规模上已经够用：失败路径→包（`repair_scope`）、失败行附近源码（`snippets`）、unittest 的逐行差异（已加）。**不引入 AST/覆盖率定位**（Agentless/AutoCodeRover 的重器，对 ≤20 个文件的新项目性价比低）。
- 真正该做的小事：**把失败测试的源码直接放进修复上下文**（省一次读取），和**“整文件重写与原文件 ≥70% 行相同”时提示改用 edit_file**（H9，低优先）。

### 2.4 模糊需求
主流（ClarifyGPT、Claude Code 的 plan 模式、spec-driven 的工具）的共识：**先检测歧义，再“问”或“假设并写明”**。我们已有：
- Planner 的**澄清请求**（≤3 个问题，`clarification_enabled`）；
- 提示词要求**把边界约定写进验收**（空输入、表头、末尾换行……）；
- 新任务页的**估计器**（本次新增）会把模糊目标判为“有风险”。

分三档落地（只做前两档）：

| 档 | 做法 | 工作量 | 状态 |
|---|---|---|---|
| V1 | 估计器多返回 ≤3 个**带默认值的问题**（“空输入输出什么？”）；页面显示成单选，**默认已选**，点“按默认继续”即可；答案追加到目标里 | 1 天（模式 + 页面） | 路线图 H10 |
| V2 | `fits=risky` 时默认走“先看方案再生成”（逐步确认），**把假设清单摆在用户面前**批准 | 0.5 天 | 路线图 H10 |
| V3 | 不好写自动测试的任务（界面、随机、开放式）：程序自己判断怎么验证，最后给用户一个**可执行的验证方法**（例如示例会话 + 一条命令） | 设计级，数天到数周 | **只写进路线图，不做** |

### 2.5 本地模型怎么“用时间换质量”
**能做、数据支持**：
- 预检/估计/日志摘要这类“一句话判断”（已用）；
- **首版实现**（glm/qwen 写首版，几秒；本次 4 次首版调用里 3 次是本地）；
- **独立投票者**：与 DeepSeek 不同家族，错误不相关。我现场测了一次 LCS 的 10 个用例：gemma4:12b 抓到 2/3 个错用例、0 误报（74 s）；qwen3.5:9b 2/3、2 误报（19 s）；glm-4.7-flash 0/3。**n=1，只能说“值得在 184 条审计数据集上免费跑一轮”（H8）**，不能说“能替代 Flash”。

**不做、数据不支持**：
- 本地当**修复工人**：7 次实测只封过 1 个很小的包（PROGRESS_2026-10-13_004 §4）；增加本地尝试次数只增加墙钟时间。
- 本地当**算术裁判**：glm 在审计里 0/3。
- 多次采样 + “最像”的实现：没有可靠验证器时收益饱和（Large Language Monkeys 的结论，也是我们 best-of-N 的实测）。

**时间换质量的真正落点**是：**同一个便宜的验证做 N 遍**（审计×3、裁判×3），每一遍都是一次独立的“盲”判断；它换的是**确定性**，不是更好的代码。

### 2.6 预算与估计（本次已做的小改动）
新任务页的估计：难度等级 → token 三档（0.6×/1×/2.5×，基线 = 评测的单任务上限公式 40k+15k×等级）→ 价格区间（各云端模型 token×85:15 混合单价）。**它给的是建议**，且在回放里可以校准：H11 用账本里的真实用量回填，检验“标准档”是否覆盖 ≥80% 的通过运行（目前只有一次运行的对照：LCS 估计 100k，实际 96k）。

## 3. 方案清单（H 系列）：证据、工作量、风险、验收、停止规则

排序依据：**(证据强度 × 影响) ÷ (工作量 × 对默认流程的风险)**。每项都满足冻结规则：写明痛点、**替换/收紧**某个现有东西（净代码不增加或增加极少）、一天内能做完。

| 编号 | 做什么 | 证据 | 工作量 | 风险 | 验收（先零 token 回放，再真实复跑一次） | 停止规则 |
|---|---|---|---|---|---|---|
| **H1** | **审计在用户默认运行方式（v2repair）下默认开**：`Console._runtime_policy` 对 `v2repair` 加 `test_audit: True`；v1/其它不变，**等价检查不变** | 配对评测 audit 更好 5 / 更差 0 / 平 12，16/21 vs 11/20 通过，¥0.267 vs ¥0.418；本次回放 ¥0.002 抓 2–3/3 | 0.5 天 | 低：审计失败不挡规划；误报最多丢掉一个正确用例（保留 ≥3 个） | ① 单测：策略出现在 v2repair、不出现在 v1；② LCS 真实复跑 3 次：至少 2 次丢掉 ≥2 个错用例并通过，总 token ≤ 50k、花费 ≤ ¥0.3 | 3 次里有 1 次因误丢正确用例而被独立判官判假通过 → 撤回默认 |
| **H2** | **S1 触发仲裁**：修复工人（V2 与 V1 的修复循环）记录失败断言的实际值；3 次观察相同且改过 ≥2 次 → 停止，调**裁判**（Flash×3）；裁判说测试错 → 直接走“修订测试”（把裁判文本写进指令）；说实现错 → 再给 1 次修复机会并带上裁判文本。**同时关掉“第 2 次修复自动放大范围”**，改为“证据涉及才放大” | 回放 10 个任务：触发 3 个，2 个之后修订了测试；LCS：第 4 次工人调用触发，触发后还花了 10 次 | 1 天 | 中：误触发会提前打断一次本来能修好的实现修复 → 用“仲裁而不是结论”缓解 | ① `replay_signals.py` 作为回归（10 个任务：触发数、精度不低于现在）；② 单测覆盖“触发→裁判→两种走向”；③ LCS 真实复跑：调用 ≤ 14、token ≤ 60k；④ 在 grades/bank 各复跑 2 次，通过数不低于现在 | 回放里出现“触发后任务本可只靠实现修复就通过”的例子 ≥2 个 → 把阈值从 3 次观察提到 4 次，再不行就撤 |

| **H8** | **本地模型当第二位盲推导者**：在 `.masa/test_reliability/audit.json`（184 条）上**免费**跑 gemma4:12b / qwen3.5:9b / glm | LCS 现场数据（n=1） | 0.5 天跑 + 0.5 天看 | 无（只是测量） | 召回 ≥80% 且误报 ≤15%，才把它加入审计的投票（与 Flash 组合）；否则关闭这条路 | 不达标就把“本地当审计者”划掉 |
| **H9** | `write_file` 覆盖已有文件且与原文件 ≥70% 行相同 → 回应“请用 edit_file”并计一次“无意义动作” | 383 次 write 平均输出 804 token，edit 149 | 0.5 天 | 低 | 单测；真实复跑 write 次数下降 | 误拒绝了合理的整文件重构 → 阈值提高到 85% |
| **H10** | **模糊需求 V1/V2**：估计器多返回 ≤3 个带默认值的问题；`fits=risky` 默认“先看方案” | ClarifyGPT 的结论；估计器已能判“有风险” | 1.5 天 | 低：只改新任务页与估计器 schema | 5 个模糊目标（页面里的推荐）每个都出 ≥1 个合理问题；“按默认继续”一键走通 | 问题质量差（本地模型）→ 改用 Flash 出问题（¥0.002） |
| **H11** | **估计校准**：用账本里的真实用量回填，检验“标准档”覆盖率 | 目前只有 LCS 一例 | 0.5 天（零 token） | 无 | 在全部历史账本上，标准档覆盖 ≥80% 的通过运行；否则调系数 | — |

**推荐的第一批（总共约 3 天，几乎不花 token）**：H4 → H3 → H1 → H2 → H5。H6/H7/H8 是“先测量再决定”的第二批；H9–H11 是顺手的第三批。

## 4. “不做”清单（为了避免过度设计）

- **不加新角色**（不做“管理者”“审查者”常驻角色）：之前的指挥者实验没有收益（已记录）；这里的每一层证据都是**一次函数调用**或**确定性解析**，不是长期在线的 agent。
- **不做 AST/覆盖率定位**、**不做多候选补丁投票**：规模不够，收益饱和。
- **不让本地模型做算术裁判或修复工人**：数据不支持。
- **不加新开关**：H1 只是改 `v2repair` 的默认策略；H2–H5 直接改行为，不增加设置项（冻结规则）。
- **不碰默认的 V1 流程**：所有改动先落在 `v2repair`（用户默认）；`loop_equivalence` 与黄金提示词保持原样。
- **模糊需求 V3（自动生成验证方式）只写路线图**。

## 5. 怎么证明没有过度优化

每个 H 项目的验收都分三步，**前两步零 token**：
1. **账本回放**（`scripts/eval/replay_signals.py` 与它的后继）：在已有的 10+ 个修复任务上，信号触发率、精度、会省多少调用，**先算出来**。
2. **单元测试**：触发条件与走向；默认流程等价检查 IDENTICAL。
3. **一次真实复跑**同一个任务（LCS），看调用数和 token 是否落在预期区间。

**总费用上限**：H1–H5 的真实复跑合计 ≤ ¥1.5（只用 Flash 与已有 Pro 设置，复跑 LCS 3 次 + grades/bank 各 2 次）；H6–H8 ≤ ¥1。超出先停下来问。
**每项最多 2 天**；做不出验收数字就撤，不留半成品。
