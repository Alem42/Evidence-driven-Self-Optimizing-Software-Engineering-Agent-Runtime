# 新机制审查

这一步只做判断，不写实现代码。审查是为了避免再次出现“做完才被数据否决，最后又删掉”。

## 1. 先读现状

- `docs/handoff/CURRENT.md`：当前断点、待拍板事项和冻结范围。这里的规则优先于本文的默认值。
- `docs/ROUTE_REVIEW_2026-10-23.md` 和 `docs/ROADMAP.md`：路线判断与优先级。如有更新的复盘，以更新的为准。
- `docs/EVIDENCE.md`：测过什么、结果如何。

`docs/` 只在本地，缺失时要说明，不要凭记忆补。

还要搜索代码和提交历史，确认是否已有类似实现，或曾经做过又删除。已删除的包括指挥者、调优器、经验库、best-of-N、Planner 示例、包间契约，删除前的版本在 tag `archive/pre-prune-2026-10`。重提这类机制时，要说明这次有什么新证据。

## 2. 回答六个问题

1. **缺口**：解决哪个已观察到的问题？给出账本、评测或探针证据。“看起来有用”和“别的项目都有”不算证据。
2. **类型**：属于引擎、验证、设施还是体验？设施指看门狗、通知、检视器、让位这类。按 `CURRENT.md` 的冻结规则判断。在系统能跑完真实的几小时任务之前，设施类默认不做。
3. **更简单的方案**：改提示词、确定性检查、调整已有参数、修 bug，能否解决？能用确定性代码就不要增加 LLM 调用。
4. **验收与停止**：写明指标、阈值、样本量、费用上限和撤回条件。验证类机制要先在探针上达到召回 ≥ 60%、误报 ≤ 15%，才能接入主流程。比较优劣时必须带样本量和 p 值。
5. **代价**：新增多少代码、开关、角色和调用？每个任务多花多少 token 和时间？删除或替换什么？默认结果是净复杂度不增加。
6. **验证路径**：能否先用已有账本做零 token 回放？能否在单个样本上验证？默认关闭，A/B 通过后才开启。

## 3. 反驳一次

写结论前，站在反对者的角度给出最强的反对理由，并检查：

- 这是否只是把问题往后推，比如为上一个补丁再加一个补丁？
- 同家族模型审查同家族模型，是否真有独立性？
- 现有评测能否测出这个机制的好坏？如果测不出，先解决评测问题。

## 4. 给出结论

只能选一个：

- **做**：证据充分、验收明确，而且代价可接受。
- **先测**：方向合理但证据不足。给出最小实验，不写正式实现。
- **不做**：没有证据、与路线冲突，或有更简单的替代方案。说明什么新证据出现时才重新考虑。

证据不足时，不要因为用户表现出兴趣就选“做”。

## 输出格式

1. **结论**：做 / 先测 / 不做，加一句理由。
2. **证据**：已验证的事实和推断分开写，并注明来源。
3. **更简单的方案**。
4. **验收与撤回条件**。
5. **代价**：新增什么，删除什么。
6. **最强反对理由**。
7. **下一步**：最小的一步，以及需要用户拍板的事。

审查结束后等待用户决定，不要直接开始实现。
