# 复盘一次真实运行

目标是用证据回答“这次到底发生了什么”，再做最小修复。没有证据的环节要写成“推断”，不要写成结论。

## 1. 定位运行

主状态库的任务：

```bash
PYTHONIOENCODING=utf-8 python scripts/eval/task_ledger_report.py <目标里的关键词> --state .masa --days 30
```

- 评测运行的账本在 `.masa/<评测名>/bench/state/<运行>/`，汇总在 `.masa/<评测名>/summary.json`。
- 一个任务通常有多个 run（规划、草稿、验证、修复），用 `parent_run_id` 串起来，按时间读完整条链。
- 找不到就说明查了哪里，请用户提供任务名或时间，不要拿相似的运行代替。

## 2. 读原文

用 `masa.infrastructure.store.Store` 读事件，用 `store.read(payload['response_ref'])` 读模型输出。至少读：

- 规格、验收条款和测试用例的原文（Architect，旧账本里是 Planner 和 Tester）。
- 每次 Diagnoser 的裁决及理由。
- 修复工人的每一步，包括 `note`。工人的怀疑常常只写在这里。
- 失败检查的实际值与期望值，以及修复前后代码的差异。

只看事件名或摘要不算读过。

## 3. 独立判断对错

1. 自己算出或运行得到真值，不要因为测试、验收或 Diagnoser 这样写就相信它。
2. Gate 通过时也要核对：用真实程序或独立判官跑一遍边界输入，确认是否假通过。
3. “失败数变少”不等于进步，要确认不是实现在迎合错误的测试。

## 4. 写根因链

按时间写，每一环都附证据（run 前缀、调用序号或事件名、原文短摘）：

| 环节 | 发生了什么 | 证据 | 本应在哪里被发现 |
|---|---|---|---|

把最上游的原因归到一层：规格 / 测试 / 实现 / 归因裁决 / 重试策略 / 引擎 / 基础设施 / 评测本身。先对照记忆里的失败模式表（`project-masa-recurring-failure-patterns`），确认是旧问题复发还是新问题。

## 5. 算账

- 用报告中的数字统计各阶段的调用数和输入 token，算出花在错误方向上的比例。
- 只有样本足够时才说趋势。单次运行只说明这一次。

## 6. 修复

只有用户要求修复时才改代码，否则到这里给出建议并停下。修复时：

1. 先写一个由这次失败倒推的零 token 回归测试，确认它在修复前失败。
2. 做最小修复。修复若需要新机制或新开关，先走 `mechanism-review`。
3. 跑相关测试。

## 7. 复跑

- 只复跑同一个样本，不跑全量。
- 花钱或占用显卡前，先说明模型、预计费用和上限，等用户确认。
- 显卡归用户：结束后卸载模型，确认 Ollama 的 `/api/ps` 为空。

## 输出格式

1. **结论**：一两句话说清发生了什么。
2. **根因链**：上面的表。
3. **花费**：错误方向占多少，来自账本。
4. **修复**：已做的或建议的，以及回归测试。
5. **未验证**：哪些是推断，哪些没有复现。

如果证据不足以确定根因，直接说不确定，并写明还需要什么证据。
